# Issue 385263984__060d45f1a9

**Bucket:** REPRODUCED

## Summary
The issue claims that a `SameSite=Strict` cookie is sent in a cross-site request when a URL is downloaded via `chrome://download-internals/` (Start Download). This was verified: a `SameSite=Strict` cookie for `127.0.0.1:18080` was attached to the download request triggered from `chrome://download-internals/`, while the same cookie was correctly withheld from a normal cross-site subresource request.

## Environment
- OS/runtime: Windows 11 (10.0.26200), PowerShell 7.6.3, Node v24.13.1, Python 3.14.2
- Browser: `C:\Program Files\Google\Chrome\Application\chrome.exe`, Chrome 151.0.7922.174 (issue was reported against Chromium 131.0.6778.139)
- Automation path: CDP over `--remote-debugging-port=9222` (Node WebSocket client), JS `Runtime.evaluate` DOM bridge
- Required environment (per issue): Chrome with `chrome://download-internals/` available; Burp Suite to modify a `Set-Cookie` response. Adaptation: Burp MITM replaced by a local HTTP server that sets the identical cookie (`test=test; SameSite=Strict; Path=/`); httpbin.org replaced by the same local server so request headers are observable server-side.
- Attachments used: none

## Reproduction

### Steps executed
1. Launched isolated Chrome with a fresh profile and CDP port.
   - cmd: `Start-Process chrome "--user-data-dir=...\repro\issue_385263984__060d45f1a9\profile --remote-debugging-port=9222 --no-first-run --no-default-browser-check about:blank"`
   - verify: `GET http://127.0.0.1:9222/json/version` returned `"Browser": "Chrome/151.0.7922.174"`.

2. Started two local HTTP servers (127.0.0.1:18080 and 127.0.0.2:18080) that log all request headers to `requests.log`; `/set` returns `Set-Cookie: test=test; SameSite=Strict; Path=/`; `/cookies` returns an attachment body and is the probe endpoint.
   - cmd: `python server.py 127.0.0.1 18080` and `python server.py 127.0.0.2 18080`
   - verify: `GET http://127.0.0.1:18080/marker` → HTTP 200; `GET http://127.0.0.2:18080/xsite` → HTTP 200.

3. Navigated the browser tab to `http://127.0.0.1:18080/set` (sets the Strict cookie).
   - cmd: CDP `Page.navigate` + `Runtime.evaluate`
   - verify: `document.readyState` = `complete|http://127.0.0.1:18080/set`; `document.cookie` = `"test=test"`; later `Network.getAllCookies` shows `{"name":"test","value":"test","domain":"127.0.0.1","path":"/","sameSite":"Strict",...}`.

4. Control A — same-site fetch (Strict cookie should be sent): `fetch('/cookies', {credentials:'include'})` from the `/set` page.
   - cmd: CDP `Runtime.evaluate`
   - verify: returned `200|cookie-probe-body`; server log shows the `/cookies` request with `"Sec-Fetch-Site": "same-origin"` and `"Cookie": "test=test"`.

5. Control B — cross-site subresource (Strict cookie should NOT be sent): navigated to `http://127.0.0.2:18080/xsite` (different site) which embeds `<img src="http://127.0.0.1:18080/cookies">`.
   - cmd: CDP `Page.navigate` + wait
   - verify: active URL read back as `http://127.0.0.2:18080/xsite`; server log shows the image request to `/cookies` with `"Sec-Fetch-Site": "cross-site"` and **no** `Cookie` header.

6. Opened `chrome://download-internals/`. (First attempt redirected to `chrome://debug-webuis-disabled/`; enabled debug pages by clicking the `cr-button` "Enable internal debugging pages" on `chrome://chrome-urls/`, verified the button state changed to "Disable internal debugging pages", after which the page loads normally.)
   - cmd: CDP `Page.navigate`
   - verify: `document.readyState` = `complete|chrome://download-internals/`; page text begins `"Download Internals\nStart Download\n Download\nService State\nState: READY..."`; DOM contains `INPUT#download-url` (type=url) and `BUTTON#start-download` ("Download").

7. Entered `http://127.0.0.1:18080/cookies` in the Start Download input and clicked the Download button.
   - cmd: CDP `Runtime.evaluate` (`input.value = 'http://127.0.0.1:18080/cookies'` + `input`/`change` events, then `#start-download.click()`)
   - verify: input value read back after fill = `"http://127.0.0.1:18080/cookies"`; page "Entry Requests" table shows `ACCEPTED  Debugging  d4765e89-1834-42b6-a2f0-2c0b2b680c8a`; "Completed/Failed Downloads" table shows `SUCCEED  Debugging  d4765e89-...  http://127.0.0.1:18080/cookies ... 17`.

8. **Triggered observable (the issue's claim):** the download request reached the server carrying the Strict cookie.
   - cmd: readback from `requests.log`
   - verify: between markers `before-download-click-4` and `after-download-wait-4` the server received `GET /cookies` with `"Sec-Fetch-Site": "none", "Sec-Fetch-Mode": "navigate", "Sec-Fetch-Dest": "empty"` (browser-initiated download request, no initiator site) and **`"Cookie": "test=test"`** — the `SameSite=Strict` cookie was sent, unlike control B where a cross-site request to the same URL carried no cookie.

9. Confirmed the download completed and the file was written.
   - cmd: `Get-Item "...\profile\Default\Download Service\Files\d4765e89-1834-42b6-a2f0-2c0b2b680c8a"`; `certutil -hashfile ... SHA256`
   - verify: file exists, 17 bytes, SHA256 `d168c5cffdcd0d9ccde1e18a7f2edb2aa1028bfc8402a35cb7c3a887c9e110b8` (matches `cookie-probe-body`); screenshot `download_internals_after.png` captured (277,044 bytes).

## Notes
- Tested on Chrome 151.0.7922.174 (issue reported on 131.0.6778.139); the reported behavior still occurs on the current build.
- Environment adaptations (documented, not invented steps): Burp Suite interception was replaced by a local server setting the identical cookie; httpbin.org was replaced by the same local server so the request headers could be read server-side. The essential precondition (a `SameSite=Strict` cookie for the target origin) and the observable effect (Strict cookie attached to the download request initiated from `chrome://download-internals/`) match the issue exactly.
- This Chrome build disables internal debug pages by default; `chrome://download-internals/` was reachable after enabling them via `chrome://chrome-urls` ("Enable internal debugging pages" button). This is a local-environment prerequisite, not part of the issue.
- Contrast evidence: the same cookie was sent on a same-site fetch (control A) and withheld on a cross-site `<img>` request (control B), showing the cookie is Strict-behaving in normal request contexts and that the download path is what attaches it.
