# Issue 440868608__73cee68214

**Bucket:** REPRODUCED

## Summary
The issue claims that a password saved in Chrome (Google Password Manager) is
autofilled in plaintext into a login page after a simple click, and that the
plaintext can then be revealed by changing the input type from `password` to
`text` — without any computer-password / master-key prompt. That observable
effect was reproduced and verified end-to-end in an isolated Chrome profile.
The issue discussion records that Chromium closed this as WontFix, referencing
the security FAQ section on unmasking passwords with developer tools; the
behavior itself is present in the current Chrome build.

## Environment
- OS/runtime: Windows 10.0.26200 (x64), PowerShell 7, Node v24.13.1, Python 3.14.2
- Browser: `C:\Program Files\Google\Chrome\Application\chrome.exe`, version
  151.0.7922.174 (issue was filed against 139.0.7258.139; behavior persists in
  current stable)
- Automation path: CDP over `--remote-debugging-port=9222`, driven by a Node
  WebSocket client (`Runtime.evaluate`, `Input.dispatchMouseEvent`,
  `Page.navigate`); no OpenClaw browser tools available, no image tools used
- Required environment: a Chrome profile containing a saved credential for the
  target origin, and a login page on that origin (local attacker with access to
  the machine — simulated by an isolated local profile)
- Attachments used: none (the issue references a demonstration video but gives
  no attachment URL; the textual steps were sufficient)

## Reproduction

### Steps executed
1. Preflight: killed stale Chrome processes; verified clean state.
   - cmd: `Get-Process chrome -EA SilentlyContinue | Stop-Process -Force`
   - verify: `remaining=0` (process list returned no chrome processes)
2. Recorded browser version from the executable.
   - cmd: `(Get-Item 'C:\Program Files\Google\Chrome\Application\chrome.exe').VersionInfo.ProductVersion`
   - verify: `151.0.7922.174`
3. Created isolated repro workspace and a local login page with `autocomplete="username"` /
   `autocomplete="current-password"` fields and empty initial values.
   - cmd: `New-Item ... repro\issue_440868608__73cee68214\profile` ; wrote `site\login.html`
   - verify: `login.html` exists, 456 bytes, fields `#user`/`#pass` have no `value` attributes
4. Started a local HTTP server for the page origin.
   - cmd: `python -m http.server 8123 --bind 127.0.0.1 --directory <site dir>`
   - verify: `GET http://127.0.0.1:8123/login.html` returned `HTTP 200 len=456`
5. Launched Chrome with a fresh profile and CDP port.
   - cmd: `Start-Process chrome.exe --user-data-dir=...\profile --remote-debugging-port=9222 --no-first-run --no-default-browser-check --disable-sync`
   - verify: `http://127.0.0.1:9222/json/version` returned `"Browser": "Chrome/151.0.7922.174"`
6. Created `chrome://password-manager/passwords` target and saved a credential
   for `http://127.0.0.1:8123` via the WebUI's own `chrome.passwordsPrivate.addPassword`
   API (`{url, username, password, note, useAccountStore:false}`).
   - cmd: CDP `Runtime.evaluate` on the chrome://password-manager target
   - verify: `addPassword` resolved `{ok:true}`; `getSavedPasswordList()`
     returned entry `{"id":0,"username":"repro_user"}`; on-disk store
     `profile\Default\Login Data` exists (40,960 bytes; hash skipped — file
     locked by the live browser process, expected)
7. Navigated the page target to the login page and confirmed empty initial state.
   - cmd: CDP `Page.navigate` to `http://127.0.0.1:8123/login.html`; `Runtime.evaluate` readback
   - verify: active tab URL read back as `http://127.0.0.1:8123/login.html`;
     `BEFORE_CLICK {"user":"","pass":""}`
8. Performed the issue's first step — visiting the saved site and focusing the
   login form (single left-click on the username field, real mouse events).
   - cmd: CDP `Input.dispatchMouseEvent` mousePressed/mouseReleased at field center
   - verify: `AFTER_CLICK {"user":"repro_user","pass":"ReproSecret_440868608","passType":"password"}`
     — Chrome autofilled the saved plaintext into both fields with no
     computer-password/master-key prompt
9. Performed the issue's second step — changing the input type from `password`
   to `text` and reading the value.
   - cmd: CDP `Runtime.evaluate`: `document.getElementById('pass').type = 'text'`
   - verify: `UNMASK {"passTypeNow":"text","passValueAfterTypeChange":"ReproSecret_440868608"}`
     — the plaintext saved password is revealed, matching the saved credential
     exactly

## Notes
- The observable effect is verified exactly as described in the issue: an
  autofilled saved password is present as plaintext in the page DOM and is
  revealed by switching the input `type` from `password` to `text`. This
  requires only local access to an unlocked Chrome session; no master-key /
  computer-password prompt is shown during autofill.
- Issue discussion records Chromium closing the report as WontFix with a
  pointer to the security FAQ ("What about unmasking of passwords with the
  developer tools"); that context is recorded here factually and the behavior
  was confirmed present in the current stable build (151.0.7922.174 vs.
  139.0.7258.139 in the report).
- The issue's referenced video attachment was not needed: no attachment URL is
  present in the issue text and the described mechanism was reproducible
  directly from the written steps.
- One attempt was sufficient; no retries or fallback UI automation were needed.
