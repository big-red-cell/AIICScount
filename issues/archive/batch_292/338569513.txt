dr...@nordsec.com： <p>A short update to the initial info.</p> <p><strong>The problem</strong></p> <p>Pre-conditions:</p> <ul> <li>Connected to VPN</li> <li>Having an IPv6 address assigned to a network interface. The interface or the address do not have to be actually used.</li> </ul> <p>After visiting <a href="https://browserleaks.com/webrtc" data-b-widget="url" data-b-original-href="https://browserleaks.com/webrtc" data-b-redirected-href="https://www.google.com/url?q=https://browserleaks.com/webrtc&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2dh2t7Y5mRmu4-1lK3CkOV">https://browserleaks.com/webrtc</a> and granting audio and/or video permissions, a public IPv6 address appears on the screen.</p> <p><strong>The cause</strong></p> <p>My understanding of WebRTC implementation is rather limited and comes mainly from studying the current implementation. If I am not mistaken, IP address selection of WebRTC candidates takes the following steps:</p> <ul> <li>Network interface information is gathered using <code>getifaddrs()</code> (for Android 14 on Pixel 6 this seems to be the following implementation <a href="https://chromium.googlesource.com/chromium/src/+/e07636ba68bd27291fd4609246ed80d73875d7cb/net/base/network_interfaces_getifaddrs_android.cc#154" data-b-widget="url" data-b-original-href="https://chromium.googlesource.com/chromium/src/+/e07636ba68bd27291fd4609246ed80d73875d7cb/net/base/network_interfaces_getifaddrs_android.cc#154" data-b-redirected-href="https://www.google.com/url?q=https://chromium.googlesource.com/chromium/src/%2B/e07636ba68bd27291fd4609246ed80d73875d7cb/net/base/network_interfaces_getifaddrs_android.cc%23154&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1NYWUg_LerTtqRCPOrpNxB">https://chromium.googlesource.com/chromium/src/+/e07636ba68bd27291fd4609246ed80d73875d7cb/net/base/network_interfaces_getifaddrs_android.cc#154</a>  and not <code>getifaddrs()</code> from bionic).</li> <li>Collected network information is filtered on several locations based on various criterias. An interesting one is that tracking users via MAC based IPv6 addresses is prevented <a href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#161" data-b-widget="url" data-b-original-href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#161" data-b-redirected-href="https://www.google.com/url?q=https://webrtc.googlesource.com/src/%2B/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc%23161&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1aQHla-wIzPtyuC5T4rBEO">https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#161</a> and this might be a similar situation.</li> <li>All IP addresses of the same interface are then merged based on interface names and network prefixes <a href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#372" data-b-widget="url" data-b-original-href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#372" <li>And finally, from the merged interfaces the <code>best IP</code> is selected, with a bias towards global IPv6 addresses <a href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#1154" data-b-widget="url" data-b-original-href="https://webrtc.googlesource.com/src/+/569849e88585580e7ad7e542dd982415dddd7b9c/rtc_base/network.cc#1154" </ul> <p>As a result of such an approach WebRTC will likely end up selecting global IPv6 addresses as <code>best IPs</code> for all of the interfaces which have such addresses assigned to them. <br> Interestingly, because of the approach of getting only 1 <code>best IP</code>, if there are multiple IPv6 addresses with the same network prefix assigned to an interface, only 1 of them will be fetched by WebRTC. <br> The issue is analyzed in more detail in the attached <code>WebRTC IPv6 Leak Report.pdf</code>.</p>
