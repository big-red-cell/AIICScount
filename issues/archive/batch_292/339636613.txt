bu...@google.com： <hr> <h3>Report description</h3> <p>Sandbox Escape via Symbolic Links in Web Accessible Resources on macOS and Linux</p> <hr> <h3>Bug location</h3> <h4>Where do you want to report your vulnerability?</h4> <p>Chrome VRP – Report security issues affecting the Chrome browser. <a href="https://bughunters.google.com/about/rules/5745167867576320/chrome-vulnerability-reward-program-rules" data-b-widget="url" data-b-original-href="https://bughunters.google.com/about/rules/5745167867576320/chrome-vulnerability-reward-program-rules" data-b-redirected-href="https://www.google.com/url?q=https://bughunters.google.com/about/rules/5745167867576320/chrome-vulnerability-reward-program-rules&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw31QXnMd5mgu42yXMeOAv3K">See program rules</a></p> <hr> <h3>The problem</h3> <h4>Please describe the technical details of the vulnerability</h4> <h3>Overview</h3> <p>The vulnerability exists due to the Chrome browser&#39;s improper handling of symbolic links included in the <code>web_accessible_resources</code> section of Chrome extensions&#39; <code>manifest.json</code>. This issue occurs on macOS and Linux systems where symbolic links can directly reference system files.</p> <h3>Mechanism</h3> <p>In Chrome extensions, <code>web_accessible_resources</code> are intended to allow web pages to directly access specific resources within an extension&#39;s directory. However, if a symbolic link is added to this list, Chrome does not correctly resolve the symbolic link to verify if the linked file is within the extension&#39;s directory. Instead, Chrome treats the symbolic link as a valid file within the extension, regardless of its actual location in the file system.</p> <h3>Exploitation</h3> <p>An attacker can create a Chrome extension that includes symbolic links to sensitive system files and distribute this extension. When loaded by Chrome, the extension can use these symbolic links to access files outside of the supposed sandboxed environment, effectively escaping the sandbox.</p> <h3>Extended Exploitation</h3> <p>Once the extension accesses the sensitive data, it can be programmed to send this data to a remote server. This is achieved by scripting the extension or an associated malicious web page to fetch the symlinked file content when activated and then send this content to the attacker&#39;s server.</p> <h3>Impact</h3> <p>This vulnerability allows for unauthorized read access to system files and the potential exfiltration of sensitive data, compromising the confidentiality and integrity of user data on affected systems.</p> <h4>Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4> <h3>Who Can Exploit the Vulnerability</h3> <p>This vulnerability can be exploited by any malicious actor with the ability to create and distribute a Chrome extension.</p> <h3>What They Gain</h3> <p>Exploiters of this vulnerability can gain unauthorized access to sensitive system files on users&#39; machines running macOS and Linux. By including symbolic links to critical files in an extension, attackers can bypass Chrome&#39;s sandboxing mechanisms designed to isolate extension functionality from the underlying operating system.</p> <h3>Potential Gains Include:</h3> <ul> <li><strong>Access to Sensitive Information</strong>: Exploiters can access sensitive files such as personal data, system configurations, or even security credentials stored on the system.</li> <li><strong>Data Exfiltration</strong>: The ability to exfiltrate this data to remote servers provides attackers with the means to steal identities, perform further attacks, or sell sensitive information.</li> </ul> <hr> <h3>The cause</h3> <h4>What version of Chrome have you found the security issue in?</h4> <p>124.0.6367.119</p> <h4>Is the security issue related to a crash?</h4> <p>No</p> <h4>Choose the type of vulnerability</h4> <p>Sandbox Escape</p> <h4>How would you like to be publicly acknowledged for your report?</h4> <p>Yair Hamo, security researcher</p>

rd...@chromium.org： <p>Thanks for the detailed report!</p> <p>Symlinks are allowed in unpacked extensions.  The code responsible for this is that related to the enum Extension::FOLLOW_SYMLINKS_ANYWHERE, which controls whether symlinks will be followed outside of the extension&#39;s package.  If an extension is distributed through the store (or otherwise through a crx), symlinks are only followed within the extension&#39;s own directory.</p> <p>The reason for this is to aid in certain development workflows, such as where a developer may be referencing a common library on disk during development that would later be added into the extension package in a processing step (not too dissimilar from what happens in some web development and through some nodeJS setups).</p> <p>Physically-local attacks <a href="https://chromium.googlesource.com/chromium/src/+/main/docs/security/faq.md#Why-arent-physically_local-attacks-in-Chromes-threat-model" data-b-widget="url" data-b-original-href="https://chromium.googlesource.com/chromium/src/+/main/docs/security/faq.md#Why-arent-physically_local-attacks-in-Chromes-threat-model" data-b-redirected-href="https://www.google.com/url?q=https://chromium.googlesource.com/chromium/src/%2B/main/docs/security/faq.md%23Why-arent-physically_local-attacks-in-Chromes-threat-model&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3bLiuTok_WMk6aCITCr5oF">are outside our threat model</a>, and this also applies to loading unpacked extensions in the Chrome browser -- so if this is only achievable with an unpacked extension, we wouldn&#39;t consider it a security bug.</p> <p>In my quick local testing, I wasn&#39;t able to repro this with a packed extension (IIRC, the behavior should be the same between an extension in the webstore and a .crx file drag-and-dropped on the chrome://extensions page -- though note that those will normally be disabled, too).  If you&#39;re able to repro this with a packed extension, please let us know, but otherwise I think we can close this out as working as intended.</p>
