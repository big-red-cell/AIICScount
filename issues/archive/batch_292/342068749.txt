da...@chromium.org： As with all other of these reports so far, this is not a bug and has misunderstood the issue. The garbaged basic constraints extension has, among other things, garbled the extension type itself. Rather than 2.5.29.19 (basic constraints), the extension type is now 0.29.19, which is not a defined extension.<br><br>This means that every X.509 parser will treat it as an unrecognized extension and not bother parsing the contents at all. That, one presumes, includes Firefox. The error in Firefox likely comes from different checks on what inputs, explicitly configured as trusted, are parsable as trust anchors. Notably whether an X.509v3 trust anchor is required to have a basic constraints extension. (Again, this certificate&#39;s basic constraints extension is not garbled. By changing the extension type, it doesn&#39;t have one.) This is something that X.509 explicitly chooses not to define and there are tons subtle variations on behavior here.<br><br>Additionally, if a bug report that includes the step:<br><br>&gt; Adding the root CA to the system&#39;s trusted root certificate store using certutil.<br><br>It fundamentally cannot be a security bug. You have configured the system to trust that CA. Now, there could be a bug if the semantics of the trust store differ from how Chrome interprets it, but this bug has not demonstrated it because the relevant trust store is not Firefox.
pi...@gmail.com： <p>It seems that when certutil adds the root CA to the system&#39;s trusted root certificate store, Chrome does not care whether the CA contains the basic constraints extension (CA=True). Although this does not comply with RFC 5280 (if the basic constraints extension is not present in a version 3 certificate, then the certified public key MUST NOT be used to verify certificate signatures.), Chrome treats the configuration of system trust for that CA as the most important premise, making this an intended behavior. However, I still recommend not unconditionally trusting the system&#39;s trusted root certificate store. In cases where you cannot ensure that the trusted root certificate store has not been tampered with, it is best to opt for strict verification.</p>
