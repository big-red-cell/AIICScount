ve...@gmail.com： VULNERABILITY DETAILS<br>Chromium and chromium based browsers bleed clear text passwords into the memory from the Chrome default password manager component. This includes both non-synced local passwords and synced passwords from the google account.<br><br>In my investigation I found that &quot;password_manager::PasswordReuseDetectorImpl::passwords_with_matching_reused_credentials_&quot; is populated by the clear text passwords from the password manager upon starting up the browser. <br><br>Password manager stores credentials encrypted, and they are only decrypted when autofill triggers, or when user visits the passwords manager and views credentials there. Chrome also cleans the used &quot;form&quot; after login, leaving the &quot;PasswordReuseDetector&quot; as the only place that reliable bleeds passwords in the memory.<br><br>I&#39;m aware of the FAQ piece: &quot;Why aren&#39;t physically local attacks in chromes threat model&quot;. To me this still looks like a bug since other components of the browser takes care of not leaking the clear text credentials in the memory longer than required, and I wanted to be sure before publishing my tool.<br><br>A better solution to check if the password is being re-used from elsewhere, could be that the password manager credentials also have a hash of the password/credentials and the new potential password is hashed and tested against those. This would mitigate this issue fully.<br><br>VERSION<br>Chrome Version: 126.0.6478.127 (Official Build) (64-bit)<br>Operating System: Microsoft Windows 10 Education N 10.0.19045 N/A Build 19045<br><br>REPRODUCTION CASE<br>Fill up Chrome password manager with credentials, or login and sync your google account to Chrome (Assuming you have stored passwords in the manager elsewhere).<br><br>Build the provided Visual Studio project using Microsoft Visual Studio 2022 (64-bit). Start up the Chrome browser and execute the &quot;CredentialKatz.exe&quot;<br><br>Tool will try to find &quot;~PasswordReuseDetectorImpl(void)&quot; in the __vfptr of PasswordReuseDetectorImpl object to locate the map of passwords_with_matching_reused_credentials_ and dump all current entires of it. To find the virtual function pointer table, the certain byte pattern in chrome.dll must be present, and therefore the tool will only work with the exact given version. <br><br>CREDIT INFORMATION<br>Reporter credit: Aleksi Vepsäläinen

fl...@google.com： <blockquote> <p>I&#39;m aware of the FAQ piece: &quot;Why aren&#39;t physically local attacks in chromes threat model&quot;. To me this still looks like a bug since other components of the browser takes care of not leaking the clear text credentials in the memory longer than required, and I wanted to be sure before publishing my tool.</p> </blockquote> <p>Thanks for taking the time to read the FAQ.  I think the particular case you&#39;re asking about is probably most clearly addressed a bit further down in the FAQ (emphasis mine):</p> <blockquote> <p>What about unmasking of passwords with the developer tools? One of the most frequent reports we receive is password disclosure using the Inspect Element feature (see <a href="https://issues.chromium.org/issues/126398" data-b-widget="issue-reference" data-b-issue-id="126398">Issue 126398</a> for an example). People reason that “If I can see the password, it must be a bug.” However, this is just one of the physically-local attacks described in the previous section, and all of those points apply here as well.</p> <p>The reason the password is masked is only to prevent disclosure via “shoulder-surfing” (i.e. the passive viewing of your screen by nearby persons), not because it is a secret unknown to the browser. <strong>The browser knows the password at many layers, including JavaScript, developer tools, process memory, and so on.</strong> When you are physically local to the computer, and only when you are physically local to the computer, there are, and always will be, tools for extracting the password from any of these places.</p> </blockquote> <p>You&#39;ve discovered one of the places where a password is known to process memory.  The <em>amount of time</em> a password spends in process memory isn&#39;t particularly relevant to the threat model; if the password is in memory at any point (and it must be, for Chrome to function as intended), then it will always be possible for a physically-local attacker to obtain it, and minimizing that time is not an effective mitigation.</p> <p>I&#39;ll be closing this bug as Wontfix.  Do feel free to file another bug in the future if you find a credential leak that doesn&#39;t rely on physically-local access.  Thanks!</p>
