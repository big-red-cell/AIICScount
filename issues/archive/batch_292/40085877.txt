Vulnerability description
to...@gmail.com： <p><strong>VULNERABILITY DETAILS</strong><br> A malicious chrome extension with the permission to &quot;read and change your data&quot; on websites that have previously requested microphone or camera access, can silently access the microphone.  It can also access the camera, but doing so is often a bit more obvious since the camera LED turns on.</p> <p>The demonstration chrome extension (attached) loads &quot;<a href="https://hangouts.google.com/somethingUnique" data-b-widget="url" data-b-original-href="https://hangouts.google.com/somethingUnique" data-b-redirected-href="https://www.google.com/url?q=https://hangouts.google.com/somethingUnique&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3WqD3-05aA16mqlOEnDlf_">https://hangouts.google.com/somethingUnique</a>&quot; into an iframe within the extension&#39;s background.html.  The &quot;/somethingUnique&quot; part of the URL is important - unlike &quot;<a href="https://hangouts.google.com" data-b-widget="url" data-b-original-href="https://hangouts.google.com" data-b-redirected-href="https://www.google.com/url?q=https://hangouts.google.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0Nthryub5TMxb6c8flkucG">https://hangouts.google.com</a>&quot;, it does NOT include an &quot;x-frame-options:SAMEORIGIN&quot; response header.  Instead it returns a 404 page lacking iframe protection, which is successfully iframed into the Chrome extension.</p> <p>When &quot;<a href="https://hangouts.google.com/somethingUnique" data-b-widget="url" data-b-original-href="https://hangouts.google.com/somethingUnique" data-b-redirected-href="https://www.google.com/url?q=https://hangouts.google.com/somethingUnique&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3WqD3-05aA16mqlOEnDlf_">https://hangouts.google.com/somethingUnique</a>&quot; is loaded, it runs a content script that accesses the microphone.  This succeeds if the user is a Hangouts user, and fails silently if they are not.  When successful, the demonstration chrome extension just plays the microphone audio back to the speakers - NOTE THAT THIS MAY CAUSE FEEDBACK so you should either mute your speakers, or plug in headphones!</p> <p>A key thing here is that Chrome gives no feedback that the microphone is being accessed.  No visible tab has the &quot;red recording button&quot;, and the &quot;video camera&quot; icon is missing from the URL bar.</p> <p>Google.com is also vulnerable if you use the &quot;speak your search&quot;.  From a cursory look, it seems docs.google.com is not vulnerable.  It does ask for microphone access if you use the docs speech-to-text feature, but 404s redirect to drive.google.com and have proper iframe protection.</p> <p>I&#39;m not sure if other content permissions like Notifications or the right to run plugins is similarly vulnerable.  I did try the same pattern with maps.google.com and geolocation API, but it seems that Chrome properly fails geolocation requests within an iframe within the extension.</p> <p><strong>VERSION</strong><br> Chrome Version: Version 54.0.2840.71 (64-bit)<br> Operating System: macOS 10.12.1</p> <p><strong>REPRODUCTION CASE</strong></p> <ul> <li>Visit hangouts.google.com and use a hangout.  Give Google access to your microphone and camera.</li> <li>put on headphones!  The demonstration chrome extension plays the microphone audio back out on speakers, which can cause feedback.</li> <li>Install attached Chrome extension.</li> <li>See that the chrome extension was able to abuse the Hangouts microphone access as it&#39;s own.</li> <li>Note that Chrome gives no indication that the microphone is being accessed whatsoever.</li> </ul> <p>It would be straightforward to extract that audio stream to a remote server instead of replaying it.</p>
