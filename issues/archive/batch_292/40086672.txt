It also allows you to specify the fieldname of both the username as the password. By sending the request to a URL that will output the values of these fields in its response, the calling page is able to extract that information from the request.</p> <p>Any page with a form that does some sort of validation will probably do, as long as it returns the sent in data back to the browser. Typical examples could be incompletely filled in registration or contact forms. If the data is not accepted, most sites fill pre-fill the form with the submitted data to prevent the user from having to fill it in all over again because they made a mistake.</p> <p>I&#39;ve also did a test with Tampermonkey and was able to extract the information using the same method. Alternatively, restricting access to the response object of a call including credentials could also be done. va...@chromium.org： Thanks for the report, the discussion so far, and for looping me in.<br><br>My opinion is below. I will be happy to discuss this further with the password manager team tomorrow, and the security team on demand.<br><br>Summary of my opinion:<br><br>* No changes in the CM API needed because of this attack. The security value of the CM API is not diminished.<br>* This attack should be prevented primarily on the server side, e.g., in the way <a href="http://accounts.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://accounts.google.com" data-b-redirected-href="http://accounts.google.com">accounts.google.com</a> do it.<br>* Chrome-side prevention, while theoretically possible, does not seem worth implementing. There would need to be some evidence of this attack having a large enough impact.<br><br>Details:<br><br>This weakness is not specific to Credential Manager (CM) API. An injected script on, say, facebook&#39;s login page can also swap the &#39;name&#39; attribute of the username and password fields before submission, resulting in the password being sent back in plain text as part of the response HTML.<br><br>While it would be beneficial if Chrome could help to protect the user against this attack, this protection is unlikely to be specific to CM API.<br><br>One of the key motivations for CM API is indeed increasing the protection against XSS based attacks aimed at passwords. This does not mean that CM API itself is able to address all such threats. Its design makes it possible to prevent the password ever being shared with the renderer process, a property of its own value, independent of this scenario. There are at least two more known XSS-related threats which cannot be prevented by CM API itself: this issue, and the fact that data stored in CM API can be filled into HTML forms for compatibility reasons. The latter will be addressed by <a href="https://www.google.com/url?q=https://mikewest.github.io/credentialmanagement/writeonly/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1SIYieZUyW3TFNBkJnlUOu" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://mikewest.github.io/credentialmanagement/writeonly/" data-b-redirected-href="https://www.google.com/url?q=https://mikewest.github.io/credentialmanagement/writeonly/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1SIYieZUyW3TFNBkJnlUOu">https://mikewest.github.io/credentialmanagement/writeonly/</a>. This issue here will also need a separate remedy, independent of CM API.<br><br>The best remedy one is found on the server side. Looking at <a href="http://accounts.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://accounts.google.com" data-b-redirected-href="http://accounts.google.com">accounts.google.com</a>, for example, it seems like the two-step login process protects against the threat, without inconveniencing the users in the case of no XSS attack present: first the user needs to enter their username and submit. Then they enter the password on the second submission. If the password does not match, but the username information on the second submission matches that of the first one, the user only needs to enter the password, not the username again. If the username does not match (e.g., as a result of the attack described here), the flow is reset and the username field is shown empty.<br><br>On the Chrome side we could also use the fact that the browser knows all the stored passwords. It could scan the HTML responses for their occurrences and filter them out, in theory. This would have a number of false positives, though. These could be reduced by restricting this protection to, e.g., only generated passwords (which are unlikely to match any real words occurring accidentally in HTML pages). But there would also be performance concerns and an increased complexity in Chrome&#39;s behaviour in general. If we see that the attack&#39;s impact is severe enough to warrant accepting these drawbacks, we can decide to implement some protection like that. I am not currently convinced that this is the case.<br>
va...@chromium.org： vasilii@ and battre@ explained to me a part of the issue which I missed before: the server URL to echo the input does not need to be one intended to handle password forms. It can be, e.g., a comment-adding backend. For those, there is no way to &quot;fix&quot; the backend itself, because it needs to be able to echo what it received.<br><br>A CSP might help to prevent posting password forms to backends not expecting to handle passwords, but in order to avoid breaking posting anything else on the domain, this needs to be complemented by something like:<br><br>* a separate subdomain only used for authentication (like <a href="http://accounts.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://accounts.google.com" data-b-redirected-href="http://accounts.google.com">accounts.google.com</a>); This is an open question and the team will try to seek an answer within the whole Chrome team.
