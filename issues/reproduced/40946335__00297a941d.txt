tj...@chromium.org： Looks like this is related to an out of process iframe that the Webstore has, which can be easily seen looking at the frame tree for the page using chrome://process-internals/#web-contents.  The redirect rule is replacing the content from that page, which doesn&#39;t hold the protections given to the Webstore itself. On the plus side that means that the content being modified doesn&#39;t have access to any of the APIs we provide to the Webstore itself and is in an entirely different process. Due to that I think we can lower the severity on this.<br><br>Still, I think the Webstore probably shouldn&#39;t have frames that commit to domains outside itself, as that content can be modified and if the content provides any user facing behavior, that behavior can therefore be modified. Copying on some webstore folk to double check that this frame isn&#39;t providing any behavior and to see if we can get rid of it.<br><br>Also copying on creis@ to see what they think about the data URL redirect triggering the alert on the top level page vs the web-hosted JavaScript redirect inside the OOPIF being blocked. Is this the behavior you would expect? Does the data URL get treated as the same origin as the iframe page, so get allowed through whatever CSP the Webstore is using with the embedded frame?
cr...@chromium.org： Are there any security consequences for the Chrome Web Store if extensions modify its out-of-process iframes (OOPIFs)?  I suspect it&#39;s not a problem, as long as the privileged <a href="http://chromewebstore.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://chromewebstore.google.com" data-b-redirected-href="http://chromewebstore.google.com">chromewebstore.google.com</a> origin doesn&#39;t take privileged actions in response to messages from its iframes.  In that sense, this shouldn&#39;t be any worse than extensions injecting scripts into these subframe origins in other non-privileged Google sites.<br><br>I also think it&#39;s required for the CWS to have cross-origin iframes that run out of process.  Among other things, there are YouTube videos shown on extension detail pages, and those run in OOPIFs.<br><br>The key question here is whether the extension can do anything to elevate its privileges by injecting into OOPIFs within the CWS (compared to injecting into other Google pages).
