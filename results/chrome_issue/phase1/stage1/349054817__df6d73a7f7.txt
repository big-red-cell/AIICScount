<h1>Steps to reproduce the problem</h1>
<ol>
<li>Generating a mutated digital certificate with an additional Subject Alternative Name (SAN) of &quot;ypj.test.com&quot;, along with its corresponding root CA and private key.</li>
<li>Configuring an Nginx web server to use the mutated certificate in HTTPS mode.</li>

<li>Adding the root CA to the system&#39;s trusted root certificate store using certutil.</li>
<li>Running nginx.exe. </ol>
<h1>Problem Description</h1>
<p>Actual Result: Chrome browser rejects X.509 certificates that include 05 00 NULL parameters in the AlgorithmIdentifier for the sha256ECDSA algorithm, resulting in the error message: &quot;You cannot visit ypj.test.com right now because the website sent scrambled credentials that Chrome cannot process. Network errors and attacks are usually temporary, so this page will probably work later.&quot;
Expected Result: Chrome should correctly process the certificate and allow access to the website, regardless of the presence of the 05 00 NULL parameter.
Additional Note: Firefox accepts certificates with the 05 00 NULL parameter, indicating a discrepancy in how different browsers handle this case.</p>

<p>Incompatibility with X.509 Certs Containing NULL Parameters in sha256ECDSA AlgorithmIdentifier</p>

<p>Nah, <a href="https://issues.chromium.org/issues/42290589" data-b-widget="issue-reference" data-b-issue-id="42290589">issue 42290589</a> is about a different instance.</p>
<p>As to the report, as with everything else found by this reporter&#39;s methodology so far, this is not a vulnerability. It is also incorrect. RFC 5758 is quite clear on the expectations here:</p>
<blockquote>
<p>When the ecdsa-with-SHA224, ecdsa-with-SHA256, ecdsa-with-SHA384, or
ecdsa-with-SHA512 algorithm identifier appears in the algorithm field
as an AlgorithmIdentifier, the encoding MUST omit the parameters
field.  That is, the AlgorithmIdentifier SHALL be a SEQUENCE of one
component, the OID ecdsa-with-SHA224, ecdsa-with-SHA256, ecdsa-with-
SHA384, or ecdsa-with-SHA512.</p>
</blockquote>
<p>Now, some X.509 verifiers accept this anyway, which is fine and not a security concern. But this is a place where we&#39;ve been able to ship stricter behavior, so changing it would be a step backwards.</p>
