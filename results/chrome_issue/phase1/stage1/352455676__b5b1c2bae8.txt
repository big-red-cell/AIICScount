Author: jd...@chromium.org
<p>Thanks for the report, but this is not a security vulnerability. For a few reasons.</p>
<p>Firstly, bypassing mixed content protections don&#39;t permit an attacker from being able to do anything that they couldn&#39;t already do -- the attacker can already get the user to load arbitrary content, and if the attacker needs the user to access an HTTP subresource, they can redirect to an attacker-controlled top-level page, and then the subresource request isn&#39;t mixed content.</p>
<p>Secondly, this isn&#39;t mixed content blocking at all. Your PoC creates a link, then clicks on it. This causes Chrome to try to navigate to the link&#39;s destination. Navigations are not subresource requests.</p>
<p>Since the file you&#39;re navigating to isn&#39;t something Chrome can display locally, Chrome is trying to download the file. That step is triggering Chrome&#39;s mixed download protections (<a href="https://blog.chromium.org/2020/02/protecting-users-from-insecure.html" data-b-widget="url" data-b-original-href="https://blog.chromium.org/2020/02/protecting-users-from-insecure.html" data-b-redirected-href="https://www.google.com/url?q=https://blog.chromium.org/2020/02/protecting-users-from-insecure.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0-LrTKCW9jWNSROi3e6NhM">https://blog.chromium.org/2020/02/protecting-users-from-insecure.html</a>), which is what&#39;s generating the console message. Mixed download blocking is also not a security boundary (for the same reason as mixed content). Because of how downloads work on the web, mixed download blocking can not prevent the HTTP request since Chrome usually doesn&#39;t know that the file is a download until it receives the response headers. At that point, it makes a blocking determination and drops the request. That&#39;s why even though you can see the request occur in DevTools, the file you try to download isn&#39;t accessible.</p>
<p>Hope that clarifies things!</p>
