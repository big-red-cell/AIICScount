<p>Turbofan incorrectly handling NaN on FindOrderedHashMapEntry</p>
<p>Hi V8 developer, I think I accidently found a bug when practicing about V8 and TurboFan on CTF. Since I&#39;m still new into v8, I&#39;m not sure about this, but worth it to make it check. So I found that FindOrderedHashMapEntry not handling a NaN value.</p>
<pre><code><span class="stx-class">Type</span> <span class="stx-qualifier">Typer</span>::<span class="stx-qualifier">Visitor</span>::<span>TypeFindOrderedHashMapEntry</span>(<span class="stx-class">Node</span>* node) {
  <span class="stx-keyword">return</span> <span class="stx-qualifier">Type</span>::Range(-<span class="stx-number">1.0</span>, <span class="stx-qualifier">FixedArray</span>::<span class="stx-const">kMaxLength</span>, zone());
}
</code></pre>
<p>So If we do this</p>
<pre><code><span class="stx-keyword">var</span> <span>o</span> = <span class="stx-keyword">new</span> Map();

<span class="stx-keyword">function</span> <span>f</span>() {

<p>IMPACT<br>
Mismatch between the Interpreter and Turbofan JIT (Just-in-Time) optimization.
In this example, the Turbolizer graph parses the result as a number instead of NaN. However, with specific manipulation, I can cause Turbofan to return results that differ from what the interpreter originally intended. This behavior can lead to unexpected program states.</p>

Author: dm...@chromium.org
<p>As far as I can see, removing <code>OptimizeFunctionOnNextCall</code> does not change the output, which means that it seems that Turbofan has the same behavior as the interpreter here.</p>
<p>Note that <code>FindOrderedHashMapEntry</code> returns -1 when the entry is not found (rather than NaN or undefined), which means that the typer&#39;s range is correct. And if you look at where <code>FindOrderedHashMapEntry</code>  is used in the TF graph, you&#39;ll see that when it&#39;s not -1 it&#39;s used to load the value, and when it&#39;s -1 it&#39;s not used, and there is a Phi following it which has <code>undefined</code> as input for the -1 case. And the Phi is followed by a <code>SpeculativeSafeIntegerAdd</code>, which is lowered in SimplifiedLowering to start with a <code>CheckedTaggedSignedToInt32</code>, which will deopt when it gets <code>undefined</code> as input. And, indeed, your example does deopt (use <code>--trace-deopt</code> flag to see it). So, everything seems to be working as intended in Turbofan.</p>
<p>Let me know if you think that I missed something and that there is indeed a bug there.</p>
