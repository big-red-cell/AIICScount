<p>VULNERABILITY DETAILS</p>
<p>Accessing Private APIs Using an Unpacked Extension with the Same Key as a Component Extension</p>
<p>Steps to Reproduce:</p>
<pre><code>1. Download the attached zip file, extract it, and load the unpacked extension.
2. Open the extension&#39;s popup menu and inspect it.
3. In the Console panel, type `chrome.webrtcLoggingPrivate` to see that the `webrtcLoggingPrivate` APIs are accessible through the loaded extension.
</code></pre>
<p><strong>Cause:</strong> The unpacked extension uses the same API key as the Hangout service extension, resulting in the existing extension being overridden. This override allows the loaded extension to access the private APIs intended for the Hangout service.</p>
<p><strong>Potential Issue:</strong> Private APIs are accessible to any unpacked extension that shares the same key as a component extension, effectively bypassing the restrictions on private API access. These APIs are meant to be restricted to their respective component extensions only.</p>
<p><strong>Note:</strong> This issue is not limited to the Hangout service; it affects other component extensions as well.</p>
<p><strong>Solution:</strong> An error should be raised before loading an extension if it uses a reserved extension ID. Failing to validate reserved IDs before loading poses a significant security risk.</p>

<blockquote>
<p>Component extensions are used for core parts of the Chromium browser. As such, a component extension should not be used for any feature that should be removable or that isn&#39;t fundamentally part of the browser.</p>
</blockquote>
<p>Component extensions are not supposed to be removable, yet we can override them with another extension. While this behavior might be acceptable for regular extensions, it isn’t for component extensions, which are a core part of the browser. For example, Brave relies on its built-in adblocker as a core feature, and allowing it to be overwritten is unacceptable. Even if you agree with overriding component extensions, it raises the question: why does the new extension load correctly the first time but revert to the original component extension when reloaded from the extensions page? It seems that we have a design flaw in how we handle the overriding of component extensions.</p>
