<h1>Problem Description</h1>
<h1>Overview</h1>
<p>When we use the direct constructor of <code>MessageEvent</code> and pass the source, it must conform to the <code>typedef (WindowProxy or MessagePort or ServiceWorker) MessageEventSource;</code>. This is defined by the standard at[HTML Standard - MessageEvent Interface] (<a href="https://html.spec.whatwg.org/multipage/comms.html#the-messageevent-interface" data-b-widget="url" data-b-original-href="https://html.spec.whatwg.org/multipage/comms.html#the-messageevent-interface" data-b-redirected-href="https://www.google.com/url?q=https://html.spec.whatwg.org/multipage/comms.html%23the-messageevent-interface&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3tdaH8WFfUuN9xCOJ6SbD2">https://html.spec.whatwg.org/multipage/comms.html#the-messageevent-interface</a>).</p>
<p>However, we have a way to create a <code>MessageEvent</code> using <code>initMessageEvent</code>, which accepts objects of a broader type, specifically <code>EventTarget</code>.
<code>&lt;a href=&quot;https://google.com/xxx&quot;&gt;&lt;/a&gt; &lt;script&gt; var exploit_message = new MessageEvent(&quot;message&quot;); exploit_message.initMessageEvent(&quot;message&quot;,false,false,{},&quot;https://example.origin&quot;,&quot;&quot;,document.getElementsByTagName(&#39;a&#39;)[0],[]) console.log(exploit_message) &lt;/script&gt;</code>
This happens because in <a href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=272;bpv=0;bpt=1" data-b-widget="url" data-b-original-href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=272;bpv=0;bpt=1" data-b-redirected-href="https://www.google.com/url?q=https://source.chromium.org/chromium/chromium/src/%2B/main:third_party/blink/renderer/core/events/message_event.cc;l%3D272;bpv%3D0;bpt%3D1&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2Q9zj9y6PNhC1oA7vSFL5E">initMessageEvent</a>, the call to <a href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=44;bpv=1;bpt=1" data-b-widget="url" data-b-original-href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=44;bpv=1;bpt=1" data-b-redirected-href="https://www.google.com/url?q=https://source.chromium.org/chromium/chromium/src/%2B/main:third_party/blink/renderer/core/events/message_event.cc;l%3D44;bpv%3D1;bpt%3D1&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0RIfmRJ4KunLcdkSEvhSRh">IsValidSource</a> is omitted.</p>
<p>If we talk about the impact, this creates numerous issues.
For example, I have exploited multiple extensions where the content script relies on <code>e.source.origin</code>.</p>
<p>Under normal circumstances, if this is a cross-origin window, it will throw an error. Thus, extensions reasonably assume that this represents the valid domain of the current window. However, this leads to unauthorized access to data from other origins within the extensions.</p>
<p>I also found a couple of examples where this helped me achieve XSS in the content script isolated world because the property contained data that the application did not expect.</p>
<h1>Fix</h1>
<p>As I mentioned earlier, it is sufficient to add a call to <a href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=44;bpv=0;bpt=1" data-b-widget="url" data-b-original-href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=44;bpv=0;bpt=1" data-b-redirected-href="https://www.google.com/url?q=https://source.chromium.org/chromium/chromium/src/%2B/main:third_party/blink/renderer/core/events/message_event.cc;l%3D44;bpv%3D0;bpt%3D1&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0Fk0OVQoPXgqJt_JYTuLoQ">IsValidSource</a> in <a href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=214;bpv=0;bpt=1" data-b-widget="url" data-b-original-href="https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/events/message_event.cc;l=214;bpv=0;bpt=1" data-b-redirected-href="https://www.google.com/url?q=https://source.chromium.org/chromium/chromium/src/%2B/main:third_party/blink/renderer/core/events/message_event.cc;l%3D214;bpv%3D0;bpt%3D1&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3WoUXHDQIwTG4PNYHESEQS">initMessageEvent</a>.
The correct logic should look like this:</p>
<pre><code> if(IsValidSource(source)){
   source_ = source
}else{
  source_ = nullptr;
}
</code></pre>

<p>Actually, upon further inspection, I don&#39;t think this is a security bug at all.</p>
<ol>
<li>
<p>The PoC logs out <code>MessageEvent.source.origin</code>. This is <strong>not</strong> <code>MessageEvent.origin</code>; in fact, this is logging out <code>HTMLAnchorElement.origin</code>. So any script checking this property is already checking the wrong property.</p>
</li>
<li>
<p><code>MessageEvent</code> already allows the origin property to be &quot;forged&quot; in a more direct way: both <code>initMessageEvent()</code> and the <code>MessageEvent</code> constructor allow an arbitrary origin to be passed in, e.g. <code>new MessageEvent(&#39;message&#39;, { &#39;origin&#39;: &#39;https://chromium.org/&#39; })</code> or <code>initMessageEvent(&#39;message&#39;, false, false, null, &#39;https://chromium.org/&#39;)</code>.</p>
</li>
<li>
<p>This isn&#39;t generally considered a security bypass, because the ability to call <code>dispatchEvent()</code> implies that you are already same-origin.</p>
</li>
</ol>
<p>Of course, there are buggy extensions, and that is unfortunate, but this isn&#39;t a fundamental security issue in Chrome itself.</p>
