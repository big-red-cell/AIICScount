<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>I believe the SOP check for <code>content://</code> URIs is not properly implemented when checking access to the contentDocument of an iframe with the <code>file://</code> origin.</p>
<p>It appears that when <code>setAllowUniversalAccessFromFileURLs(true)</code> is set, the <code>content://</code> URI origin is partially behaving like a <code>file://</code> origin and can access the contentDocument of a <code>file://</code> iframe. This can be abused by a malicious app to steal the content of app-internal files.</p>
<p><strong>Detailed Steps:</strong></p>
<ol>
<li>A file loaded into an Android WebView using a <a href="https://developer.android.com/reference/androidx/core/content/FileProvider" data-b-widget="url" data-b-original-href="https://developer.android.com/reference/androidx/core/content/FileProvider" data-b-redirected-href="https://www.google.com/url?q=https://developer.android.com/reference/androidx/core/content/FileProvider&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3jZPUt_ps48v_-sABiEI2N">FileProvider</a> uses the <code>content://</code> scheme. For example: <code>content://io.hextree.webview/internal/secret.html</code></li>
<li>In general documents with the <code>content://</code> origin can only access other <code>content://</code> origins. They can not access <code>https://</code> or <code>file://</code>.</li>
<li>Android WebViews can set <code>setAllowUniversalAccessFromFileURLs(true)</code>, which essentially disables web security for the <code>file://</code> origin. In that case, documents with the <code>file://</code> origin can access any other origin via XHR or iframe (see attachment <code>webview_universal_file_access.png</code>)
<span data-b-widget="image" data-b-img-src="https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/webview_universal_file_access.png" data-b-img-redirected-src="https://www.google.com/url?q=https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/webview_universal_file_access.png&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2Fo4oJ4TCU1-Bl0jUOendP" data-b-img-alt="content_provider.png">[image:https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/webview_universal_file_access.png]</span></li>
<li>However when <code>setAllowUniversalAccessFromFileURLs(true)</code> is enabled, <code>content://</code> origins start to behave weird. They are allowed to access the contentDocument of a <code>file://</code> loaded in an iframe, even though XHR is still blocked (see attachment <code>content_provider.png</code>)
<span data-b-widget="image" data-b-img-src="https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/content_provider.png" data-b-img-redirected-src="https://www.google.com/url?q=https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/content_provider.png&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0-gBpgR4HHo4wvHjGA4zgC" data-b-img-alt="content_provider.png">[image:https://raw.githubusercontent.com/hextreeio/android-webview-research/refs/heads/main/content_provider.png]</span></li>
</ol>

<h4>Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p><strong>Threat Model:</strong></p>
<p>A <a href="https://blog.oversecured.com/Android-security-checklist-webview/#typical-example-of-the-vulnerability" data-b-widget="url" data-b-original-href="https://blog.oversecured.com/Android-security-checklist-webview/#typical-example-of-the-vulnerability" data-b-redirected-href="https://www.google.com/url?q=https://blog.oversecured.com/Android-security-checklist-webview/%23typical-example-of-the-vulnerability&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3DBZ7BMPbzcdWCL-svcmf5">common issue</a> for Android WebViews is that an attacker can control the URI loaded into a WebView via an Intent. If <code>setAllowUniversalAccessFromFileURLs(true)</code> is enabled and an attacker could load a malicious document via a file URI, then the attacker has full access to content of any other origin. This can be used to leak any app-internal files.</p>
<p><strong>Scoped Storage file:// Restrictions:</strong></p>
<p>Unfortunately, due to scoped storage introduced in Android 11, it&#39;s almost impossible to create a world-readable file that can be loaded into the WebView by another app. I am only aware of one trick using <a href="https://github.com/hextreeio/android-webview-research/tree/main?tab=readme-ov-file#32-extract-nativelibs-trick" data-b-widget="url" data-b-original-href="https://github.com/hextreeio/android-webview-research/tree/main?tab=readme-ov-file#32-extract-nativelibs-trick" data-b-redirected-href="https://www.google.com/url?q=https://github.com/hextreeio/android-webview-research/tree/main?tab%3Dreadme-ov-file%2332-extract-nativelibs-trick&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw27W_AvFhT2Bk5_fPHZ1-DP"><code>extractNativeLibs=&quot;true&quot;</code></a>, which probably doesn&#39;t work for Play Store distributed apps. For any other origin loaded in a WebView , the Same Origin Policy generally prevents further exploitation. Thus any SOP issue on other origins weakens these mitigations.</p>
<p><strong>Impact:</strong></p>
<p>It turns out that <code>setAllowUniversalAccessFromFileURLs(true)</code> leads to some kind of invalid origin check with <code>content://</code> URIs, allowing for a partial SOP bypass. This means when <code>setAllowUniversalAccessFromFileURLs(true)</code> is enabled, documents loaded via a <code>content://</code> URI can leak app-internal files. For example the shared preference files which often contains authentication tokens.</p>

(see also Google&#39;s Mobile VRP threat models: &quot;User must install malicious app or victim app is configured in a non-default way&quot; <a href="https://bughunters.google.com/about/rules/android-friends/6618732618186752/google-mobile-vulnerability-reward-program-rules#application-tier-1-rewards" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://bughunters.google.com/about/rules/android-friends/6618732618186752/google-mobile-vulnerability-reward-program-rules#application-tier-1-rewards" data-b-redirected-href="https://bughunters.google.com/about/rules/android-friends/6618732618186752/google-mobile-vulnerability-reward-program-rules#application-tier-1-rewards">https://bughunters.google.com/about/rules/android-friends/6618732618186752/google-mobile-vulnerability-reward-program-rules#application-tier-1-rewards</a>)<br><br>Question is, what is the security impact when a malicious app can make a target app load an arbitrary URL in the WebView? Well, content:// URIs are weirdly treated as file:// URIs which has significant impact on the exploitability of this threat model. <br><br>App-to-app WebView Attack:<br>1. Let&#39;s say, there is a victim app that stores authentication tokens in the [shared preferences](<a href="https://developer.android.com/training/data-storage/shared-preferences" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://developer.android.com/training/data-storage/shared-preferences" data-b-redirected-href="https://developer.android.com/training/data-storage/shared-preferences">https://developer.android.com/training/data-storage/shared-preferences</a>) (app internal .xml file) and uses a WebView that allows JavaScript with disabled file SOP `setAllowUniversalAccessFromFileURLs(true)`.  <br>2. As expected, if the malicious app could make this target app load a malicious file:// URI, the malicious app&#39;s loaded site could steal the authentication token in the shared preference files. And this used to be a typical exploitation technique when encountering such a WebView.<br>3. Though, this is not possible anymore. The malicious app cannot create a file readable by the target app due to [scoped storage](<a href="https://source.android.com/docs/core/storage/scoped" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://source.android.com/docs/core/storage/scoped" data-b-redirected-href="https://source.android.com/docs/core/storage/scoped">https://source.android.com/docs/core/storage/scoped</a>). This is probably weird to hear coming from Desktop, but the Android app sandbox simply prevents the malicious app from creating a `file:///tmp/exploit.html` and forcing the target app to load it. It&#39;s just not possible, the victim app cannot see/read this file. This means, even a WebView with disabled file SOP (`setAllowUniversalAccessFromFileURLs(true)`) is not actually exploitable by a malicious app in this way.<br>4. BUT because content:// URIs are partly treated as file:// URIs in this weird edge case of `&lt;iframe&gt;`, this is exploitable again. The malicious app simply uses a [ContentProvider](<a href="https://developer.android.com/guide/topics/providers/content-provider-basics" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://developer.android.com/guide/topics/providers/content-provider-basics" data-b-redirected-href="https://developer.android.com/guide/topics/providers/content-provider-basics">https://developer.android.com/guide/topics/providers/content-provider-basics</a>) to share the malicious page with the target app. The target app is allowed to load the malicious content:// page, which due to the weird SOP rule is now allowed to steal the app internal shared preferences file.<br><br>That&#39;s why changing this behaviour and treating it like its own origin could be a strong mitigation.
