<h4>Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>This report highlights security vulnerability in chrome ios browser where an iframe-embedded website (attacker.com) can gain microphone access under the name of the top-level site (legit-website.com).</p>
<p>Despite implementing Permissions-Policy headers to explicitly block microphone access, chrome continues to grant microphone permissions to the iframe (attacker.com), allowing unauthorized eavesdropping and potential privacy violations.</p>
<h1>Impact</h1>
<h1>User Trust Violation (UI Misrepresentation)</h1>
<ol>
<li>chrome displays a misleading permission prompt stating that legit-website.com is requesting microphone access.</li>
<li>However, the actual recipient of the microphone input is attacker.com, violating user trust.</li>
</ol>
<h1>Eavesdropping &amp; Audio Exploitation</h1>
<ol>
<li>
<p>Once the user clicks &quot;Allow&quot;, attacker.com can:</p>
</li>
<li>
<p>Silently record conversations without user awareness.</p>
</li>
</ol>
<h1>Bypassing Same-Origin Policy (SOP)</h1>
<ol>
<li>Browsers enforce Same-Origin Policy (SOP) to prevent unauthorized cross-origin interactions.
In this case, legit-website.com embeds attacker.com within an iframe and adds allow=&quot;microphone&quot;, enabling the iframe to access microphone input.
chrome incorrectly grants the permission to the top-level origin (legit-website.com), but the iframe (attacker.com) is the actual recipient.</li>
</ol>

The security vulnerability in Chrome for iOS arises from a critical UI misrepresentation in permission prompts when a cross-origin iframe requests access to sensitive hardware, such as the microphone or camera. When a trusted top-level site (<a href="https://www.google.com/url?q=http://legit-website.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3iTc-IXAbkWuASxWDih7vM" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://legit-website.com" data-b-redirected-href="https://www.google.com/url?q=http://legit-website.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3iTc-IXAbkWuASxWDih7vM">legit-website.com</a>) embeds a third-party iframe (<a href="https://www.google.com/url?q=http://attacker.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1UbMTiG3FKyAMElQfPBxFn" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://attacker.com" data-b-redirected-href="https://www.google.com/url?q=http://attacker.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1UbMTiG3FKyAMElQfPBxFn">attacker.com</a>), Chrome iOS erroneously attributes the permission request to the top-level origin in the dialog (e.g., &quot;Allow <a href="https://www.google.com/url?q=http://legit-website.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3iTc-IXAbkWuASxWDih7vM" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://legit-website.com" data-b-redirected-href="https://www.google.com/url?q=http://legit-website.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3iTc-IXAbkWuASxWDih7vM">legit-website.com</a> to access your microphone?&quot;). However, the actual recipient of the permission is the embedded iframe (<a href="https://www.google.com/url?q=http://attacker.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1UbMTiG3FKyAMElQfPBxFn" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://attacker.com" data-b-redirected-href="https://www.google.com/url?q=http://attacker.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1UbMTiG3FKyAMElQfPBxFn">attacker.com</a>), which gains unauthorized access to the device. This UI spoofing directly violates user trust, as the prompt misleads users into believing they are granting access to a legitimate site, while the permissions are covertly routed to a hidden, potentially malicious origin.<br><br>The flaw is exacerbated by Chrome iOS’s reliance on WebKit (due to Apple’s engine restrictions), which does not fully enforce Chromium’s Permissions-Policy standards. While Chrome desktop would block an iframe’s allow=&quot;microphone&quot; attribute if the parent site sets Permissions-Policy: microphone=(), Chrome iOS fails to honor this hierarchy. Even in cases where no explicit policy is set, the permission prompt’s incorrect origin attribution allows attackers to exploit the ambiguity. For example, an attacker could embed a malicious iframe within a popular social media or banking site, tricking users into enabling microphone access under the guise of a trusted service. This bypasses the intent of the Same-Origin Policy (SOP), enabling cross-origin permission escalation through deceptive UI practices that Chrome’s security model is designed to prevent.<br><br>The impact of this vulnerability is severe:<br><br>Privacy Breach: Attackers can silently record audio or video, capturing sensitive conversations or environments without user knowledge.<br><br>User Trust Exploitation: By hijacking the credibility of trusted domains, attackers manipulate users into granting permissions they would otherwise deny.
