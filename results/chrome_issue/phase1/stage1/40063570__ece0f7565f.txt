<a href="https://www.google.com/url?q=https://crbug.com/chromium/1083278&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0MWkuPIJQPgkloj22VWeW6" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://crbug.com/chromium/1083278" data-b-redirected-href="https://www.google.com/url?q=https://crbug.com/chromium/1083278&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0MWkuPIJQPgkloj22VWeW6">https://crbug.com/chromium/1083278</a> is related but different.  That bug involves DNS spoofing, i.e. attacker-generated responses that get accepted as valid results and poison the cache.<br><br>This report concerns attacker-generated responses that are correctly recognized as invalid, but that invalid response gets treated as an error, thus preventing receiving the true result.  Unlike DNS spoofing, I don&#39;t think we&#39;ve ever considered this sort of thing to violate our threat model, so it&#39;s unclear to me if this is something we want to bother mitigating or not.  In the very least, I agree with calling this p3.<br><br>As a thought experiment, I suppose our typical goal is to try to make DNS over UDP as safe as DNS over TCP.  I believe the TCP equivalent to this would be a TCP reset attack, but I believe a forged TCP RST will get ignored if its sequence number is wrong, thus preventing an attacker being able to do it without snooping the legitimate messages.  (Somebody more familiar with TCP than me, feel free to correct me if I&#39;m wrong on any of this.)  So from that perspective, updating our logic to silently ignore invalid/malformed responses seems to be a reasonable measure, quasi emulating the TCP protections.<br><br>Change would be to alter DnsUDPAttempt::DoReadResponseComplete() to do another read (`next_state_ = STATE_READ_RESPONSE; return OK;`) in place of where it currently returns `ERR_DNS_MALFORMED_RESPONSE`.  I can&#39;t think of any adverse effects of doing that other than that relevant legitimate failures would take a little bit longer (waiting for timeout) before we move on to attempting retry or trying alternate DNS server.  But if we assume DNS servers aren&#39;t regularly serving out garbage responses, that doesn&#39;t seem too bad.
