<p>Apologies for the delay here, this fell through the cracks.</p>
<p>The child navigable&#39;s document&#39;s inherited policy is initialized with a snapshot of the container policy taken at the time of the navigation commit in the <span>&lt;iframe&gt;</span> (in other words, at the time of the creation of the document in the child navigable), and remains unchanged for the lifetime of that document. If you change the container policy (aka. the <code>allow</code> or <code>allowfullscreen</code> attributes` on the <span>&lt;iframe&gt;</span> element), those changes will take effect only for the next navigation committed in that child navigable.</p>
<p>This is both for consistency with other security policies that are conceptually stored (or planned to be stored) in the document&#39;s <a href="https://html.spec.whatwg.org/multipage/dom.html#concept-document-policy-container" data-b-widget="url" data-b-original-href="https://html.spec.whatwg.org/multipage/dom.html#concept-document-policy-container" data-b-redirected-href="https://www.google.com/url?q=https://html.spec.whatwg.org/multipage/dom.html%23concept-document-policy-container&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2MeghjPaqaoaNN6MrW4nH8">policy container</a> and follow the <a href="https://html.spec.whatwg.org/multipage/browsing-the-web.html#beginning-navigation:determining-navigation-params-policy-container" data-b-widget="url" data-b-original-href="https://html.spec.whatwg.org/multipage/browsing-the-web.html#beginning-navigation:determining-navigation-params-policy-container" data-b-redirected-href="https://www.google.com/url?q=https://html.spec.whatwg.org/multipage/browsing-the-web.html%23beginning-navigation:determining-navigation-params-policy-container&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2ytBLthVifzr6H_KkAVRMu">beginning-navigation:determining-navigation-params-policy-container</a> algorithm; as well as for practical purposes, i.e. neither the web-facing Permission Policy API, nor user agents&#39; implementations, support handling the permission policy state changing during the lifetime of an existing document.</p>
<p>Therefore I am inclined to say that this is working as intended/spec&#39;ed. Unlike other policies in the policy container, Permission Policy does not affect renderer process assignment nor process-level policies, so theoretically it is possible for us to change the spec. If you want, you can file an issue against the spec at <a href="https://github.com/w3c/webappsec-permissions-policy/issues/" data-b-widget="url" data-b-original-href="https://github.com/w3c/webappsec-permissions-policy/issues/" data-b-redirected-href="https://www.google.com/url?q=https://github.com/w3c/webappsec-permissions-policy/issues/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0pJ1A3PF-N7_h8YxU3GiL7">https://github.com/w3c/webappsec-permissions-policy/issues/</a>. However, given the substantial implementation complexity, and the limited security benefits, I am not optimistic that this stronger security boundary is something we are going to be willing to defend.</p>
<p>We could certainly emphasize in developer-facing documentation that developers need to set the proper container policy, and then navigate the <span>&lt;iframe&gt;</span>, or even better, encourage always setting policies with explicitly specified list of origins (instead of special values like <code>src</code>) and those obviate needing to worry about this problem.</p>
