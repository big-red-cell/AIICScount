<p><strong>VULNERABILITY DETAILS</strong><br>
When using the Credential Management API, it is possible to extract the users&#39; username and password of a website that is vulnerable to XSS attacks (or through Chrome extensions). In order to be able to execute the attack, the user needs to give permission to the website to use the credentials that are stored in the browser (normal behaviour when using the Credential Management API). If the user has previously given its consent (eg. when the website itself has implemented the Credential Management API) this condition is already met and the attack can be executed without any further user interaction.</p>
<p>The Credential Management API allows the credentials to be sent to any URL within the same origin. It also allows you to specify the fieldname of both the username as the password. By sending the request to a URL that will output the values of these fields in its response, the calling page is able to extract that information from the request.</p>
<p>Any page with a form that does some sort of validation will probably do, as long as it returns the sent in data back to the browser. Typical examples could be incompletely filled in registration or contact forms. If the data is not accepted, most sites fill pre-fill the form with the submitted data to prevent the user from having to fill it in all over again because they made a mistake.</p>
<p>I&#39;ve also did a test with Tampermonkey and was able to extract the information using the same method. This means that any Chrome extension is potentialy able to extract the credentials when a user visits a site that is targeted by the extension.</p>
<p>Although the API doesn&#39;t expose the information itself, the fact that you can specify the endpoint and the fieldnames of both username and password makes it very easy to exploit the vulnerability if one is able to inject the javascript into the page.</p>
<p>To solve this, I think there need to be put some restrictions on the endpoint to which retrieved credentials can be sent to (eg. limit to the original URL where they were captured) and/or the names of the fields used to submit the data.  Alternatively, restricting access to the response object of a call including credentials could also be done. Then again, I assume you have people better qualified to come up with a suitable solution.</p>

Chrome Version: 55.0.2883.87 m (stable?)<br>
Operating System: Windows 10 Home</p>
<p><strong>REPRODUCTION CASE</strong><br>
I&#39;ve attached a zip file containing a mini-site.</p>
<ul>
<li>index.php contains the javascript.</li>
<li>login.php is simply there to accept the regular login form (doesn&#39;t do anything, but the browser should ask to store the password)</li>
<li>contact.php is the target script that will output the submitted data back in the form, that is then extracted by the script in index.php.</li>
</ul>
<p>The script will show an alert with the extracted username and password. This could of course easely be sent off to a remote server instead.</p>

That is indeed quite similar. The main difference is that the script does not have direct access to the password and needs some sort of &quot;echo&quot; functionality (the data sink) to get a hold of it, where information like CSRF tokens is already accessible to the script. Once it does obtain the password, it can use any other available vector to get the data to the attacker.<br><br>Since the browser knows he&#39;s submitting a password when it&#39;s still in the credential object, the only possible time/place to prevent this kind of attack is the place the data is submitted. <br><br>CSP would probably be an option to restrict it, but even then it&#39;s still possible that one of the allowed resources has some form of functionality by design that allows the data to be passed back.  <br><br>In typical conditions, the only place a password can be obtained is to capture it when the user enters it on the login form. The Credential Manager API potentially allows an attacker to request this data on every pageview. If your site is vulnerable to XSS, you probably have other problems as well, but by giving the developer the option (or requirement) to specify what endpoints can be used to submit a credentials object to, you can prevent this from being exfiltrated as a direct result of using the Credentials Management API.<br>

You are correct that in the event that the login page itself is vulnerable to such an attack, you would have a 100% succes rate, so unsing a suitable endpoint is key to this working. <br><br>However, don&#39;t forget that sites that have NOT implemented the API are equaly vulnerable to the attack. Since these developers might not even be aware of the existance of the API, you can&#39;t expect them to have locked it down. I just did a check agains the homepages of the top 100 sites according to Wikipedia. Of these sites, only 6 have CSP headers at all and only 4 limit connections through default-src or connect-src. Why is this? My guess is that no-one has forced them to do so. This is why it should be blocked unless deliberately whitelisted by the developer. If the developer chooses to use an existing (designed for humans) page to verify the login against, it is the responsability of the developer to make sure it only returns what&#39;s needed (a computer/automated script doesn&#39;t need autocomplete, nor should it have to rely on parsing html to extract any relevant data). Anyway, at that point it&#39;s a loophole the developer created itself, not one that is simply there because of the API.<br><br>If instead the developer creates a new endpoint that will validate the data and return a structured (like json) response to indicate failure or success, he can effectively ensure that the password is not returned in the response. If it fails (eg. swapped username and password), just return a simple error<br><br>{ &#39;result&#39;: &#39;fail&#39; }<br><br>If it succeeds, he can return additional data (which sensibily doesn&#39;t include the password). <br><br>{ &#39;result&#39;: &#39;ok&#39;, &#39;fullName&#39;: &#39;John Doe&#39; }<br><br>If we can then furher limit the endpoints a Credential object can be submitted to through Fetch, you can effectively prevent the password from being extracted. It&#39;s probably a few lines extra for those who choose to implement the API, but it closes the backdoors for all the other sites that have not implemented it. <br><br>So basically, this should not leave any scenario open where the information is disclosed unintentially:<br>- The site requests credential<br>- The browser returns PasswordCredential<br>- Fetch checks the existance of a to-be-defined header on the endpoint before submitting the actual data<br>- If the header is missing, or does not have the correct value, the request is denied<br>- If the header is present and has the correct value, the request is processed and passed back to the script/browser.<br><br>Assuming the endpoint is not designed for humans, or at least with this in mind:<br>- It will not disclose the username and password in case of a login failure (eg. when an attacker swapped username and password)<br>- It will not disclose the password in case of a succesful login <br><br>

Thanks for the report, the discussion so far, and for looping me in.<br><br>My opinion is below. I will be happy to discuss this further with the password manager team tomorrow, and the security team on demand.<br><br>Summary of my opinion:<br><br>* No changes in the CM API needed because of this attack. The security value of the CM API is not diminished.<br>* This attack should be prevented primarily on the server side, e.g., in the way <a href="http://accounts.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://accounts.google.com" data-b-redirected-href="http://accounts.google.com">accounts.google.com</a> do it.<br>* Chrome-side prevention, while theoretically possible, does not seem worth implementing. There would need to be some evidence of this attack having a large enough impact.<br><br>Details:<br><br>This weakness is not specific to Credential Manager (CM) API. An injected script on, say, facebook&#39;s login page can also swap the &#39;name&#39; attribute of the username and password fields before submission, resulting in the password being sent back in plain text as part of the response HTML.<br><br>While it would be beneficial if Chrome could help to protect the user against this attack, this protection is unlikely to be specific to CM API.<br><br>One of the key motivations for CM API is indeed increasing the protection against XSS based attacks aimed at passwords. This does not mean that CM API itself is able to address all such threats. Its design makes it possible to prevent the password ever being shared with the renderer process, a property of its own value, independent of this scenario. There are at least two more known XSS-related threats which cannot be prevented by CM API itself: this issue, and the fact that data stored in CM API can be filled into HTML forms for compatibility reasons. The latter will be addressed by <a href="https://www.google.com/url?q=https://mikewest.github.io/credentialmanagement/writeonly/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1SIYieZUyW3TFNBkJnlUOu" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="https://mikewest.github.io/credentialmanagement/writeonly/" data-b-redirected-href="https://www.google.com/url?q=https://mikewest.github.io/credentialmanagement/writeonly/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1SIYieZUyW3TFNBkJnlUOu">https://mikewest.github.io/credentialmanagement/writeonly/</a>. This issue here will also need a separate remedy, independent of CM API.<br><br>The best remedy one is found on the server side. Looking at <a href="http://accounts.google.com" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://accounts.google.com" data-b-redirected-href="http://accounts.google.com">accounts.google.com</a>, for example, it seems like the two-step login process protects against the threat, without inconveniencing the users in the case of no XSS attack present: first the user needs to enter their username and submit. Then they enter the password on the second submission. If the password does not match, but the username information on the second submission matches that of the first one, the user only needs to enter the password, not the username again. If the username does not match (e.g., as a result of the attack described here), the flow is reset and the username field is shown empty.<br><br>On the Chrome side we could also use the fact that the browser knows all the stored passwords. It could scan the HTML responses for their occurrences and filter them out, in theory. This would have a number of false positives, though. These could be reduced by restricting this protection to, e.g., only generated passwords (which are unlikely to match any real words occurring accidentally in HTML pages). But there would also be performance concerns and an increased complexity in Chrome&#39;s behaviour in general. If we see that the attack&#39;s impact is severe enough to warrant accepting these drawbacks, we can decide to implement some protection like that. I am not currently convinced that this is the case.<br>

Author: vasilii@ and battre@ explained to me a part of the issue which I missed before: the server URL to echo the input does not need to be one intended to handle password forms. It can be, e.g., a comment-adding backend. For those, there is no way to "fix" the backend itself, because it needs to be able to echo what it received.

A CSP might help to prevent posting password forms to backends not expecting to handle passwords, but in order to avoid breaking posting anything else on the domain, this needs to be complemented by something like:

* a separate subdomain only used for authentication (like accounts.google.com); then everything posted within that origin is assumed to be a password; for this to work, PSL matching needs to be disabled for that eTLD+1 (see https://cs.chromium.org/chromium/src/components/password_manager/core/browser/psl_matching_helper.h?l=43-51 for how to do it)
* or some creative use of subresources together with adding a flag to fetch (needing a change to the spec https://fetch.spec.whatwg.org/)
* or letting the origin to specify which endpoints are eligible to receive submissions from CM API and password forms (there seems to be no standard for this yet)

The question we hit on the team meeting is: is Chrome planning to achieve at some day, that passwords will never be shared with the renderer? If yes, then protecting against various XSS attacks is something Chrome needs to offer to the interested developer: in the form of CM API not sharing the password with the site, implementing the form-writeonly protection, and some doable protection about this issue here as well (the above listed alternatives seem to present an unreasonable burden in their current form).

So offering some kind of doable protection against this issue is not blocking CM API directly, but either we should aim to ultimately offer it, or we should reconsider what we are achieving with CM API. This is an open question and the team will try to seek an answer within the whole Chrome team.
