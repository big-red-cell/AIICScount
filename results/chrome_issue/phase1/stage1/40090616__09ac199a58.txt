<p>My understanding is that the platform very deliberately keeps an empty script modifyable (Poc #1 + #3) , and that this is a &quot;sharp edge&quot; in the platform that developers need to avoid. Author: aa...@google.com
googlers_unrestricted

Author: **VULNERABILITY DETAILS**   
[Context: This issue was found by Masato Kinugawa of Cure53 and used in a recent XSS challenge: https://henhouse.cure53.berlin/. On our side the first working exploit was discovered by koto@.]  
  
There is a logic flaw (arguably at the spec level) which leads to the clearing of the parser_inserted flag on scripts which were indeed added via a parser, making it possible to bypass policies with 'strict-dynamic' in some cases.  
  
The problem in Chrome is in blink/Source/core/script/ScriptLoader.cpp (l. 272-288), which is a direct implementation of the algorithm defined in the spec: https://html.spec.whatwg.org/multipage/scripting.html#script-processing-model:  
  
[parser_inserted is set to false here]  
  // 4. "If the element has no src attribute, and its child nodes, if any,  
  //     consist only of comment nodes and empty Text nodes,  
  //     then abort these steps at this point. The script is not executed."  
  // FIXME: HTML5 spec says we should check that all children are either  
  // comments or empty text nodes.  
  if (!element_->HasSourceAttribute() && !element_->HasChildren())  
    return false;  
  
  // 5. "If the element is not connected, then abort these steps.  
  //     The script is not executed."  
  if (!element_->IsConnected())  
    return false;  
  
  // 6. "Determine the script's type as follows:"  
  // |script_type_| is set here.  
  if (!IsScriptTypeSupported(support_legacy_types, script_type_))  
    return false;  
[parser_inserted flag is set to true again here]  
  
Since the code first removes the parser_inserted flag, if any of the three conditions above is true, PrepareScript() will return without setting it back to the previous value -- this means the script element will now be in a state that will bless it for 'strict-dynamic'. When the script element later gets mutated (in a way that would otherwise be safe), CSP will allow it to execute.   
  
**REPRODUCTION CASE**   
  
The three PoCs corresponding to each of the above conditions are as follows:  
  
#1. Empty <script>  
  
<!-- XSS here--><script id='foo'></script><a id="myVariable" href="data:alert(1)//" />  
  
<!-- Regular code -->  
<script nonce="foo">document.getElementById('foo').textContent = myVariable;</script>

One possible idea for fixing this on the CSP side:<br>1. Turn the local was_parser_inserted bool in ScriptLoader::PrepareScript into a property of the script element.<br>2. When making a decision for CSP, check both parser_inserted and was_parser_inserted and block if either was true. Author: Hmm, from what I gather looking at the specs for the first time, the parser-inserted flag is removed because in order to execute the script another script needs to alter and modify it, which is viewed similar to the second script loading one its external dependencies. 

I notice that in all PoC a nonce-blessed script will have to intentionally modify the inserted script. I suppose the danger is that the attacked could identify a script that is empty/not connected/has invalid type that is supposed to be altered by another script to become executable. But even then it seems that a significant amount of co-operation needs to happen from the side of the regular script. Is this a situation that actually happens?

I suppose this is somewhat similar to scripts that create new scripts in the document by using createElement for instance and I believe those scripts are indeed marked as parser inserted.

So... long story short I agree we should look at aaj@'s was_parser_inserted solution as that seems reasonable enough and then we can either check both flags on the CSP side or insert a spec change in the HTML Parser to set both flags. (I would argue the latter is cleaner but what do I know.)

Also I will lower the priority since I believe this requires a very specific set of circumstances to be exploitable. Feel free to disagree and raise the priority back if you think it's easier to exploit than I make it out to be.

Author: Had a longer discussion with aaj@ (reporter) on how to fix this. I'll summarize below. tl;dr: we don't know. 

- ScriptLoader follows the spec quite precisely.

- What we thought was an oversight in the spec -- that <script> elements inserted by the parser end up with parser_inserted_ being false -- turns out to be on purpose, and is guarded by quite a few WPT & other tests: If a <script> element fails certain conditions - e.g. if it's empty - then the script loader will purposely treat it like a dynamically created script. Spec, implementation, and tests are all consistent on this.

- One way to summarize this is that the flag name parser_inserted_ is a lie. Actual semantics don't match the name, and it's really parser_inserted_and_ready_to_execute_or_something_or_other_.

- CSP spec references the parser_inserted_ flag when specifying script-src 'strict-dynamic'. This is arguably wrong, because this assigns behaviour to 'script-dynamic' that it doesn't want to have.

- In particular, the case of a <script> element in the page source that then gets updated via some injected property assignment, ought to not be allowed by 'script-dynamic'. But by importing the parser_inserted_ semantics, this may well be the case.

- The high road to fixing this is thus: Re-define with more precision what 'script-dynamic' is supposed to do, likely without reference to parser_inserted_; update the CSP spec; update the implementation.

- There's no immediately obvious definition of the 'strict-dynamic' conditions. This will require some thought. There might also be backwards-compatibility issues if the definition is changed.

- One way out might be to declare this as working-as-intended, and ask people to rely on Trusted Types to prevent the undesirable property assignments.

<p>Good afternoon, everyone. It&#39;s been a while.</p>
<ul>
<li>At present (2024-12), the browser behaviour is unchanged. The POCs still work.</li>
<li>Meanwhile, the <code>parser_inserted</code> logic in the spec has been redefined, <a href="https://html.spec.whatwg.org/#parser-inserted" data-b-widget="url" data-b-original-href="https://html.spec.whatwg.org/#parser-inserted" data-b-redirected-href="https://www.google.com/url?q=https://html.spec.whatwg.org/%23parser-inserted&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw194RgyBm0KU3WJH6xSkraR">https://html.spec.whatwg.org/#parser-inserted</a>, and is now expressed in terms of a parser-associated document.</li>
<li>My understanding is that, for the purpose of this bug, the re-write has intentionally kept the existing behaviour.</li>
<li>I still think we are faithfully implementing the specs.</li>
</ul>
<p>My understanding is that the platform very deliberately keeps an empty script modifyable (Poc #1 + #3) , and that this is a &quot;sharp edge&quot; in the platform that developers need to avoid. Trusted Types can be used to protected against this, but <code>strict-dynamic</code> unfortunately not, even though it would seem to.</p>
<p>To the best of my knowledge, we haven&#39;t seen these approaches used for actual attacks in the ~6 years that this bug has been open. I guess this is chiefly because they require some fairly specific pre-requisites in the page to make use of, such as an empty, unused <code>&lt;script&gt;</code> lying around, or a <code>&lt;script&gt;</code> being imported through importNode.</p>
<p>I&#39;ll close this issue as WAI.</p>
<hr>
<p>The spec aspect is being (re-)discussed in a slightly different context: <a href="https://github.com/w3c/trusted-types/pull/533" data-b-widget="url" data-b-original-href="https://github.com/w3c/trusted-types/pull/533" data-b-redirected-href="https://www.google.com/url?q=https://github.com/w3c/trusted-types/pull/533&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw36bPb5xBvCBnKgZUwR77S8">https://github.com/w3c/trusted-types/pull/533</a>. Trusted Types also wants a flag which means inserted-by-parser-and-the-content-is-actually-what-the-pasrer-put-in-there. If that work provides the proper spec hooks, then I&#39;ll approach CSP to make use of it.</p>
