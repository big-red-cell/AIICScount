<h1>Problem Description</h1>
<p>When analyzing <a href="https://issues.chromium.org/issues/367755363" data-b-widget="issue-reference" data-b-issue-id="367755363">https://issues.chromium.org/issues/367755363</a>, I recently discovered that although RenderFrameHost has introduced ADVANCED_MEMORY_SAFETY_CHECKS(), my testing shows it fails to effectively prevent exploitation of UAF vulnerabilities.
At [0], the code checks whether slots_ has sufficient capacity to accommodate newly quarantined objects. If space is available, the object gets added to slots_.back(). Subsequently, it randomly swaps slots_.back() with a slot at any selected random_index [3].</p>

<p>When entering the while loop at [3], it indicates that the quarantine can no longer accommodate newly added objects. At this point, the object corresponding to slots_.back() is released back into the global slot via FreeNoHooksImmediate.</p>

<p>RenderFrameHost exhibits two key characteristics:</p>
<ol>
<li>Attackers can easily create and release arbitrary numbers of iframes, which is functionally equivalent to releasing RenderFrameHost.</li>
<li>RenderFrameHostImpl is a large object, meaning the slots_ cannot retain many instances.
I think this check can be easily bypassed in the UAF scene of RenderFrameHost.</li>
</ol>
<p>In the test version of <a href="https://issues.chromium.org/issues/367755363" data-b-widget="issue-reference" data-b-issue-id="367755363">issue 367755363</a> (commit 129d018cd38423003cd025fe9ef01c75a897203b):</p>
<ul>
<li>capacity_in_bytes is 262,144; usable_size is 5,628 ; The slots_ can hold up to 46 objects</li>
<li>To successfully reallocate a UAF-compromised RenderFrameHostImpl, it must be ensured that once during n iterations, the target is swapped to the slots_.back() position.</li>
<li>Calculated via 1 - (45/46)^n ≥ 0.999, when n = 315 (i.e., remove 315 + 46 iframes), there is a 99.9% probability of achieving heap spray success.
In the latest stable version (commit fd886e2cb29dd984c13deec032832dee68d8abe3):</li>
<li>capacity_in_bytes is 262,144</li>
<li>usable_size is 6,140</li>
<li>Calculated via 1 - (169/170)^n ≥ 0.90, when n = 396 (i.e., remove 396 + 170 iframes), there is a 90% probability of achieving heap spray success.</li>
</ul>
