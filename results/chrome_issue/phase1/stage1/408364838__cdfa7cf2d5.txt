VULNERABILITY DETAILS
The native function `Runtime_WasmStringEncodeWtf16` takes a `WasmTrustedInstanceData` as its first argument. Although this is an `ExposedTrustedObject`, an attacker can manipulate the pointer handle such that when `memory_bases_and_sizes()->get(2 * index)` is loaded, we can get a predictable pointer value and very large size field.
With the attached PoC, loading 'memory index 10' gives us a fake memory region with base pointer 0x62e75. As the function takes a `double` offset to write the string to, we can subtract this value from our target address and call it to write our string into the desired location.
Please note that while the attached demo is reliable on my machine, it's very sensitive to changes in the heap and any changes to the source code require some debugging to fix offsets.

<p>Hi reporter,</p>
<p>Thanks for the report.
It seems like this builtin is never actually callable like this, i.e. with a controlled WasmTrustedInstanceData (as that would already require a Sandbox bypass to manufacture such a controlled trusted object).<br>
This native is not exposed in production builds and therefore not reachable, which is also why it is disabled for fuzzing, it would lead to false positives like this.</p>
<p>If you can reach this builtin through the regular exposed functions, then this would constitute a proper bypass. So if you can make it work with <code>--fuzzing</code> you can open up a new report and we can take a look.<br>
Closing this as works-as-intended.</p>
