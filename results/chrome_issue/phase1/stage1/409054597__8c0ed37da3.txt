<h3>Vulnerability Description:</h3>
<p>I’ve discovered an unexpected behavior in Chrome that appears to be a security vulnerability. Assigning a specific <code>javascript:</code> string to <code>location</code> results in an HTML <code>&lt;input&gt;</code> tag being rendered in the DOM, without using direct DOM manipulation APIs like <code>innerHTML</code> or <code>document.write</code>.</p>
<h3>Steps to Reproduce:</h3>
<ol>
<li>Create a simple HTML file (e.g., <code>test.html</code>) with the following content:<pre><code>&lt;<span class="stx-keyword">html</span>&gt;
&lt;<span class="stx-keyword">body</span>&gt;
&lt;<span class="stx-keyword">script</span>&gt;
    location=<span class="stx-string">&quot;javascript:location=&#39;javascript:location=\&quot;s&lt;input&gt;sss\&quot;&#39;&quot;</span>;
&lt;/<span class="stx-keyword">script</span>&gt;
&lt;/<span class="stx-keyword">body</span>&gt;
&lt;/<span class="stx-keyword">html</span>&gt;
</code></pre>
</li>
<li>Open the file in Chrome.</li>
<li>Observe that an interactive <code>&lt;input&gt;</code> element (e.g., a text input field) is rendered on the page, followed by the text &quot;sss&quot;.</li>
</ol>
<h3>Expected Behavior:</h3>
<ul>
<li>Assigning a <code>javascript:</code> value to <code>location</code> should either create an infinite loop, throw an error, or modify the URL.</li>
<li>No HTML content (e.g., <code>&lt;input&gt;</code>) should be rendered in the DOM, as no explicit DOM injection mechanism is used.</li>
</ul>
<h3>Actual Behavior:</h3>
<ul>
<li>An interactive <code>&lt;input&gt;</code> HTML element is rendered in the page, along with the text &quot;sss&quot;.</li>
<li>This suggests that the string <code>&quot;s&lt;input&gt;sss&quot;</code> is being incorrectly interpreted as HTML and injected into the DOM.</li>
</ul>
<h3>Additional Information:</h3>
<ul>
<li>I’ve tested this behavior in the latest Chrome version (and claim similar results in other major browsers).</li>
<li>No extensions or additional code were used in the test.</li>
<li>POC video attached</li>
</ul>
<p>I’m happy to provide further details or assist with additional testing.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<ul>
<li>This behavior could represent a security vulnerability, as it allows arbitrary HTML to be injected into the DOM without proper sanitization.</li>
<li>In a real-world scenario, an attacker could potentially exploit this for Cross-Site Scripting (XSS) by injecting malicious tags (e.g., <code>&lt;script&gt;</code>).</li>
<li>Since this works in a local HTML file, it could have broader implications if combined with a web application context.</li>
</ul>
