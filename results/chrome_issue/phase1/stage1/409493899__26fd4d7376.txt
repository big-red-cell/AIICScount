<p>The iframe on the attacker page loads <a href="https://example.com/redirector.html" data-b-widget="url" data-b-original-href="https://example.com/redirector.html" data-b-redirected-href="https://www.google.com/url?q=https://example.com/redirector.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1EZYPOaZPbqDOOh1V_pNwA">https://example.com/redirector.html</a>, which performs a client-side redirect to /protected-resource.</p>
<p>Chrome sends the session_id cookie with this request, despite it being initiated from a cross-site context, violating the SameSite=Strict contract.</p>
<h1>Problem Description</h1>
<p>Observed Behavior
The SameSite=Strict cookie is unexpectedly sent with the request to /protected-resource, even though the request originated through a chain of cross-site interactions (via iframe and client-side redirect).</p>
<p>✅ Expected Behavior
Cookies marked SameSite=Strict should never be sent in any request that originates from a cross-site context, including those involving:</p>
<p>Top-level navigations triggered from iframes.</p>
<p>Client-side redirects initiated from cross-origin subresources.</p>
<p>🔐 Security Impact
This issue weakens CSRF protections for sites relying on SameSite=Strict alone. A malicious actor can induce users to unknowingly perform authenticated actions on another site, potentially leaking sensitive information or triggering unintended state changes.</p>

<p>It&#39;s not a duplicate of <a href="https://crbug.com/40056264" target="_blank">crbug.com/40056264</a>.</p>
<p>This issue is describing an A[B-&gt;B] scenario (a top-level A is embedding a frame that does a B-&gt;B redirect).</p>
<p><a href="https://crbug.com/40056264" target="_blank">crbug.com/40056264</a> is about a cross-site redirect chain, e.g. B[A-&gt;B] where the redirect itself goes cross-site.</p>
<p>I have not tried the repro files attached here, but if it works as described then it is a bug. The iframe should be recognized as cross-site (and SameSite=Strict, or Lax cookies for that matter, should not be sent) because the top-frame <a href="https://attacker.com/malicious.html" data-b-widget="url" data-b-original-href="https://attacker.com/malicious.html" data-b-redirected-href="https://www.google.com/url?q=https://attacker.com/malicious.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2YWo87sGDN-SVqBA8D28X-">https://attacker.com/malicious.html</a> is cross-site from <a href="https://example.com/protected-resource" data-b-widget="url" data-b-original-href="https://example.com/protected-resource" data-b-redirected-href="https://www.google.com/url?q=https://example.com/protected-resource&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3h5Wv1N_iGFDXXlmO7yRRX">https://example.com/protected-resource</a>, regardless of anything about how it got there.</p>
<p>I think this example may unintentionally depend on the fact that localhost is the same host, and cookies may not take the port into account (yet? - see net::kEnablePortBoundCookies). If this repros on two different sites, then yes this is a bug.</p>
