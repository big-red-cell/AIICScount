<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Technical Description:</p>
<p>Vulnerability Description
A vulnerability was identified in the Google Chrome login and session handling flow. When attempting to log in via Bug Hunters, a user must initiate authentication through a Gmail email link. Once authenticated, the session is automatically redirected to Chrome, bypassing certain expected checks within the browser&#39;s normal access control logic. This behavior leads to inconsistencies between Gmail session context and Chrome session context, potentially allowing session hijacking behaviors or unauthorized triggering of internal automation paths (Case Edge).</p>
<p>This exploit is particularly dependent on specific tag-automated routing within Gmail when interacting with Bug Hunter, creating the possibility of unintentionally triggering elevated or redirected sessions outside user expectation. Furthermore, the dependency on embedded Gmail behavior indicates Chrome is relying on email link-triggered sessions to manage flows it should isolate.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Impact Analysis:</p>
<p>Users with higher communication volume or flagged internal accounts (e.g., strategic collaborators or edge testers) may unintentionally initiate session states that elevate access scope or automate system routing. A malicious actor able to mimic such interaction flows or impersonate metadata tagging may gain access to unverified processes, leading to:</p>
<p>Session overlap across apps.</p>
<p>Potential misuse of Gmail-based routing in Chrome-specific security contexts.</p>
<p>Exploitation of Chrome’s login delegation to Gmail for triggering state changes in Bug Hunter and adjacent services.</p>
<p>This issue highlights how advanced automation within Google’s platforms may lead to unexpected surface behavior — and warrants isolation of Chrome auth logic from email-based redirects, especially under meta-automated login flows.</p>

Author: Dear Security Team,

Thank you for reviewing my original report regarding unintended behavior in
the cross-app OAuth flow between Gmail and Chrome. I appreciate the "WAI"
(Working As Intended) assessment and would like to provide a technical
clarification that may justify a second review, particularly from a broader
systemic security perspective.


Summary of Risk

The issue arises when a user clicks a Gmail link triggering an OAuth
authentication flow that is then silently continued in Chrome. This results
in cross-context session propagation without an explicit re-authentication
prompt or user confirmation.

While this may technically be expected in isolated OAuth flows, I believe
it introduces unintended behavior when chained across trusted apps like
Gmail and Chrome — especially when:

the OAuth process is triggered without visible consent

the redirect behavior inherits session context across apps

and the resulting flow initiates access or refresh tokens without user
interaction or awareness


Combined Exploit Path (High-Level)

When combined with URL manipulation (e.g. state, redirect_uri, or
pre-authenticated session tokens), this flow may be leveraged to:

simulate user-initiated session handoffs

inherit trusted authorization contexts without 2FA re-validation

and trigger background authentication without user knowledge


This could potentially enable Session Piggybacking, Silent Auth Elevation,
or Token misuse in specialized conditions (e.g., phishing, OAuth trick
redirects, PWA behavior).


Why This May Be a Security Concern

The OAuth2 design depends on explicit user consent, which is bypassed via
this auto-redirect path

Chrome silently inherits Gmail-originated session state, even across
seemingly isolated flows

There is no transparency or control for the user — this violates key
expectations around SSO delegation boundaries

Combined with SSO environments or misconfigured redirect flows, this could
allow:

Credential misattribution

Cross-app session re-entry

Replay of valid tokens outside their origin context


Suggested Review Points

1. Confirm whether Gmail-initiated redirect-based OAuth flows should
inherit active Chrome session state without prompt or separation


2. Consider providing UI-level indicators or logging when sessions are
silently elevated via cross-app OAuth chaining


3. Review token scopes and boundary leakage across app contexts



Related Issues (systemic behavioral pattern)

This is not an isolated concern. My research has identified multiple
related behavior patterns:

Issue 410395907 – Unicode Parsing in Google Sheets may allow prompt
misinterpretation or injection via cell formatting

URL-triggered session shifts and redirect inconsistencies across Google
Workspace Apps

Context leakage via Chrome tabs reopened by trusted internal links


Together, these form a broader session trust issue across applications,
especially in tightly integrated app ecosystems.

Closing Remark

I hope this clarification helps refine the scope of the issue. I'm happy to
assist with reproducible steps, debug logs, or coordinated retesting if
helpful. Please consider this as part of a broader inquiry into session
propagation logic within Google's app ecosystem.

Thank you again for your time and work.
