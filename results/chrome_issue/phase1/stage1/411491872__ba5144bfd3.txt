<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p><strong>Description</strong>:
Google’s client‑side code unsafely injects object values into the DOM via innerHTML without proper sanitization. By overriding Object.prototype.toString(), an attacker can cause arbitrary HTML/JS to be executed when an object is rendered as a string. This is a true DOM‑based XSS vulnerability—not self‑XSS—because it can be triggered by attacker‑controlled data flowing into the page, not by a user manually pasting payloads into their console.</p>
<p>Note: This flaw is exploitable via external or user‑supplied data (e.g., API response, URL parameter), so it’s not just a “self‑XSS” that requires victim cooperation.</p>
<p><strong>Steps to Reproduce</strong>:</p>
<ul>
<li>Navigate to <a href="https://www.google.com" data-b-widget="url" data-b-original-href="https://www.google.com" data-b-redirected-href="https://www.google.com/url?q=https://www.google.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0xHc4PnJ-5PnGXiIvS00h7">https://www.google.com</a> in a modern browser.
Open the Developer Console (F12 or Ctrl+Shift+I).</li>
<li>Simulate attacker‑controlled object data by executing:</li>
</ul>
<p>&#39;Object.prototype.toString = function() {
return <code>&lt;img src=&quot;x&quot; onerror=&quot;alert(document.cookie)&quot;&gt;</code>;
};
let obj = {};  // attacker‑controlled
document.body.innerHTML = &quot;Hello: &quot; + obj;&#39;</p>
<ul>
<li>Observe the alert showing document.cookie the injected script executed in the page’s context.</li>
</ul>
<p><strong>Expected Behavior</strong>:
The application must never execute untrusted HTML/JS.
Dynamic content inserted into the DOM should be sanitized or escaped.
Inline event handlers should be disallowed (or protected by a strict CSP with nonces/hashes).</p>
<p><strong>Actual Behavior</strong>:
The overridden toString() returns an <span>&lt;img&gt;</span> tag with an onerror handler.
Assigning &quot;Hello: &quot; + obj to innerHTML causes the browser to parse and execute the injected script.</p>
<p><strong>Impact</strong>:</p>
<ul>
<li>High Severity: Arbitrary JavaScript execution in users’ browsers</li>
<li>Session Hijacking: Theft of cookies or tokens</li>
<li>Data Exfiltration: Access to sensitive page data</li>
<li>Defacement/Phishing: UI manipulation for social engineering</li>
</ul>
<p><strong>Suggested Remediation</strong>:</p>
<ul>
<li>Avoid using innerHTML for untrusted data; prefer textContent or safe DOM APIs.</li>
<li>Sanitize or escape all dynamic content (e.g., use DOMPurify).</li>
<li>Enforce a strict Content Security Policy disallowing inline scripts (script‑src &#39;self&#39;; without unsafe-inline).</li>
<li>Do not rely on object conversion for rendering; use explicit templating that auto‑escapes.</li>
</ul>
<p><strong>Severity</strong>: High</p>
<ul>
<li>Affected Component: Client‑side rendering logic using innerHTML
Environment: Google.com (latest production), Modern browsers (Chrome, Firefox, Edge, Safari)</li>
</ul>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p><strong>Who Can Exploit</strong>:</p>
<ul>
<li>Any attacker who can control or influence the object data that Google.com renders via innerHTML.
This might be:</li>
<li>A malicious third‑party widget or ad network supplying JSON data.</li>
<li>An attacker who can inject parameters into a URL or API request that get reflected into the page’s client‑side rendering.</li>
<li>A compromised browser extension or user script that alters the page’s JavaScript context.</li>
</ul>
<p><strong>What They Gain</strong></p>
<ul>
<li>By successfully exploiting the DOM‑XSS:</li>
<li>Session Hijacking – Steal cookies or tokens (document.cookie, localStorage) to impersonate users.</li>
<li>Data Exfiltration – Read or modify sensitive content on the page (e.g., search queries, user profiles).</li>
<li>Phishing/Defacement – Inject fake login forms or modify the UI to trick users into disclosing credentials.</li>
<li>Persistence – Install persistent scripts (via service‑worker hijacking or local storage) that continue to run across visits.</li>
</ul>
