<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>I discovered this attack vector where a webpage can open any trusted domain (e.g., Gmail) in a new tab using window.open() and then use setTimeout() to redirect the new tab to a malicious URL after a delay. This behavior bypasses the Same-Origin Policy (SOP) protections and could be exploited for malicious purposes.

<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Impact:</p>
<ol>
<li>
<p>Session Hijacking: If the trusted tab had active authentication, the redirect could capture cookies or tokens via evil.com or attacker&#39;s domain, potentially allowing the attacker to hijack the user&#39;s session and gain unauthorized access to their Google or any authenticated account on that trusted domain.</p>
</li>
<li>
<p>Enhanced Tabnabbing: Attackers can replace trusted tabs with malicious clones (e.g., Keylogger, )  bypassing standard tabnabbing defenses.</p>
</li>
<li>
<p>User Expectation Violation: Chrome&#39;s current behavior contradicts user intent—interaction with attacker&#39;s_domain.com should not grant control over unrelated tabs.</p>
</li>
</ol>

Author: Thank you for reviewing this report. While I understand the current implementation doesn't leak cross-origin information, I believe the core issue lies in UI spoofing via delayed tabnabbing which i presume might be a violation of Chrome's VRP rules regarding deceptive user interfaces.

# Key Differences: Classic Tabnabbing vs. Deferred Cross-Origin Tab Weaponization (My Submission)


|   Aspect
|----------------------------------------------------------------------------------------------------------
|1. Attack Flow
|2. Trust Relationship
|3. Timing                
|4. Trigger Mechanism      
|5. Browser Defenses  
|6. Social Engineering                            

|   Classic  Tabnabbing/Reverse Tabnabbing                                                                                                                        
|----------------------------------------------------------------------------------------------------------   
|1. Legitimate site ➔ Malicious new tab ➔ Original tab hijacked via `window.opener` 
|2. Exploits trust in the *original tab* (e.g., LinkedIn)                                                          |
|3. Immediate redirect when new tab loads                                              
|4. Uses `target="_blank"` links with missing `rel=noopener`                                   
|5. Mitigated by modern browsers via implicit `rel=noopener` ****                     
|6. Relies on user returning to original tab after interaction with new tab           

| Deferred Cross-Origin Tab Weaponization  
|----------------------------------------------------------------------------------------------------------   
|1. Malicious site ➔ Legitimate new tab ➔ Delayed redirect via `setTimeout()`                               
|2. Exploits trust in the *newly opened tab* (e.g., Linkedin)                                        
|3. Uses `window.open()` + delayed `location` override          
|4. Delayed redirect (e.g., 1-5 minutes) to bypass user vigilance                                        
|5. Bypasses `rel=noopener` defenses (not applicable to programmatic `window.open()`)                   
|6. Uses fake instructions (e.g., "Keep the tab open") to maintain user focus on the malicious context 





# Impact Comparison:

|   Classic Tabnabbing/Reverse Tabnabbing       |   Deferred Cross-Origin Tab Weaponization                |
|-------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| Session hijacking via original tab redirection   | Session hijacking via trusted tab replacement           |
| Phishing via cloned login pages                         | Advanced phishing with time-delayed context shift  |
| Relies on `window.opener`                                  | Uses direct `Window.location` control                         |



Reference: https://medium.com/@ibm_ptc_security/reverse-tabnabbing-ccede451d444

Deferred Cross-Origin Tab Weaponization:   

1. Trusted Origin Pretense: 

   - This attack weaponizes the newly opened trusted tab (eg, Gmail) instead of hijacking the original tab. This subverts user expectations and Creates false trust , as the initial interaction appears legitimate

2. Bypass of Modern Defenses:
   
   - Classic defenses like rel=noopener and Cross-Origin Opener Policy (COOP) focus on target="_blank" links, not programmatic window.open() with user gestures. 
     this attack leverages Chrome’s permission inheritance for user-triggered popups

3. Exploitation of Browser Behavior

   - User-triggered window.open() (granting initial control)

   - Delayed redirect post-user interaction (evades popup blockers)

VRP Relevance:
This directly violates Section the  ("Security UI Spoofing ``") 
`https://bughunters.google.com/about/rules/chrome-friends/5745167867576320/chrome-vulnerability-reward-program-rules`

as it:
- Creates false trust via legitimate domains
- Exploits Browser's delayed execution model to override user intent
- Circumvents anti-spoofing measures through temporal decoupling


I would also like to request to reclassify this as a UI deception vulnerability rather than a SOP bypass issue. The risk may not lies on cross-origin data leakage, but in abusing Chrome's navigation permissions to create malicious UI contexts that users perceive as trusted
