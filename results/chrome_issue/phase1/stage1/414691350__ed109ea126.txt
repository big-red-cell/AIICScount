<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>This vulnerability class targets inconsistencies and race conditions in Chrome’s Trusted Types enforcement mechanism, particularly in how it interacts with asynchronous DOM mutation patterns such as microtasks, macrotasks, timers, and MutationObservers. These inconsistencies can enable execution of dangerous payloads (e.g., onerror=alert()) even when Trusted Types are configured or expected to be enforced.</p>
<p><strong>Technical Background</strong>
Trusted Types is a client-side web browser security feature intended to mitigate DOM-based XSS by restricting the use of dangerous sinks like element.innerHTML, document.write(), etc. With Trusted Types enabled (via CSP), any assignment to these sinks must go through a TrustedHTML policy.</p>
<p>A CSP header like:
Content-Security-Policy: require-trusted-types-for &#39;script&#39;; trusted-types default
...ensures that only content explicitly wrapped with a TrustedHTML policy can be assigned to sensitive sinks.</p>
<p><strong>Core Issue</strong>
The observed behavior indicates that Trusted Types enforcement can be bypassed under specific asynchronous execution patterns, including:</p>
<ul>
<li>Microtask mutations (e.g., Promise.resolve().then(...))</li>
<li>Timers (setTimeout) that precede or race with policy creation</li>
<li>MutationObserver-triggered updates</li>
<li>Asynchronous innerHTML assignments before the policy is registered</li>
<li>Trusted Type assignments occurring without proper CSP enforcement</li>
</ul>
<p>These patterns reveal a race condition between DOM mutation and policy enforcement, or a policy scope leak, resulting in code execution that should be blocked.</p>
<p><strong>Test Cases That Confirm It</strong></p>
<p><code>const policy = trustedTypes.createPolicy(&#39;x&#39;, { createHTML: s =&gt; s }); setTimeout(() =&gt; { el.innerHTML = policy.createHTML(</code><span>&lt;img src=x onerror=alert(1337)&gt;</span><code>); }, 0);</code></p>
<p>Result: Executes alert — implies that policy assignment and sink enforcement are not synchronized.</p>
<p>testTrustedTypesEnforcementNoPolicy</p>
<p><code>el.innerHTML = </code>&lt;img src=x onerror=alert(&#39;no_policy_exec&#39;)&gt;<code>;</code></p>
<p>Result: Executes alert even though no policy was defined, suggesting Trusted Types were not enforced (CSP not present).</p>
<p>testDesyncPolicyAssignment</p>
<p><code>setTimeout(() =&gt; { const html = policy.createHTML(</code>&lt;img src=x onerror=alert(&#39;desync&#39;)&gt;<code>); container.innerHTML = html; }, 10);</code></p>
<p>testMutationObserverTrustedTypesLeak</p>
<p><code>const observer = new MutationObserver(() =&gt; { target.innerHTML = policy.createHTML(</code>&lt;img src=x onerror=alert(&#39;mo_leak&#39;)&gt;<code>); });</code></p>
<p>Result: Alert executes — demonstrates inconsistent Trusted Types scope inside MutationObserver microtask.</p>
<p><strong>Root Vulnerability Themes</strong></p>
<ol>
<li>
<p>Policy registration and sink usage can be desynchronized.</p>
</li>
<li>
<p>Mutation contexts (microtask, macrotask, observer) can escape expected policy enforcement boundaries.</p>
</li>
<li>
<p>trustedTypes.createPolicy() can be invoked and used before CSP enforcement is activated.</p>
</li>
<li>
<p>InnerHTML executes even without CSP header, meaning developers can believe they&#39;re protected while they&#39;re not.</p>
</li>
</ol>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p><strong>Severity</strong></p>
<p>Impact: High (Potential XSS in apps relying on Trusted Types without robust CSP)</p>
<p>Exploitability: Medium (Requires precise async control, but scriptless XSS payloads are feasible)</p>
<p>Affected Environments: Any Chrome/Chromium-based environment where Trusted Types are used without strict and correctly timed CSP enforcement.</p>
