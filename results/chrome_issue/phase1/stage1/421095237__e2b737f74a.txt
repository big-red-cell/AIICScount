This proof-of-concept demonstrates a logical UXSS and site isolation bypass in Chromium, where a SharedWorker launched from a benign-looking origin (simulated via port bank1.local) survives a simulated DNS rebinding to a trusted site (e.g. bank2.local).<br><br>Despite the change in visual and functional origin, the attacker&#39;s SharedWorker remains alive and can intercept cross-origin messages containing sensitive data, such as session tokens (auth_token). This violates Chromium’s origin-based trust model and the assumptions of site isolation.<br><br> Core Attack Flow<br> The attacker loads a page on localhost:8000/attacker, which creates a SharedWorker.<br><br> An iframe is loaded with localhost:8001/page.html (Bank 1 – benign).<br><br> After 3 seconds, the iframe is re-navigated to localhost:8002/page.html (Bank 2 – trusted).<br><br> Bank 2 sets a secure auth_token cookie and sends it via postMessage to its parent (as many real sites do).<br><br> The attacker’s SharedWorker, still alive, captures the token despite the navigation and logical origin switch.<br><br> PoC Features<br>Uses multiple ports to simulate DNS rebinding (attacker-controlled domain → target domain).<br><br>Exploits the persistence of SharedWorker beyond a change of logical origin.<br><br>Demonstrates real token exfiltration via postMessage.<br><br>Requires no DOM injection or XSS — purely a logic flaw in isolation boundaries.<br><br> Why this is dangerous<br>SharedWorker’s scope is not properly revalidated after navigation.<br><br>Sensitive data is leaked from what appears to be a trusted origin.<br><br>Breaks the assumption: “active JavaScript should match the current visible origin.”<br><br>Bypasses same-origin protections in practice.<br><br>Could be used to compromise banking, identity, or OAuth-based login flows.<br><br> Realistic Threat Model<br>In the real world, an attacker could host a malicious site under *.<a In the initial proof of concept I submitted, both domains (bank1 and bank2) were hosted on localhost, meaning they shared the same top-level domain (TLD) and were therefore not fully cross-origin. While it demonstrated the logical mechanism, it did not satisfy the strict origin separation expected in real-world attack scenarios.<br><br>Following the feedback from your team, I restructured the setup to use two distinct publicly resolvable domain names:<br><br><a href="https://www.google.com/url?q=http://attackerpoc.duckdns.org&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2Hqr0J9hkQmHVZ2ejchU9H" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://attackerpoc.duckdns.org" data-b-redirected-href="https://www.google.com/url?q=http://attackerpoc.duckdns.org&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2Hqr0J9hkQmHVZ2ejchU9H">attackerpoc.duckdns.org</a><br><br><a href="https://www.google.com/url?q=http://bankvictim.dynv6.net&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0QSRplLwCFxkx7BT_5fmtS" target="_blank" rel="noopener noreferrer nofollow ugc" data-b-widget="url" data-b-original-href="http://bankvictim.dynv6.net" data-b-redirected-href="https://www.google.com/url?q=http://bankvictim.dynv6.net&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0QSRplLwCFxkx7BT_5fmtS">bankvictim.dynv6.net</a><br><br>Both domains are served on the same physical host and port (:8000), but per the RFC 6454 origin definition, they are strictly considered separate origins, as they differ by hostname (TLD). The browser enforces isolation based on scheme, host, and port — not physical server or IP address.<br><br>This confirms that the current proof of concept successfully demonstrates an inter-origin attack scenario, and the isolation bypass observed is not due to shared origin or local testing artifacts, but a result of logical persistence across origins.<br><br><br><br><br><br>
