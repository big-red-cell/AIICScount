<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>This report describes a full-chain vulnerability affecting Google Chrome Desktop (v137+), composed of three chained bugs across accessibility, DevTools, and extension message handling.</p>
<p>The attack leverages:</p>
<ol>
<li>AXTree Heap Leak: Exploits a timing race in the Accessibility Tree’s mutation observers, producing a stable JS object address leak.</li>
<li>DevTools Actor Injection: Uses inspectedWindow.eval to execute arbitrary code in the privileged DevTools chrome context.</li>
<li>Extension Message Hijack: Spoofs trusted extension messaging response to trigger callback execution with elevated access.</li>
</ol>
<p>Together, these allow full JavaScript memory manipulation, chrome-privileged actor registration, and final escape from the renderer sandbox.</p>
<p>Technical Root Cause:</p>
<ul>
<li>
<p>Heap Leak (AXTree): The AXTree node traversal logic does not properly guard against object shape changes during recalculation. Crafted DOM nodes with deep nesting and ARIA roles can leak internal object pointers during accessibilityUpdate() traversal.</p>
</li>
<li>
<p>DevTools Injection: A race condition allows eval() inside the DevTools actor environment to reflect attacker-supplied Blob URLs. These can embed a full actor registration script that runs in chrome context.</p>
</li>
<li>
<p>Extension Messaging Spoof: Chrome’s IPC message routing does not verify origin when responding to extension message events. By mimicking an internal extension ID and crafting the callbackId, arbitrary responses are routed to DevTools scripts.</p>
</li>
</ul>

<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Any website, advertisement, or malicious third-party page can exploit this vulnerability chain upon a user visiting the page — no interaction required. The attacker gains full JavaScript-level remote code execution, followed by a privileged DevTools actor injection and sandbox escape. This results in arbitrary code execution within the Chrome browser process, allowing access to sensitive browser APIs, extension data, internal IPC messaging, and potentially system-level privilege escalation via chained attacks.</p>

<p>Mitigation Recommendations (Optional):
While the vulnerabilities themselves are severe, their resolution may be achievable through targeted architectural adjustments. The following suggestions are provided in good faith to support remediation efforts, based on analysis of internal Chrome subsystem behavior observed during testing:</p>
<p>Harden AXTree Traversal Logic
Implement stricter guards during accessibilityUpdate() to prevent object shape or prototype mutations mid-traversal. Validate the integrity of ARIA-annotated nodes and reject frames that result in observable structure drift.</p>
<p>Restrict DevTools eval() in Chrome Context
Disallow inspectedWindow.eval from evaluating untrusted Blob URLs or DOM-injected scripts. Add a content origin check or privilege boundary layer to prevent actor injection from renderer contexts.</p>
<p>Enforce Origin Validation on Extension IPC Responses
Require Chrome’s internal extension message routing (callbackId) to verify sender and origin consistency. Introduce a nonce or token validation layer that binds the requestor’s extension ID to its callback scope.</p>
<p>Isolate Renderer-Privileged Context Leakage
Ensure that DevTools and extensions cannot share IPC routes or callback handlers with standard renderer contexts. Treat all cross-component communication as untrusted unless explicitly whitelisted.</p>
<p>Add DevTools Actor Registration Heuristics
Monitor DevTools actor registration flow for abnormal patterns (e.g., Blob eval from renderer injection), and block or warn on suspicious privilege elevations triggered from inside loaded pages.</p>
