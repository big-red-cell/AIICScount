<h1>Problem Description</h1>
<p>Good day, I&#39;m trying to understand if it&#39;s intended behavior that a credentialless iframe can access data from a same-origin non-credentialless iframe.
In the attached example, I&#39;ve demonstrated a simple example of how this works.</p>
<p>In a real exploit, this can be used in the following logic:
Create the following HTML file:</p>
<pre><code>&lt;iframe src=&quot;http://attacker.domain/csrf&quot; width=&quot;40%&quot; height=&quot;500px&quot; credentialless&gt;&lt;/iframe&gt;
&lt;iframe src=&quot;http://victim.domain/&quot; width=&quot;40%&quot; height=&quot;500px&quot;&gt;&lt;/iframe&gt;
</code></pre>
<p><code>http://attacker.domain/csrf</code> uses a CSRF issue in the login service and logs into the attacker&#39;s account, where after that a Self-XSS is triggered and the cookie from the original victim&#39;s account is retrieved using:</p>
<pre><code>window.top[1].document.cookie
</code></pre>
<p>I don&#39;t consider this to be a vulnerability in Chrome, as it only adds an exploitation vector in cases where the target site is already vulnerable to CSRF + SELF-XSS
But I decided to ask for your opinion before publishing this publicly</p>
<h1>Summary</h1>
<p>credentialless iframe can access original origin cookie</p>

<p>Login CSRF isn’t really necessary either, since you can just use a variation of clickjacking on the login form.
So the only real requirement here is the presence of a Self-XSS vulnerability in the application.</p>
<p>In my opinion, this simply adds a way to exploit Self-XSS bugs that previously couldn’t be exploited.

I don&#39;t think this is an issue?<br><br>Credentialless iframes were created to fit one threat model: the embedding document attacking the credentialless iframe with a Spectre attack. Since here the attack is coming from the credentialless iframe, this is outside the scope of the threat model for credentialless iframes. Basically, from the point of view of the embedder, embedding an iframe as credentialless instead of in a regular manner does not give you any additional protection. I believe that an iframe could do all of the steps you describe, so I think this should be marked as WAI.
