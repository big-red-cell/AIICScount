<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<h2>Summary</h2>
<p>A Use-After-Free vulnerability exists in Chrome&#39;s file input implementation. When a file input element is removed from the DOM using <code>removeChild()</code>, the element retains its ability to trigger file selection dialogs and read file contents.</p>
<h2>Technical Details</h2>
<ul>
<li><strong>Component</strong>: Blink file input elements (<code>&lt;input type=&quot;file&quot;&gt;</code>)</li>
<li><strong>Method</strong>: DOM manipulation via JavaScript</li>
<li><strong>Root Cause</strong>: Improper cleanup of system resources on element removal</li>
</ul>
<h2>Steps to Reproduce</h2>
<ol>
<li>Create a file input element: <code>const input = document.createElement(&#39;input&#39;); input.type = &#39;file&#39;;</code></li>
<li>Add to DOM: <code>document.body.appendChild(input);</code></li>
<li>Remove from DOM: <code>document.body.removeChild(input);</code></li>
<li>Trigger on freed element: <code>input.click();</code></li>
<li><strong>Result</strong>: File dialog opens and files can be selected/read despite element removal</li>
</ol>

<li>Basic UAF confirmation</li>
<li>Directory traversal via <code>webkitdirectory</code></li>

</ul>

Author: dr...@chromium.org
<p>[security triage] Thanks for the report. This is not a use-after-free. Use-after-free refers to a vulnerability pattern in languages like C++ where you can have a reference to an object when the backing memory is being used for something else. JavaScript does not have this problem due to being a garbage-collected language. As long as you have a reference to an object, the backing memory is not freed by the garbage collector. In particular, removal from the document does not necessarily free the memory. Your PoC maintains a reference through the <code>input</code> variable, which prevents the garbage collector from freeing the memory, and making it safe to use.</p>
