<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p><strong>Summary</strong></p>
<p>The Chrome browser&#39;s download UI (chrome://downloads) incorrectly attributes the download origin when a file is downloaded through a google.com/url redirection endpoint. Instead of showing the actual file source domain (ybt01.github.io), Chrome displays google.com as the download origin, which may mislead users about the true origin of the file.</p>
<p><strong>Vulnerable Behavior</strong></p>
<p>Chrome shows &quot;google.com&quot; as the source of the download, when the actual file is served from a different domain (ybt01.github.io), potentially misleading users about the safety or trustworthiness of the file source.</p>
<p><strong>Reproduce</strong></p>
<ol>
<li>Host this file :</li>
</ol>
<blockquote>
</blockquote>
<div>&lt;body onload=&quot;autoRedirect()&quot;&gt;
  &lt;script&gt;
    function autoRedirect() {
      window.open(
        &quot;https://www.google.com/url?q=https://ybt01.github.io/upload/app-debug.apk&amp;sa=D&amp;source=autotrigger&amp;usg=INVISIBLE123&quot;,
        &quot;_blank&quot;,
        &quot;width=1,height=1,top=-9999,left=-9999,scrollbars=no,resizable=no&quot;
      );
    }
  &lt;/script&gt;
&lt;/body&gt;
</div>
<ol start="2">
<li>When the file is downloaded, go to chrome://downloads</li>
<li>The origin is shown as google.com, even though the file is served from ybt01.github.io</li>
</ol>
<p><strong>Expected Behavior :</strong></p>
<p>Chrome should show the final origin (ybt01.github.io) of the download, not the redirector domain (google.com).</p>
<p><strong>Actual Behavior :</strong></p>
<p>When a file is downloaded using a redirect link like:
<a href="https://www.google.com/url?q=https://ybt01.github.io/upload/app-debug.apk&amp;sa=D&amp;source=autotrigger&amp;usg=INVISIBLE123" data-b-widget="url" data-b-original-href="https://www.google.com/url?q=https://ybt01.github.io/upload/app-debug.apk&amp;sa=D&amp;source=autotrigger&amp;usg=INVISIBLE123" data-b-redirected-href="https://www.google.com/url?q=https://www.google.com/url?q%3Dhttps://ybt01.github.io/upload/app-debug.apk%26sa%3DD%26source%3Dautotrigger%26usg%3DINVISIBLE123&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3wEbnqkFEH0Vu_sLSSBrbo">https://www.google.com/url?q=https://ybt01.github.io/upload/app-debug.apk&amp;sa=D&amp;source=autotrigger&amp;usg=INVISIBLE123</a>
and triggered via JavaScript using window.open() (or even a standard anchor tag), Chrome downloads the file from ybt01.github.io, but the Chrome downloads page (chrome://downloads) incorrectly displays the download origin as google.com.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<ul>
<li>User deception: Users may wrongly trust a file because it appears to be downloaded from Google.</li>
<li>Security UI bypass: This undermines Chrome’s trust indicators and makes phishing/malware delivery more plausible.</li>
<li>Potential for abuse in malware distribution: An attacker could serve a malicious APK/executable under the guise of a google.com-initiated download.</li>
</ul>

Author: dr...@chromium.org
<blockquote>
<p>This is not entirely accurate. In my testing, when a user clicks the download link, the popup clearly displays the final download URL, and it does show ybt01.github.io before the file starts downloading.</p>

<p>That&#39;s not a choice the browser made, it&#39;s an implementation detail of the google.com redirect. I am certain there exist sites with similar redirects that don&#39;t show you the URL. We don&#39;t want to decide what is appropriate behavior for the browser based on the details of this one site. Instead, we set a policy that the initiator of the download is what we show to the user. And in this case, that&#39;s google.com.</p>
<p>But maybe I wasn&#39;t sufficiently precise with my phrasing. It&#39;s not necessarily that a user doesn&#39;t see the ybt01 URL, but that it&#39;s not meaningful to them. If the attacking site says &quot;click here to get Google&#39;s recommended software update&quot; and then pops up a window with google.com that downloads from some-random-site-with-a-meaningless-host.com, which site is the user trusting? You argue that they will see and remember some-random-site-with-a-meaningless-host.com, but I think their trust is closer associated with google.com.</p>
<p>Now ideally we&#39;d track this all the way back to the attacking site, but tracking user intent through multiple navigations is pretty much impossible, so we went with whoever is the last click.</p>
