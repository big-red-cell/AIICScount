# Overview:

A Chrome extension can access and execute arbitrary JS on all iframes embedded within isolated and sensitive WebUI webpages, thus violating Chrome's process isolation.

This allows an attacker to easily:

1: Spoof chrome://whatsnew page entirely.

2: Spoof trusted application menus within chrome://newtab & chromewebstore.google.com

3: Huge foot gun bound to happen if an iframe's postMessages are not properly sanitized.

----

# Steps to reproduce:

Pre-requisite: Please sign into your Google account. Not required, but makes for a better demonstration of this issue.

**chrome://whatsnew steps:**

1. Load poc.zip into Chrome

2. Visit chrome://whatsnew

Observe https://www.example.com is loaded. 

*Note: this can be any website.*

**chrome://newtab steps:**

1. Load poc.zip into Chrome

2. Visit chrome://newtab

3. Click 9 dot square or your profile icon. 

Observe the fake menus.

**chromewebstore.google.com steps:**

1. Load poc.zip into Chrome

2. Visit https://chromewebstore.google.com.

3. Click 9 dot square or your profile icon. 

Observe the fake menus.

----

# Impact:

All the iframes contained have access to certain methods that the embedder has put into place through window message listeners. A simple `parent.postMessage("")` from the iframe is enough to invoke these methods. 

I have gone through all the methods and cannot find anything too dangerous, however this is a big foot gun bound to happen. 

**Examples:**

*chrome://newtab:*
```java
window.addEventListener("message", ( ({data: data}) => {
    if (data.type === "updateAppearance") {
        oneGoogleBarApi.setForegroundLight(data.applyLightTheme)
    }
}
```

*chrome://whats-new:*
```java
    handleMessage_(event) {
        if (!this.url_) {
            return
        }
        const iframeUrl = new URL(this.url_);
        if (!event.data || event.origin !== iframeUrl.origin) {
            return
        }
        const data = event.data.data;
        if (!data) {
            return
        }
        switch (data.event) {
        case EventType.BROWSER_COMMAND:
            handleBrowserCommand(data);
            break;
        case EventType.PAGE_LOADED:
            handlePageLoadMetric(data, this.isAutoOpen_);
            break;
        case EventType.MODULES_RENDERED:
            break;
        case EventType.EXPLORE_MORE_OPEN:
            WhatsNewProxyImpl.getInstance().handler.recordExploreMoreToggled(true);
            break;
        case EventType.EXPLORE_MORE_CLOSE:
            WhatsNewProxyImpl.getInstance().handler.recordExploreMoreToggled(false);
            break;
        case EventType.SCROLL:
            handleScrollDepthMetric(data);
            break;
        case EventType.TIME_ON_PAGE_MS:
            handleTimeOnPageMetric(data);
            break;
        case EventType.MODULE_IMPRESSION:
        case EventType.GENERAL_LINK_CLICK:
        case EventType.VIDEO_STARTED:
        case EventType.VIDEO_ENDED:
        case EventType.PLAY_CLICKED:
        case EventType.PAUSE_CLICKED:
        case EventType.RESTART_CLICKED:
            handleModuleEvent(data);
            break;
        default:
            console.warn("Unrecognized message.", data)
        }
    }
```

<ol>
<li>It&#39;s well-known and intended that content script can still use DOM methods (e.g. to register event listeners), even though the content script itself executes in an isolated world.</li>
<li>In general, <code>&lt;all_urls&gt;</code> permission does not include chrome:// schemes. Note that certain chrome:// pages may include other iframes (e.g. chrome://newtab and chrome://whats-new both iframe non-WebUI URLs), and those iframes may be be able to load non-WebUI content: in those cases, it is expected that <code>&lt;all_urls&gt;</code> still allows those iframed pages to be modified.</li>
</ol>
