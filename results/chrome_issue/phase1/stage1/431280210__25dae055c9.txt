<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>When setting a Content-Security-Policy header with: this data:
<code>sandbox allow-scripts allow-same-origin allow-top-navigation-by-user-activation</code>
...top level navigation should be prevented if it does not contain user interaction.</p>
<p>This can be bypassed if you eval() the given functions instead.</p>
<p>I would assume this is unintended, though I don&#39;t know the security expectations of allow-scripts, allow-same-origin, and CSP policies applied via HTTP headers.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>A threat actor is actively exploiting the vulnerability to bypass sandboxing for advertisement iFrames to redirect the user to phishing pages.</p>

<p>I think the issue here is that the combination of allow-same-origin and allow-script gives the iframed document script access into its parent. Yes, the iframed document can circumvent the user activation requirement, but it could do a lot of other things inside its parent document too. It&#39;s basically not sandboxed.</p>

Author: al...@gmail.com
<p>That makes sense to me, though do you believe the root page itself should at least attempt to enforce that activation requirement universally if it is set over CSP header?  I understand the threat actor can just add a script element with the click event listener to the root, though from this point, I would attempt to clamp it with the <code>script-src-attr</code> parameter, or a mix of other CSP script protections to reduce attack effectiveness. We do load in the srcdoc iframes under another domain&#39;s iframe, so the CSP settings get reset for the child frames. This would hopefully allow nested iframe children to have click handlers for their own content, and perhaps read/write content to the root document, with extra restrictions under the root document&#39;s CSP (I think?). That is where the user-navigation requirement would become useful on the root document.</p>
<p>I understand the threat actor can outright replace the root page in this case, though I feel this is good if a threat actor is forced to deliver much more malware to a page rather than sending the user off-site. This would give our anti-malvertising tools (Confiant) a bit more time to scan the requests and disable the malicious scripts. I might be wrong though.</p>
<p>I&#39;ve had my hands wrapped up in malicious advertisements for the last few weeks, I feel like this would slow down the threat actor a lot if they couldn&#39;t send the user to one of their universal landing pages anymore. Though if the solution &amp; CSP becomes widespread, I don&#39;t know if it would make much difference. I do find usage of CSP rare enough that it might be too costly for the attacker to work around this.</p>
<p>My suggestions here almost sound like a feature request, I would be quite happy if this bug report could invoke some thoughts as a suggested implementation change instead.</p>
