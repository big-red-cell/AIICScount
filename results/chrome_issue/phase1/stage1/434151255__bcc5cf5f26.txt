<h1>Problem Description</h1>
<p>A Use-After-Free vulnerability exists in Chrome’s GPU process when using GPUQueue.copyExternalImageToTexture() with a stale ImageBitmap.</p>
<p>The issue arises from a race condition during the lifetime management of ImageBitmap objects and their underlying GPU memory resources.</p>
<p><strong>Root Cause</strong></p>
<ol>
<li>An ImageBitmap is created on the main thread from a canvas, filled with a recognizable pattern (e.g., 0xDEADBEEF).</li>
<li>A gpuDevice.queue.copyExternalImageToTexture() operation is initiated, referencing this ImageBitmap as the source. This operation sends a command to the GPU process to read from the ImageBitmap&#39;s backing memory.</li>
<li>Concurrently, the ImageBitmap is transferred to a Web Worker, which implicitly detaches its ownership from the main thread. This makes the ImageBitmap&#39;s underlying memory eligible for garbage collection and subsequent freeing by the browser.</li>
<li>The GPU copy operation, still in progress, attempts to access the ImageBitmap&#39;s backing memory <strong>after it has been freed</strong>. This results in a Use-After-Free read.</li>
<li>Heap spraying (using WebGL buffers, WebGPU buffers, and WebGPU textures) is performed in parallel to increase the likelihood of the freed ImageBitmap memory being re-allocated with attacker-controlled patterns (0x43434343 or 0x44444444).</li>
</ol>
<h3><strong>Impact</strong></h3>
<p><strong>Reliable UAF Read (Information Leak):</strong></p>
<p>The PoC reliably leaks the contents of previously freed GPU memory back into JavaScript. When the UAF is triggered successfully, the leaked data on the output canvas and in the console logs consistently shows the 0xDEADBEEF pattern that was originally used to fill the source ImageBitmap. This confirms that memory that was supposed to be freed has been read.</p>
<p><strong>No Crash Required:</strong></p>
<p>Unlike other GPU vulnerabilities, this issue does not necessarily require a full GPU process crash to be observed. The leaked data is directly visible and verifiable in JavaScript. While a crash can occur in some fuzzing iterations due to other factors (as seen in the full fuzzer logs), the UAF read itself is observable without a crash.</p>
<h3><strong>Security Implications</strong></h3>
<p><strong>Confidentiality:</strong></p>
<p>Attackers can reliably leak the contents of freed GPU memory. This memory may contain sensitive pixel data from other tabs, cross-origin resources, or internal GPU process structures. This can lead to a violation of user privacy and bypass security boundaries (e.g., Same-Origin Policy for GPU memory).</p>
<p><strong>Integrity / Potential Code Execution:</strong></p>
<p>The ability to deterministically re-read freed GPU memory provides a powerful primitive for Address Space Layout Randomization (ASLR) bypass. By leaking pointers or internal data structures, an attacker can gain knowledge of memory layout. This knowledge, combined with other potential vulnerabilities (e.g., other UAFs, heap corruptions, or logic bugs), could potentially be leveraged for arbitrary memory corruption within the GPU process sandbox, leading to arbitrary code execution or sandbox escape.</p>
<p><strong>Attack Surface:</strong></p>
<p>This vulnerability is exploitable remotely via malicious web content, requiring no user interaction beyond visiting a crafted web page.</p>
