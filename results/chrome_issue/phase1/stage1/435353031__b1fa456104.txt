<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Hello Google Security team,</p>
<p>I am writing to report a significant security issue involving a publicly writable Google Cloud Storage (GCS) bucket used by the Perfetto trace recording UI.</p>
<p>While I initially discovered the affected code in a ChromiumOS mirror of the Perfetto project, the vulnerability itself lies in a Google-managed web service and infrastructure.</p>
<p>I believe this presents a supply chain risk and could be abused to inject malicious configurations into the Perfetto UI used by Android developers and partners.</p>
<p>The Google Cloud Storage bucket <strong>perfetto-ui-data</strong> is publicly writable. I was able to upload arbitrary files to this bucket without authentication using the gsutil CLI.</p>
<p>This bucket is referenced in the file:</p>
<pre><code>src/aosp/external/perfetto/ui/src/plugins/dev.perfetto.RecordTraceV2/pages/record_page.ts
</code></pre>
<p>Via the line</p>
<pre><code>const url = `https://storage.googleapis.com/${BUCKET_NAME}/${hash}`;
</code></pre>

<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Because the perfetto-ui-data GCS bucket is publicly writable and is used in trace configuration loading code, this presents a supply chain and user-targeted security risk:</p>
<p>Malicious Config Injection</p>
<p>An attacker can upload a crafted configuration file and generate a URL pointing to it. If any frontend (e.g., a trace recording UI) loads configs from this bucket, users may unknowingly apply untrusted settings, leading to unexpected device behavior, excessive resource usage, or privacy exposure.</p>

<p>The fact that we have a public GCS bucket is working as intended.</p>
<p>I don&#39;t see any vulnerability here. The attached video proves nothing, you just show you are able to copy a file into a world-writable bucket (mildly surprising)</p>
<p>Let&#39;s break this down:</p>
<ol>
<li>
<p>the bucket is publicly-writable but unlistable. You cannot &quot;ls&quot; the files in the bucket. which means you cannot see any of the existing files.</p>
</li>
<li>
<p>The files are stored in the bucket based on the hash of their contents, which is quite hard to guess (And even if you did, you would invalidate the hash). Due to its permission you can&#39;t even overwrite existing files even if you magically guessed the path.</p>
</li>
</ol>
<p>So, yes an attacker can forge a NEW config file and create a URL that points the UI to that. So what?</p>
<p>If the config is invalid, it will fail parsing. if it&#39;s valid, you&#39;ll end up with some valid (maybe useless) config for recording traces. Those configs are only used to record traces via usb. they don&#39;t affect the operation of the UI.</p>
<p>Even if the bucket was non-public and was using OAUTH2, you could still use devtools to inject arbitrary configs and achieve the same end result, so the public-writable part doesn&#39;t really gain you anything</p>
<blockquote>
<p>users may unknowingly apply untrusted settings, leading to unexpected device behavior, excessive resource usage, or privacy exposure.</p>
</blockquote>
<p>There is a lot of speculation that doesn&#39;t match reality here.
That config is passed to the device if the user click record. So first of all you&#39;ll have to convince a user to click on a &quot;malicious&quot; link, then you would have to convince them to select a device and click &quot;record&quot;. And even if you do, all you achieved is recording a trace with a custom config. Then what?</p>
<p>This would would be more interesting if you showed a concrete case of how clicking on a link actually causes dome data exfiltration (e.g. being able to send the recorded data somewhere else you own).</p>
<p>But as is, this bug is... not interesting at all, and not a bug frankly.</p>
