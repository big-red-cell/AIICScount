<p><strong>Expected Behavior:</strong></p>
<ul>
<li>Chrome should restrict supportedMethods values to verified, registered payment handlers.</li>
<li>Arbitrary HTTPS URLs (e.g., <a href="https://google.com/pay" data-b-widget="url" data-b-original-href="https://google.com/pay" data-b-redirected-href="https://www.google.com/url?q=https://google.com/pay&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3lCNJW7HCgO95I5gtA7mtg">https://google.com/pay</a>) should not render a spoofed payment UI.</li>
<li>The UI should clearly show both the initiating origin (attacker.com) and the payment handler origin.</li>
</ul>
<p><strong>Actual Behavior:</strong></p>
<ul>
<li>Chrome displays a spoofed UI that appears to come from Google Pay.</li>
<li>Users are misled into believing they are authorizing a legitimate Google Pay flow.</li>
</ul>
<p><strong>Impact:</strong></p>
<ul>
<li>
<p>Phishing / Fraud: Attackers can present a spoofed Google Pay (or any trusted PSP) payment UI to trick users into providing sensitive payment details.</p>
</li>
<li>
<p>Brand Misuse: Trusted brands’ payment flows can be impersonated, damaging user trust.</p>
</li>
<li>
<p>Financial Theft: Users may be misled into authorizing fraudulent transactions.</p>
</li>
<li>
<p>Wider Exploitation: Other payment handlers or third-party payment providers could also be spoofed in the same way.</p>
</li>
</ul>
<p><strong>Affected Version(s):</strong>
<strong>Product:</strong>
Google Chrome (PaymentRequest API implementation)</p>
<p><strong>Tested Version(s):</strong></p>
<ul>
<li>Chrome 140.0.7339.123</li>
<li>Android 15 (Build V2427, AP3A.240905.015.A2_NN_V000L1)</li>
</ul>
<p><strong>Mitigation:</strong></p>
<ol>
<li>
<p>Strict Origin Validation: Chrome should enforce that only pre-registered, verified payment handlers (e.g., Google Pay, Samsung Pay) can appear in supportedMethods. Arbitrary URLs must not be allowed.</p>
</li>
<li>
<p>UI Hardening: Ensure the Payment UI explicitly shows the origin of the requesting site in addition to the payment handler.</p>
</li>
<li>
<p>Deprecation of arbitrary HTTPS strings: Replace with a whitelist or a secure registration model.
User Education: Display clear warnings if the payment request is initiated by an unknown/unverified origin.</p>
</li>
<li>
<p>Patch Rollout: Fix should be backported to stable and extended to all Chromium forks.</p>
</li>
</ol>
<p><strong>Severity:</strong>
High — allows phishing and financial fraud with a spoofed trusted brand UI.</p>
<h1>Problem Description</h1>
<p>Summary:
A vulnerability in Chrome’s PaymentRequest API allows attackers to spoof trusted payment handlers such as Google Pay by supplying arbitrary supportedMethods values. This does not impact Google Pay’s backend, but it misleads users into believing they are engaging with a legitimate Google Pay payment flow, creating phishing and fraud risks.</p>
<p><strong>Description:</strong>
The PaymentRequest API accepts an array of payment instruments, each defined with a supportedMethods property. Chrome currently allows arbitrary HTTPS values here. When an attacker specifies supportedMethods: &quot;<a href="https://google.com/pay" data-b-widget="url" data-b-original-href="https://google.com/pay" data-b-redirected-href="https://www.google.com/url?q=https://google.com/pay&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3lCNJW7HCgO95I5gtA7mtg">https://google.com/pay</a>&quot;, the PaymentRequest dialog misleadingly presents itself as if the request is associated with Google Pay. In reality, the attacker’s site fully controls the flow.</p>
<h1>Additional Comments</h1>
<ul>
<li>Only Android version is affect iOS working fine.</li>
<li>This is a Chrome vulnerability, not a Google Pay vulnerability.</li>
<li>Google Pay’s backend is unaffected, but Chrome’s handling allows brand spoofing that undermines user trust in payment flows.</li>
</ul>
