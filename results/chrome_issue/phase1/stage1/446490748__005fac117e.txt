<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>In Chromium-based browsers, the file picker dialog from a previous origin can remain active even after the page has been redirected to a different origin. This behavior creates a misleading context for the user, who may believe the file picker originates from the redirected destination (e.g., Google.com), when in fact the upload target remains the original attacker-controlled site. The root issue appears to be that user activation is not properly invalidated upon navigation.</p>
<p><strong>Step to Reproduce:</strong></p>
<ol>
<li>navigate the link: <code>https://dosnet.my.id/picker.html</code> or open the picker.html</li>
<li>then click button</li>
<li>observe</li>
</ol>
<p><strong>Actual Result:</strong>
The file picker from the previous origin remains visible and functional even after redirecting to a new origin. The user may mistakenly attribute the file picker to the redirected site (e.g., Google.com) rather than the original attacker-controlled page.</p>
<p><strong>Expected result:</strong>
The file picker should be dismissed or the user activation invalidated once the page navigates to a different origin. This prevents confusing the user about which site is requesting file access.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>This issue enables a spoofing scenario. An attacker can trigger the file picker and then immediately redirect to a trusted site, making it appear as though the trusted site is requesting the file. This could trick users into uploading sensitive files under false assumptions, leading to information disclosure.</p>
