<h1>Problem Description</h1>
<p>#Summary
Assume a.com is loaded in the top-level context and embeds b.com in an iframe. When an auto-fillable input field inside the b.com page is focused, autofill suggestions for the embedding domain are shown instead.</p>
<p>This issue occurs in any browser that uses Chromium as its browser engine or an app that uses WebView to display web content, when an external password manager is used as the autofill service. I tried the following password managers: Avira Password Manager, Edge, Google password manager, LastPass, 1Password, Keeper, Roboform, Bitwarden, Keepass2Android, NordPass, and I found out that Avira Password Manager, Keeper, Roboform, Edge, NordPass, and Bitwarden are affected.</p>
<p>#Context
The Android autofill framework [AAF] acts as a bridge between apps and password managers and provides the latter with useful methods for fulfilling their goals (storing credentials, autofill). One of such methods is the onFillRequest, which is called by the AAF inside the AutofillService [AS] (the password manager) when an auto-fillable input field is focused, providing the context needed to the AS for providing correct suggestions. This information is represented in a tree structure (each node is of the AssistStructure.ViewNode type). This tree structure is created in the app context by spanning the View tree and calling the methods onProvideAutofillStructure and onProvideAutofillVirtualStructure on each view. The onProvideAutofillVirtualStructure method needs to be overridden by each custom View that wants to provide information to the autofill services. For example, a WebView is just a single View from the Android UI perspective, but to provide autofill capabilities, it implements the onProvideAutofillVirtualStructure method to parse the web content and send it in a structured way to the autofill service.</p>
<p>The root of the problem is that the WebView class implements the onProvideAutofillVirtualStructure in a way that contradicts the documentation. When an auto-fillable input field inside the embedded page is focused, the form is represented inside an AssistStructure.ViewNode node with the embedding domain as a field. This behavior contradicts the documentation, which says that ViewNodes for forms inside an iframe must use the iframe’s src as the domain. (<a href="https://developer.android.com/reference/android/webkit/WebView#onProvideAutofillVirtualStructure%28android.view.ViewStructure,%20int%29:~:text=Similarly%2C%20if%20the,the%20IFRAME%20node" data-b-widget="url" data-b-original-href="https://developer.android.com/reference/android/webkit/WebView#onProvideAutofillVirtualStructure%28android.view.ViewStructure,%20int%29:~:text=Similarly%2C%20if%20the,the%20IFRAME%20node" data-b-redirected-href="https://www.google.com/url?q=https://developer.android.com/reference/android/webkit/WebView%23onProvideAutofillVirtualStructure%2528android.view.ViewStructure,%2520int%2529:~:text%3DSimilarly%252C%2520if%2520the,the%2520IFRAME%2520node&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw36gG_DxKXugIrdMiQItm6h">https://developer.android.com/reference/android/webkit/WebView#onProvideAutofillVirtualStructure%28android.view.ViewStructure,%20int%29:~:text=Similarly%2C%20if%20the,the%20IFRAME%20node</a>).</p>
<p>This leads to password managers that rely on the information provided in the documentation to provide wrong autofill suggestions. Using this vulnerability, a malicious ad embedded in a benign website could lure the user to provide the benign website’s credentials to the malicious website.</p>
<h1>Additional Comments</h1>
<h1>Threat Model</h1>
<p>An attacker can embed a malicious iframe—such as through a malicious advertisement—inside an otherwise trusted webpage.
Confidentiality break: The ad resembles the trusted webpage’s login page. When a user interacts with form fields inside this cross-origin iframe, the Password Manager displays autofill suggestions containing credentials saved for the trusted site. Because users typically trust autofill prompts, they may unknowingly submit their legitimate credentials to the attacker-controlled iframe, enabling phishing attacks and credential theft.</p>
<p>Integrity Break: A malicious advertisement embeds hidden, prefilled form fields designed to trick the user into interacting with it by offering a reward. When the user clicks the ‘submit’ button, the password manager prompts to save credentials for the embedding domain. Additionally, the ad can employ fingerprinting or heuristic techniques to prefill fields with identifiers resembling the user’s real email, increasing the likelihood of successful deception.</p>

<h2>The sandbox attribute</h2>
<p>When the sandbox attribute is activated in an iframe, the nodes representing the fields in the tree structure have the string “null” as “webDomain”. This adds another layer of confusion to Password Managers. When a field in a sandboxed iframe is focused, some of them still suggest the embedding domain (like NordPass, Bitwarden, RoboForm), some of them do not provide any Autofill Suggestion, because they are searching for the “null”  “webDomain” (like 1Password, Google Password Manager, Keeper), while LastPass gives Autofill suggestions for the embedding domain when it was correctly displaying suggestion in the dev version.</p>
<h1>Baseline proposal for Credential Autofill in Iframes</h1>
<p>Here is a standardized way on how Password Autofill should work on Android when dealing with websites embedded in iframes.</p>
<ol>
<li>Autofill within iframes: Credential autofill should be supported within iframes, allowing password managers to provide credentials when an iframe is the active input context (even with a different origin).</li>
<li>Domain-matching enforcement: Credentials must only be autofilled for the domain that matches the focused field&#39;s domain.
Sandbox restrictions</li>
<li>Credentials must not be autofilled inside iframes that have the sandbox attribute. This prevents untrusted or restricted content from inadvertently receiving autofilled credentials.</li>
<li>No cross-origin one-tap autofill Cross-origin “one-tap” autofill (the feature implemented by desktop browser autofill to automatically fill card payment info when fields are split across different domains) should be disabled. Although disabling this feature introduces a minor usability cost—users must confirm autofill separately for each origin—it provides the possibility of cleaner data exchange: With one-tap disabled, the Autofill Framework only needs to exchange data relevant to the focused field’s origin rather than the entire form. This minimizes confusion, avoids over-sharing of form fields across domains, and reduces the chance of errors in password managers.</li>
</ol>
<p>##What can you do
What can you do as a browser developer to reach the baseline is to send the form fields that are siblings of the focused field. If the fields have different domains (like when there are payment providers involved), send only the ones with the same domain as the focused field.</p>

Author: Hi Riccardo,

Thank you for the report. Here's the current status of this:
- On WebView, there are no origin guarantees. That's because the WebView is running is in the process of the hosting app and can therefore be manipulated by it. Ultimately, the only information that a password manager can trust when coming from a WebView is the hosting app.
- On Chrome, we enforce origin guarantees when using Chrome's built-in password manager. When you switch to 3rd party password managers, there are no guarantees that Chrome can provide. We have recently started ([CL](https://chromium-review.googlesource.com/c/chromium/src/+/6810533), currently enabled as an experiment on 50% pre-stable and 1% stable channels) passing on information to the Android Autofill framework about the frames that a field is on, but whether 3rd party password managers make use of that information is up to them.

Author: Hi Jan,

Thanks for the feedback. Just for context, this report is part of a research project I am conducting at TU Wien together with Marco Squarcina (squarcina@gmail.com) and Philipp Beer (philipp.beer.6882@gmail.com). I would be grateful if you could CC them here.

> [...] whether 3rd party password managers make use of that information is up to them

We definitely agree with you on this. However, our empirical analysis shows that password managers are receiving conflicting signals from the browser, leading to incorrect autofill behavior. We summarize our findings and provide additional analysis below.

* On Chrome stable (Android), given a.com embedding b.com, when a form field inside b.com is focused, the browser sends to the autofill service a `ViewNode` object with the `webDomain` attribute set to `a.com`. The children of this object (which represent the form fields) have the `webDomain` attributes set to `null`. As a result, all password managers we tested (list password managers tested here) prompt credentials for a.com instead of b.com. This is a serious security issue that could lead to credential leaks. We are in touch with password manager vendors to discuss this issue.

* With the introduction of the AndroidAutofillForwardIframeOrigin feature,  the parent `ViewNode` (which represents the form) has the `webDomain` attribute set to `a.com`, while the children have the `webDomain` attribute set to `b.com`. Password managers now have sufficient information to correctly prompt credentials for b.com, although some of them still prompt credentials for a.com. Assuming our understanding is correct, we still think that this behavior is not ideal, because the form seems to be associated with a.com, while it's embedded in b.com. This could be puzzling for developers.

* Our guess is that password managers are confused by what stated in the [WebView](https://developer.android.com/reference/android/webkit/WebView#onProvideAutofillVirtualStructure(android.view.ViewStructure,%20int):~:text=Similarly%2C%20if%20the,the%20IFRAME%20node) and [AutoFillService](https://developer.android.com/reference/android/service/autofill/AutofillService#web-security:~:text=This%20same%20procedure%20could%20also%20be%20used%20when%20the%20autofillable%20data%20is%20contained%20inside%20an%20IFRAME%2C%20in%20which%20case%20the%20WebView%20generates%20a%20new%20autofill%20context%20when%20a%20node%20inside%20the%20IFRAME%20is%20focused%2C%20with%20the%20root%20node%20containing%20the%20IFRAME%27s%20src%20attribute%20on%20AssistStructure.ViewNode.getWebDomain()) documentation, where it is reported that

> [...] the web domain of the FORM contains the src attribute from the IFRAME node

and

> [...] when the autofillable data is contained inside an IFRAME, in which case the WebView generates a new autofill context when a node inside the IFRAME is focused, with the root node containing the IFRAME's src attribute on AssistStructure.ViewNode.getWebDomain()

Which does not correspond to our findings as reported above, neither on Chrome stable nor on Chrome dev (with the `AndroidAutofillForwardIframeOrigin` feature enabled).

We further reviewed the implementation of the AndroidAutofillForwardIframeOrigin feature and detected additional issues that, in our opinion, should be carefully considered.

* Given an embedding chain such as a.com -> b.com -> a.com (a setting that received attention in the implementation of state partitioning, see [Standardizing Security Semantics of Cross-Site Cookies - Same-Site Embeds with Cross-Site Ancestors (ABA embeds)](https://github.com/explainers-by-googlers/standardizing-cross-site-cookie-semantics?tab=readme-ov-file#same-site-embeds-with-cross-site-ancestors-aba-embeds)) with the inner a.com having some form fields, the structure sent to the autofill service only includes references to the topmost a.com and the innermost a.com, omitting b.com. This could be problematic for password managers that want to implement a strict same-site autofill policy.

* With an embedding such as a.com -> b.com, where b.com is an iframe with the `sandbox` attribute enabled, the `ViewNode` object representing the form has the `webDomain` set to `a.com`, while its children have it set to the string `"null"`. We did not find any reference to this behavior in the documentation. Again, this could be problematic for password managers that may 1) assume that the form fields belong to a.com, which is incorrect, or 2) assume that the origin is actually `"null"`, putting all opaque origins in the same bucket, sharing the same credentials cross-site. We noticed instances of both behaviors in the password managers we tested.

We would be happy to continue this discussion and provide any additional information to help improve the interaction between Chrome and password managers before the new feature is rolled out to stable. In parallel to this report, we are also investigating the behavior of Firefox on Android and plan to keep both parties (Chrome and Firefox) updated on our findings. Ideally, password managers should be able to rely on consistent and unambiguous signals from the browser to determine the correct origin to associate with form fields.

Cheers,
Riccardo, Marco, and Philipp
