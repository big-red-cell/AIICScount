<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>The TypedArray.prototype.at() method in V8 fails to enforce memory boundaries, allowing unauthorized memory access through negative indices. This violates ECMAScript specifications and compromises fundamental memory safety guarantees, potentially leading to information disclosure and security control bypass.</p>
<ol>
<li>Technical Details
Vulnerability Location
File: src/compiler/turboshaft/turbolev-graph-builder.cc (and equivalent Maglev compiler code)
Problematic Code Path:
<code>// In CheckTypedArrayBounds processing __ UintPtrLessThan(__ ChangeUint32ToUintPtr(Map(node-&gt;index_input())), Map(node-&gt;length_input()))</code>
Root Cause: The bounds checking logic incorrectly handles negative indices by:
Converting Uint32 indices to UintPtr without proper sign validation
Failing to throw RangeError for indices &lt; 0 as required by ECMAScript specification
Allowing memory access with calculated offsets that may read outside allocated bounds
ECMAScript Specification Violation
§23.2.3.2 %TypedArray%.prototype.at ( index ) explicitly requires:
Valid indices: 0 to length-1 → return element
Invalid indices (including negatives): MUST throw RangeError
Actual Behavior:
<code>const arr = new Uint8Array(100); arr.at(-1);  // → Returns 0 (SHOULD THROW RangeError) arr.at(-10); // → Returns 246 (SHOULD THROW RangeError) </code></li>
</ol>
<p>Affected Components
All TypedArray implementations:
Uint8Array, Int8Array, Uint16Array, Int16Array
Uint32Array, Int32Array, Float32Array, Float64Array
WebAssembly Memory arrays
Cryptographic API buffers using TypedArrays
SharedArrayBuffer with TypedArray views</p>
<ol start="2">
<li>Impact Analysis
Who Can Exploit
Any website visitor - No special privileges required
Malicious JavaScript in any context (main thread, workers, etc.)
Cross-origin attackers via embedded content
Exploitation Gains
Memory Disclosure: Read adjacent memory regions
Security Bypass: Circumvent bounds checking in security-sensitive code
Information Leakage: Potentially access sensitive data in process memory
Sandbox Weakening: Violate memory isolation guarantees
Demonstrated Security Impacts</li>
</ol>
<p>A. Security Validation Bypass
<code>class SecuritySystem { accessSensitiveData(index) { // This security check can be bypassed if (this.data.at(index) === undefined) { throw new Error(&quot;Security violation&quot;); } return this.data[index]; // Returns undefined for negative indices } } // EXPLOIT: system.accessSensitiveData(-1) → Bypasses check</code></p>
<p>B. WebAssembly Memory Access
<code>const memory = new WebAssembly.Memory({ initial: 1 }); const wasmArray = new Uint8Array(memory.buffer); wasmArray.at(-1); // → Accesses WebAssembly memory (should be isolated)</code></p>
<p>C. Cryptographic Data Exposure
<code>const keyMaterial = new Uint8Array(32); crypto.getRandomValues(keyMaterial); keyMaterial.at(-1); // → Can access cryptographic buffers</code></p>
<p>I am attaching some files. They are HTML files that can be opened using “google-chrome name.html.” They contain evidence of memory leaks, one global and the other showing random memory locations.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Exploitation Scenarios:
Security Validation Bypass:
Attackers can bypass bounds checks in security-sensitive code that uses .at() for validation
Example: if (sensitiveData.at(userInput) !== undefined) { return sensitiveData[userInput]; } can be bypassed with negative indices
Memory Disclosure:
Allows reading memory outside allocated TypedArray bounds
Potential information leakage from WebAssembly memory, cryptographic buffers, and adjacent heap objects
Sandbox Assumption Violation:
Compromises memory isolation guarantees between different execution contexts
Weakens security boundaries in sandboxed environments
Who Can Exploit:
Any website with JavaScript execution capabilities
No special privileges required
Works in standard web content without user interaction
What Attackers Gain:
Bypass input validation in security-sensitive applications
Potential information disclosure from process memory
Violation of memory safety guarantees
Compromise of security boundary assumptions
Severity: HIGH - Violates memory safety, enables security bypass, affects all Chrome platforms</p>
