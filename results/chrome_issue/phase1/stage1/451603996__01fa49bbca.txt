<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<h2>Executive Summary</h2>
<p>This report discloses a vulnerability in Chrome&#39;s &quot;Save to Google Drive&quot; feature, specifically in the ResumableDriveUploader class. The implementation fails to validate the origin/domain of the Location header in the HTTP response to the resumable upload initiation request. This allows a network-level attacker (e.g., via Man-in-the-Middle on a compromised Wi-Fi) to redirect subsequent file upload PUT requests to an attacker-controlled server, resulting in the exfiltration of arbitrary file contents (e.g., PDFs, documents) and, critically, the user&#39;s OAuth access token. The stolen token enables further escalation, such as enumerating, downloading, and modifying files in the victim&#39;s Google Drive, potentially leading to persistent access or malware injection.
No user interaction beyond initiating a &quot;Save to Google Drive&quot; action is required. The attack is stealthy, as the upload appears to succeed from the user&#39;s perspective. This affects all users of Chrome&#39;s built-in PDF viewer and &quot;Save to Drive&quot; integration.
A proof-of-concept (POC) using mitmproxy demonstrates full exfiltration of both file content and the authorization token.</p>
<h2>Vulnerability Description</h2>
<p>The ResumableDriveUploader class handles resumable uploads to Google Drive via the Drive API (v2/v3). The upload process begins with a POST request to <a href="https://www.googleapis.com/upload/drive/v%5B2%7C3%5D/files?uploadType=resumable" data-b-widget="url" data-b-original-href="https://www.googleapis.com/upload/drive/v%5B2%7C3%5D/files?uploadType=resumable" data-b-redirected-href="https://www.google.com/url?q=https://www.googleapis.com/upload/drive/v%255B2%257C3%255D/files?uploadType%3Dresumable&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3PBx-gvT2mssOAIcp1ywcT">https://www.googleapis.com/upload/drive/v[2|3]/files?uploadType=resumable</a> to initiate the session. Google responds with a 200 OK and a Location header containing a unique resumable upload URL (e.g., <a href="https://www.googleapis.com/upload/drive/v3/files?uploadType=resumable&amp;upload_id=" data-b-widget="url" data-b-original-href="https://www.googleapis.com/upload/drive/v3/files?uploadType=resumable&amp;upload_id=" data-b-redirected-href="https://www.google.com/url?q=https://www.googleapis.com/upload/drive/v3/files?uploadType%3Dresumable%26upload_id%3D&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3K7bgPpbOdCciDQCcgQsY9">https://www.googleapis.com/upload/drive/v3/files?uploadType=resumable&amp;upload_id=</a>...).
The class stores this URL in the upload_url_ member variable without validating its scheme (must be HTTPS), host (must be a Google domain like <a href="http://www.googleapis.com" data-b-widget="url" data-b-original-href="http://www.googleapis.com" data-b-redirected-href="https://www.google.com/url?q=http://www.googleapis.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2Bmf_G9ycUo257pq5tYjaV">www.googleapis.com</a>), or path. Subsequent PUT requests (for file chunks) are sent to this URL, including the user&#39;s OAuth Bearer token in the Authorization header.
An active network attacker can intercept the initiation response, replace the Location header with a malicious URL (e.g., <a href="http://attacker.com/exfil" data-b-widget="url" data-b-original-href="http://attacker.com/exfil" data-b-redirected-href="https://www.google.com/url?q=http://attacker.com/exfil&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw28SvAv5wbDyQfqn1H60X-w">http://attacker.com/exfil</a>), and forward the response. The browser then uploads the file to the attacker, leaking both the file contents and the token.
Root Cause Location:
The vulnerability stems from the HandleInitiationResponse method in resumable_drive_uploader.cc (implementation of the header-declared method), which assigns the Location header value directly to upload_url_ without domain/origin validation.</p>
<pre><code>// chrome/browser/save_to_drive/resumable_drive_uploader.h (excerpt)
class ResumableDriveUploader : public DriveUploader {
  // ...
 private:
  void HandleInitiationResponse(
      std::unique_ptr&lt;endpoint_fetcher::EndpointResponse&gt; response);
  // ...

  GURL upload_url_;  // Assigned without validation
  // ...
};
</code></pre>
<p>In HandleInitiationResponse (.cc file), the response&#39;s Location header is parsed into upload_url_ without checks like response.url.SchemeIs(&quot;https&quot;) or response.url.host() == &quot;www.googleapis.com&quot;.
This violates Chrome&#39;s general security principle of validating redirects and API responses, especially for sensitive operations like file uploads.</p>

<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<h2>Impact Analysis</h2>
<h2>Primary Impact: File Exfiltration</h2>
<p>Scope: Any file uploaded via &quot;Save to Google Drive&quot; (e.g., PDFs, images, docs) is fully leaked to the attacker.
Attack Vector: Requires network adjacency (e.g., malicious hotspot), but no authentication.
Real-World Risk: Users on public Wi-Fi (airports, cafes) uploading sensitive docs (e.g., tax forms, contracts) lose privacy.</p>
<h2>Escalated Impact: OAuth Token Theft and Account Compromise</h2>
<p>The POC captures the Authorization: Bearer <span>&lt;token&gt;</span> header from PUT requests, granting the attacker full Drive API access (scopes like drive.file or broader). This enables:</p>
<p>Enumeration/Download: List and steal all Drive files (GET /drive/v3/files).
Modification: Tamper with existing files (PATCH /drive/v3/files/{id}), e.g., inject JavaScript into PDFs for client-side RCE on reopen (via Adobe Reader exploits) or embed macros in Docs for malware persistence.
Persistence: Use the token to create backdoors (e.g., share folders with attacker accounts). If a refresh token is indirectly accessible, gain indefinite access.
Chained Attacks: Pivot to other Google services (Gmail, Photos) if scopes allow. Potential for ransomware (encrypt Drive files) or targeted phishing.</p>
<h2>Remediation Recommendations</h2>
<p>Immediate Fix: In HandleInitiationResponse (resumable_drive_uploader.cc):</p>
<pre><code>if (response &amp;&amp; response-&gt;status == 200) {
  GURL location = response-&gt;headers.GetHeader(&quot;Location&quot;);
  if (!location.is_valid() || !location.SchemeIs(&quot;https&quot;) ||
      (location.host() != &quot;www.googleapis.com&quot; &amp;&amp; location.host() != &quot;upload.googleapis.com&quot;)) {
    // Reject invalid URL (e.g., log error, abort upload)
    return;
  }
  upload_url_ = location;
}
</code></pre>
