<h1>Problem Description</h1>
<p>The DangerousDownloadDialog (the &quot;File might be harmful&quot; download confirmation) displays an origin string and filename that can be manipulated by controlled href/data: input when a download is initiated via an <span>&lt;a href=... download=...&gt;</span> click. Specifically:</p>
<ul>
<li>
<p>data: URLs and data: payload content (including URL-encoded text and literal ASCII content inside the data: value) are reflected into the download UI origin field without adequate validation or sanitization. This allows a malicious page to make the dialog display a trusted-looking origin (for example google.com) or otherwise obfuscate the true source of the file.</p>
</li>
<li>
<p>The dialog does not reliably show the true network origin for downloads initiated from data: URLs or when href contains crafted payloads; in some cases the origin is blank, in others it contains attacker-controlled strings. This is an information integrity / UI spoofing risk that can be used in social engineering attacks to trick users into accepting a dangerous download.</p>
</li>
<li>
<p>Additionally, there is insufficient input length validation for the origin/filename rendering logic. Providing a very long data: URL or very large base64 payload passed to the dialog caused the browser to crash or hang during my testing (observed renderer/browser instability). This indicates a potential denial-of-service vector and/or memory handling bug in the dialog rendering code.</p>
</li>
</ul>
<p>Observed behavior: UI displays attacker-controlled/malformed origin strings; in extreme cases the dialog or browser process crashes when given a very long data: payload.</p>
<p>Expected behavior: The download dialog should display a validated and canonical origin (e.g., the actual network origin host: <a href="https://rebelsec.id" data-b-widget="url" data-b-original-href="https://rebelsec.id" data-b-redirected-href="https://www.google.com/url?q=https://rebelsec.id&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw2XSGe12N3uS-ZwwYeBHuqd">https://rebelsec.id</a>) or display a clear, non‑spoofable placeholder for non-network-derived downloads (data:) — and the UI should never reflect raw untrusted payload contents as origin text. The dialog should also enforce reasonable maximum lengths on origin/filename fields and handle overly long inputs gracefully without crashing.</p>
<h1>Summary</h1>
<p>Download dialog origin spoofing and crash via crafted data: URLs / long base64 payload</p>
