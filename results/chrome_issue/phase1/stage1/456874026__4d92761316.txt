<li>From a victim-controlled navigation (onload or on click), the attacker-controlled origin initiates the redirect.</li>
<li>Browser opens the native mail client directly with no visible origin displayed in Chrome 142.0.7444.60 on macOS Tahoe 26.0.1.</li>
<li>(Contrast) Equivalent flows using <code>sms:</code>/<code>tel:</code> expose the origin URL in the browser UI. This leads to origin spoofing via server side redirects.</li>
</ol>
<h1>Problem Description</h1>
<ul>
<li>When a cross-origin page triggers native protocol handlers via a redirect chain, <code>sms:</code>/<code>tel:</code> show the originating URL in the browser UI, but <code>mailto:</code> does <strong>not</strong> — the browser immediately opens the mail client without displaying the origin, enabling origin spoofing.</li>
</ul>
<h2>Impact:</h2>
<ul>
<li>An attacker can cause the user&#39;s mail client to open while hiding the web origin that triggered it, enabling UI/identity spoofing and making phishing or social-engineering attacks more convincing.</li>
</ul>
<h2>Recommended remediation:</h2>
<ol>
<li>Treat <code>mailto:</code> like other external protocols: display the triggering origin URL or a clear origin prompt before invoking the native client.</li>
<li>If origin disclosure is not possible, require an explicit user gesture/confirmation dialog that includes the origin.</li>
<li>Add server-redirect provenance tracking for protocol handler launches and display the final visible origin consistently across protocols.</li>
<li>Short-term mitigation: restrict automatic server-redirect -&gt; protocol launches from cross-origin pages unless user-initiated.</li>
</ol>
