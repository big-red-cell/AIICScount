VULNERABILITY DETAILS:

I found a crafted PDF (js_injected_xss.pdf) that contains embedded JavaScript and executes automatically in Chrome’s built-in PDF viewer (PDFium). The payload runs in three ways I tested:

1. when the PDF is hosted and opened over HTTPS (remote)

2. when the same file is downloaded and opened locally (file://)

3. when the file is uploaded to Google Drive, downloaded from Drive, and then opened locally

In all three cases, the JavaScript executes immediately without user consent.
This shows that PDFium executes /OpenAction and /JavaScript objects embedded inside PDFs.
When served from a web origin, this results in arbitrary JavaScript execution within that origin’s context — effectively a stored cross-site scripting (XSS) vulnerability and Same-Origin Policy (SOP) bypass.

VERSION:
Chrome Version: 141.0.7390.123 
OS: Windows 11 Version 25H2 
JavaScript Engine: V8 14.1.146.11


REPRODUCTION CASE:

1. Hosted Proof of Concept (Remote Case):
https://vulnerabilityreports.net/js_injected_xss.pdf

2. Local Proof of Concept:
file://D:/downloads/js_injected_xss.pdf

3. Google Drive Reproduction:
The same PDF was uploaded to Google Drive, then downloaded and opened locally.
The alert('xss poc') executed immediately again, confirming the embedded script remains intact through Drive’s upload/download pipeline.

Steps to Reproduce:

1.Open the hosted URL above in Chrome.
2.Observe an alert box displaying xss poc.
3.Open DevTools → Console and check:
4.location.origin=https://vulnerabilityreports.net

Download the same file from Drive or directly, then open it locally (file://…).
The alert appears again as soon as the file opens.

Observed result:
Embedded JavaScript executes automatically in Chrome’s PDF viewer, both remotely and locally.
Expected result:
PDFium should never execute embedded JavaScript automatically.
All /JavaScript and /OpenAction actions should be ignored or executed only in a sandbox isolated from the browser’s origin context.
