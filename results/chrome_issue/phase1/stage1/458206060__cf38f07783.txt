<h1>Problem Description</h1>
<h2>Hi Team,</h2>
<ul>
<li>During my research on Chrome Browser Version 142.0.7444.48 for Android, I found a cross-origin ad/iframe chain was observed that resulted in an automatic top-level redirect without user interaction. The redirect was triggered from an iframe hosted on an attacker-controlled domain via window.open() and caused the publisher page to navigate to an external site (top level navigation).</li>
</ul>
<h2>Impact:</h2>
<ul>
<li>Automatic, silent redirection of users to external/malicious sites.</li>
<li>Bypasses browser popup/redirect protections and can be used in malvertising/phishing chains.</li>
<li>High potential for traffic funneling to malware or scam pages.</li>
</ul>
<h2>Expected behaviour:</h2>
<ul>
<li>Top-level navigation from sandboxed or cross-origin frames should be blocked unless initiated by an explicit user gesture or unless the full ancestor chain explicitly permits navigation.</li>
</ul>
<h2>Recommendation:</h2>
<ul>
<li>Implement ancestor-aware navigation checks similar to Chromium’s fix: ensure allow-top-navigation on a sandboxed iframe does not override restrictions imposed by ancestor frames and window.open.</li>
</ul>

<p>This seems to be working as intended. It&#39;s a bit hard to distinguish which navigation is which, but if you replace one of the <code>google.com</code> navigations in <code>Maliciousadd.html</code> with some other site, it&#39;ll become more clear what&#39;s happening.</p>
<p>Here&#39;s my understanding of what the repro is doing (with generic URLs to make it easier to follow):</p>
<ol>
<li>Navigate to an <code>A.com</code> page.</li>
<li>The <code>A.com</code> page embeds a <code>B.com</code> iframe.</li>
<li>The page in the <code>B.com</code> iframe embeds a <code>data:url</code> iframe.</li>
<li>The <code>data:url</code> iframe opens an <code>about:blank</code> popup window.</li>
<li>The <code>data:url</code> iframe attempts to navigate the <code>about:blank</code> popup window to <code>C.com</code>.
<ul>
<li>This succeeds. It&#39;s fine for popups to be navigated by their openers, and we don&#39;t subject those to user activation checks. It looks like it fails on desktop because <a href="https://google.com" data-b-widget="url" data-b-original-href="https://google.com" data-b-redirected-href="https://www.google.com/url?q=https://google.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw0VT8wnjtPCJ_ZzcGf2doE0">https://google.com</a> has some server-side policy related to being loaded in a popup window that is failing (Android opens popups in new tabs so this doesn&#39;t happen there). Loading something like <a href="https://example.com" data-b-widget="url" data-b-original-href="https://example.com" data-b-redirected-href="https://www.google.com/url?q=https://example.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw32_WZYagLX5XuNCw35Xw40">https://example.com</a> or <a href="https://something.com" data-b-widget="url" data-b-original-href="https://something.com" data-b-redirected-href="https://www.google.com/url?q=https://something.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3Bl8lZocSXsf-xqNmcJyzP">https://something.com</a> does result in a successful navigation.</li>
</ul>
</li>
<li>The <code>data:url</code> iframe attempts to do a top-level navigation to <code>D.com</code>.
<ul>
<li>That fails the framebusting checks with the following error: <code>The frame attempting to navigate the top-level window is cross-origin and either it or one of its ancestors is not allowed to navigate the top frame.</code> This is also expected.</li>
</ul>
</li>
</ol>
<p>After all of this, you&#39;ll be left with the following:</p>
<ul>
<li>an <code>A.com</code> page</li>
<li>a <code>B.com</code> iframe</li>
<li>a <code>data:url</code> iframe</li>
<li>a popup window navigated to <code>C.com</code></li>
</ul>
<p>The attempted navigation to <code>D.com</code> is stopped, which means the intervention is still working. The navigation to <code>C.com</code> is not part of the threat model for these interventions. If you look at the Android repro video at around 0:23, you&#39;ll see the publisher site was not navigated away, and instead the popup became the foreground tab and then <strong>that</strong> was navigated. If <code>A.com</code> had been successfully navigated away, then this would&#39;ve been a bug. But since <code>A.com</code> was untouched, everything seems to be working as expected.</p>
