<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Summary
Prerender/SpeculationRules activation leaves a short window where the prior same-origin document of a popup is still synchronously readable. This enables DOM-secret exfiltration (UXSS-like read). This is distinct from a plain cross-origin navigation race: the trigger here is prerender activation (e.g., pageswap), not location.href polling.
Environment
Chrome: [paste from chrome://version] (Stable; also tested Canary if available)
OS: Windows 11 24H2
Clean profile (--user-data-dir), no extensions/flags.
Expected
After a prerendered cross-origin page is activated, the opener must not be able to read the previous document at any time.
Actual
Immediately after activation, the opener can still read vic.document from the prior page and leak a secret string. I also observe pageswap firing with immediate readable DOM.
Steps to Reproduce
Serve two files on localhost:8000: target.html (secret in DOM) and attacker.html (below).
Open <a href="http://localhost:8000/attacker.html" data-b-widget="url" data-b-original-href="http://localhost:8000/attacker.html" data-b-redirected-href="https://www.google.com/url?q=http://localhost:8000/attacker.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1cZeypNwScvOBcP2Bfoziy">http://localhost:8000/attacker.html</a> in a clean Chrome profile.
Click Start.
Observe post-activation tight read =&gt; PWNED and/or pageswap fired — immediate read =&gt; PWNED.</p>

Observed result
On my machine: PWNED immediately after activation (and via pageswap), repeatedly.
Impact
Universal read across site boundaries following prerender activation, enabling token/PII exfiltration. Different subsystem (Prerender/SpeculationRules) from the previously reported cross-origin navigation race.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Who can exploit:
Any web attacker controlling a site the user visits (or a malicious ad/embedded widget) that can open a popup to a same-origin page, inject a speculationrules prerender for a cross-origin URL, and then trigger prerender activation.</p>
<p>What they gain:
A short window immediately after activation where the attacker can still synchronously read the prior document’s DOM in the popup (same-origin to attacker). This enables exfiltration of:
session/auth tokens and anti-CSRF nonces from the page,
private page content and PII visible in the DOM,
application state that should be isolated across sites.</p>
<p>Why this matters:
It is a Site-Isolation/SOP bypass caused by prerender activation, yielding universal read of data from a different site without extra user interaction beyond opening a popup.</p>
<p>Prerequisites &amp; scope:
One user gesture to open the popup; default Chrome settings; no extensions/flags.
Affects any site rendered in the popup if a cross-origin prerender is activated.
Security impact (concise):
Account takeover and data theft are feasible via DOM secret leakage during the activation window.</p>

Author: *Subject:* Re: Issue 458227149 — Clarification on impact
(prerender/activation prior-document read)

Hi *[team]*,

Thanks for the quick review. I agree my earlier wording ("universal read
across site boundaries") was too strong. The PoC demonstrates a
*same-origin* condition: immediately after prerender activation, the *prior
document remains readable for a short window*, allowing DOM state (tokens
in the page, user-specific content, etc.) to be read before it's fully torn
down.

While this is not cross-origin, it can still be *security-relevant in
multi-tenant same-origin setups* (e.g., shared hostnames, user areas under
the same origin, or flows where a prerendered page inherits authenticated
state). In those cases, residual DOM reads during activation can expose
sensitive, per-user data within the same origin boundary.

If this is considered "Intended Behavior," could you please confirm whether:

   1.

   The transient read window after activation is expected by design, and
   2.

   There is any recommended mitigation (e.g., ensuring prior document is
   fully cleared/hidden before activation completes, or a spec note for sites
   that rely on prerender + auth)?

I can attach a minimal repro with precise timing (DevTools timeline +
video) showing the read window if helpful.

Thanks,
Yuval Fradkin
