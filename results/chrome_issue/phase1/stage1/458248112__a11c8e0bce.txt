<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Summary
Notifications permission prompt misattribution. A popup is opened on localhost, which triggers the Notifications permission prompt. While the prompt is pending, the popup is navigated to 127.0.0.1. Pressing Allow grants the permission to 127.0.0.1 (attacker origin) instead of the original localhost that initiated the prompt. Minimal localhost PoC reliably reproduces.</p>
<p>Environment
Chrome 142.0.7444.60 (Stable), Windows 11 24H2 (Build 26100.689)
Clean profile (--user-data-dir), no extensions/flags
Expected
The permission decision must be attributed to the origin that initiated the prompt (localhost), or the prompt should be cancelled on navigation.</p>
<p>Actual
After navigating the prompt-holding popup to 127.0.0.1, pressing Allow results in Notification.permission === &quot;granted&quot; on the attacker origin (127.0.0.1). Page log shows:
after: Notification.permission on attacker = granted ⇒ MISATTRIBUTION (PWNED).</p>

Serve these two files on 127.0.0.1:8000.
Open <a href="http://127.0.0.1:8000/attacker_perm.html" data-b-widget="url" data-b-original-href="http://127.0.0.1:8000/attacker_perm.html" data-b-redirected-href="https://www.google.com/url?q=http://127.0.0.1:8000/attacker_perm.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1dsDLY3hYUUmVIUVBXMfXe">http://127.0.0.1:8000/attacker_perm.html</a> in a clean Chrome profile.

A popup to <a href="http://localhost:8000/perm_victim.html" data-b-widget="url" data-b-original-href="http://localhost:8000/perm_victim.html" data-b-redirected-href="https://www.google.com/url?q=http://localhost:8000/perm_victim.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw3gIyFIAHazCK-66RqBvJQb">http://localhost:8000/perm_victim.html</a> will request Notifications after ~700ms.</p>

<p>Impact
Permissions Bypass / Security UI misattribution. An attacker origin can obtain Notifications permission (and potentially other prompt-based permissions under similar flows) by racing a cross-origin navigation during the prompt, enabling unwanted notification spam and erosion of the origin security model.</p>
<h4>Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so</h4>
<p>Who can exploit: Any web attacker controlling a site the user visits (or a malicious ad/widget) that can open a popup and trigger a Notifications prompt.</p>
<p>What they gain: By navigating the prompt-holding popup to a different origin mid-prompt, the attacker’s origin receives Notifications permission. This enables unsolicited notification spam, social-engineering, and abuse of trust (permission appears to belong to the attacker’s site).</p>
<p>Why it matters: This is a Permissions Bypass / Security UI misattribution that breaks the origin attribution model for browser prompts.</p>

Author: Thanks for the update. Clarification: http://localhost and http://127.0.0.1
are *different hosts* and therefore *different origins* (origin = scheme +
host + port). Notification permissions are origin-scoped.

In my PoC, a popup opens on localhost and is immediately navigated to
127.0.0.1. Clicking *Allow* ends up granting the permission to 127.0.0.1,
even though the user interaction was initiated by localhost. This
creates a *permission
laundering / confused-deputy* situation: the requesting UI is presented by
one origin while the grant is recorded for another origin after navigation.

Could you please confirm whether Chrome intentionally binds the permission
to the origin *at the moment of the click* (after navigation) rather than
to the origin that *initiated* the request? If this is by spec, I'd
appreciate a precise reference. If not, consider:

   1.

   Binding the grant to the origin that initiated the request; or
   2.

   Freezing navigation of the requesting window while the prompt is open; or
   3.

   Updating the prompt to clearly show the *exact origin* that will receive
   the permission at click time.

*Notes:*

   -

   While both hosts resolve to loopback, they can front different local
   services; the risk is primarily *UX/permission misattribution*, not
   cross-network compromise.
   -

   The essence here is preventing user confusion and ensuring origin
   integrity for permission grants.
