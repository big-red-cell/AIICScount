### Report description


Responses with Content-Type: video/mp4 and the mp4 extension are processed by the mediostream as M3U; the browser automatically requests the URLs specified in the playlist.


---

### Bug location


#### Where do you want to report your vulnerability?

Chrome VRP – Report security issues affecting the Chrome browser. [See program rules](https://bughunters.google.com/about/rules/5745167867576320/chrome-vulnerability-reward-program-rules)


---

### The problem


#### Please describe the technical details of the vulnerability

1. Host the following content at https://victim.com/asd.mp4 with header Content-Type: video/mp4:
```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:1
#EXTINF:1,
/api/test
#EXT-X-ENDLIST
```
> Relative path /api/test intentionally points to https://victim.com/api/test.

2. Open a page that loads the file via `<video>` (e.g. a simple PoC page or any page on the site that references https://victim.com/asd.mp4):
```
<video src="https://victim.com/asd.mp4" autoplay muted playsinline></video>
```

3. In Chrome DevTools → Network, filter by api/test and observe that the browser first requests asd.mp4, then automatically issues a GET request to https://victim.com/api/test with authentication cookies attached.


#### Impact analysis – Please briefly explain who can exploit the vulnerability, and what they gain when doing so

An attacker can force the victim's browser to perform authenticated GET requests via the `<video>` element. A URL that is expected to be an MP4 file (`.mp4`, `Content-Type: video/mp4`) can return an #EXTM3U playlist instead. Chrome then follows the playlist entries and issues same-site subrequests with cookies, creating a CSRF vector for any state-changing GET endpoint.
