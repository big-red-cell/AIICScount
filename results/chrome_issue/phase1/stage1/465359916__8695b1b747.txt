<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Following my previous submissions, which demonstrated multiple unintended ways a synced passkey can be abused for account takeover, including:</p>
<ol>
<li><strong>Leaking the Security Domain Secret (SDS)</strong> and using it to decrypt the synced passkey secret and generate valid assertions</li>
<li><strong>Registering an attacker-controlled UV key</strong> to obtain Cloud Authenticator user-verified assertions</li>
<li><strong>Silently using the victim’s identity key</strong> to produce Cloud-Authenticator-authenticated requests</li>
</ol>
<p>This report highlights a design gap that prevents Chrome, the Cloud Authenticator, and relying parties from detecting these abuses. Chrome’s synced passkey implementation does <strong>not</strong> use the existing WebAuthn signature-counter mechanism (<code>signCount</code>). Every synced-passkey assertion returns an authenticator data structure where <code>signCount</code> is always <strong>zero</strong>.</p>
<p>If Chrome used a proper signature counter, these types of unauthorized or unexpected credential uses could be detected and blocked by:</p>
<ul>
<li><strong>The Cloud Authenticator</strong></li>
<li><strong>Security domain members</strong></li>
<li><strong>Relying parties</strong></li>
</ul>
<p>The absence of a functioning signature counter removes an important WebAuthn safeguard that would otherwise help contain or prevent the previously reported attacks.</p>
<p><strong>Recommendation</strong></p>
<p>Add a signature counter to the synced passkey record (<code>WebauthnCredentialSpecifics</code>) and increment it by one for every assertion. This counter should then be included in the authenticator data returned to relying parties, allowing Chrome, the Cloud Authenticator, and RPs to detect abused or abnormal credential usage.</p>
<h4>Impact analysis</h4>
<p>Without a functioning signature counter, Chrome, the Cloud Authenticator, and relying parties cannot detect decrepted, abused, or abnormal use of synced passkeys, allowing attackers to authenticate as the victim without any visibility or safeguards.</p>

Author: ke...@chromium.org
<p>Apologies for the slow response on these issues.</p>
<p><a href="https://issues.chromium.org/issues/465359916#comment2" data-b-widget="issue-reference" data-b-issue-id="465359916" data-b-comment-number="2">Comment #2</a> is correct, syncing makes this impractical, aside from the general concerns over the usefulness of signature counters that agl points out in his blog.</p>
<p>If a user uses a GPM passkey on a desktop PC to sign in to a site, and then uses the same passkey on the same site or associated app on a phone, the site would see a non-increasing signature count on successive assertions. The signature counter could be propagated between devices in the sync data, but the potential problem would always be a race with the syncing mechanism.</p>
<p>This is not something we will implement.</p>
