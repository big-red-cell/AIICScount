<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>The current implementation of crypto.subtle.encrypt using the AES-GCM algorithm in Chromium/V8 is overly permissive regarding the length of the Initialization Vector (IV).</p>
<p>The browser successfully processes encryption requests using an 8-byte (64-bit) IV, returning a ciphertext without any warning or error.</p>
<p>While generic GCM allows variable IV lengths, modern security standards for GCM (specifically RFC 5116 Section 5.1 and NIST SP 800-38D) strongly mandate or recommend using a 96-bit (12-byte) IV.</p>
<p>Using non-96-bit IVs forces the GCM algorithm to process the IV via the GHASH function (multiplier path) instead of directly using it with the counter. This drastically increases the probability of IV/Nonce Collisions. In GCM, a nonce collision with the same key is catastrophic, potentially leading to the loss of confidentiality (plaintext recovery) and integrity (forgery).</p>
<p>References:</p>
<pre><code>RFC 5116 Sec 5.1: &quot;The nonce_len is 12 octets.&quot;

NIST SP 800-38D: Recommends restricting support to 96-bit IVs to promote interoperability and efficiency.
</code></pre>
<p>Steps to Reproduce</p>
<pre><code>Save the attached Proof of Concept file (aes_gcm_report.html) locally.

Open the file in the latest stable version of Chrome.

Click the &quot;Run Exploit Test&quot; button.

Observe the output in the on-screen console.
</code></pre>
<p>Expected Behavior (Secure): The browser should throw an OperationError or NotSupportedError, rejecting the 8-byte IV.</p>
<p>Actual Behavior (Vulnerable): The browser accepts the 8-byte IV and successfully generates ciphertext and an authentication tag.</p>
<h4>Impact analysis</h4>
<p>This is a security hardening issue. While it does not allow immediate RCE or UXSS, it weakens the cryptographic guarantees of web applications using AES-GCM via WebCrypto. It allows developers to deploy insecure crypto implementations that are prone to nonce collisions.</p>
