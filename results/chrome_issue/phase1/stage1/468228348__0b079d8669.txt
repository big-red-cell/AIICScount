<h1>Steps to reproduce the problem</h1>
<ol>
<li>Open the following URL on iOS: <a href="https://fake-google-subdomain-page-for-phishing.github.io/test/test.apk" data-b-widget="url" data-b-original-href="https://fake-google-subdomain-page-for-phishing.github.io/test/test.apk" data-b-redirected-href="https://www.google.com/url?q=https://fake-google-subdomain-page-for-phishing.github.io/test/test.apk&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw36MdroOYJCOllrXYLJ-3m-">https://fake-google-subdomain-page-for-phishing.github.io/test/test.apk</a></li>
<li>Trigger the file download from the page.</li>
<li>Open the browser’s Downloads UI (download bar / downloads page).</li>
<li>Observe the displayed download source/origin text.</li>
</ol>
<h1>Problem Description</h1>
<p>Expected Result</p>
<ul>
<li>The Downloads UI always prominently displays the registrable domain (TLD+1), e.g. github.io.</li>
<li>If truncation is required, the UI preserves and shows the end of the hostname (e.g. …github.io) or otherwise clearly indicates the real origin.</li>
</ul>
<p>Actual Result</p>
<ul>
<li>The Downloads UI truncates the hostname from the leading side.</li>
<li>The registrable domain (TLD+1) is omitted or hidden.</li>
<li>A long attacker-controlled subdomain prefix is shown instead, creating a misleading trust signal about the file’s true origin.</li>
</ul>
<h1>Summary</h1>
<p>Download UI truncates origin, hides real TLD+1, allowing long subdomain spoofing that misleads users</p>
