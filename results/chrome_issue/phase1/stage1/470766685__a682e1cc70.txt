<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Bypass or Similar to: <a href="https://issues.chromium.org/issues/40066643" data-b-widget="issue-reference" data-b-issue-id="40066643">https://issues.chromium.org/issues/40066643</a></p>
<p><strong>Problem:</strong></p>
<p>Popup opened with about:blank (address bar remains about:blank). When cross-origin HTML (e.g., from <a href="https://permission.site" data-b-widget="url" data-b-original-href="https://permission.site" data-b-redirected-href="https://www.google.com/url?q=https://permission.site&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw28UjpAeWMtxTw3PO3a7RDh">https://permission.site</a>) is fetched and injected via document.write(), the popup&#39;s execution context inherits the opener&#39;s origin.</p>
<p><strong>Result:</strong></p>
<p>Notification.requestPermission() prompt displays the main window&#39;s domain (opener origin) instead of the actual content&#39;s origin (permission.site).
This misleads users into thinking the permission request comes from the trusted main site, not the embedded third-party content.</p>
<p><strong>Proof Of Concept:</strong></p>
<ol>
<li>Open the page and click the button.</li>
<li>Popup opens with URL bar about:blank.</li>
<li>If fetch succeeds (use CORS-enabled site for full repro; fallback uses iframe with correct origin).</li>
<li>In popup, trigger notification request (via permission.site tools).</li>
<li>Observe prompt: Shows &quot;yourdomain.com wants to show notifications&quot; (or similar opener domain), not &quot;permission.site&quot;.</li>
</ol>
