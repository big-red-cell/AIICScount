<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p><strong>Steps to Reproduce</strong></p>
<ol>
<li>Log in to a valid user account.</li>
<li>Navigate to the Change Password functionality.</li>
<li>Observe that the application does not ask for the current password.</li>
<li>Enter a new password and submit the form.</li>
<li>The password is successfully changed without any verification of the current password.</li>
</ol>
<h4>Impact analysis</h4>
<h2>Impact</h2>
<ul>
<li>An attacker who gains access to an authenticated session (via XSS, CSRF, or session hijacking) can:
<ul>
<li>Change the victim’s password</li>
<li>Permanently lock the legitimate user out</li>
</ul>
</li>
<li>Leads to <strong>Account Takeover (ATO)</strong></li>
<li>Weakens overall account security posture</li>
</ul>
<h2>One-Line Impact Statement</h2>
<p>An authenticated user can change their account password without verifying the current password, enabling account takeover.</p>

Author: Hello Security Team,

Thank you for reviewing the report.

I understand that Google may rely on recent re-authentication instead of
explicitly requesting the current password during password changes. My
observation was based on the absence of a current password prompt in the UI
during the change-password flow.

If this behavior is considered intended due to prior re-authentication or
session freshness, please feel free to mark the issue accordingly.

Thank you for your time and for maintaining Google's security standards.
