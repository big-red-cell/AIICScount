<p>Hello tim</p>
<p>Thanks for the clarification.</p>
<p>The core security issue is not event ordering itself, but trusted input routing being re-enabled before a privileged fullscreen exit transition has fully completed.</p>
<p>Fullscreen is a privileged UI state with a security invariant: trusted user input should not be delivered to page-level content until the fullscreen exit is fully committed (UI state reset, focus restoration, and hit-testing stabilization).</p>
<p>In Chromium, during fullscreen exit, document.fullscreenElement is already null, yet trusted mouse events are dispatched to page-level listeners before the fullscreen exit lifecycle completes (i.e., before fullscreenchange(EXIT) fully settles).</p>
<p>This creates a window where web content can receive trusted input while the browser is still transitioning out of a privileged UI mode. That window should not exist.</p>
<p>This matters because fullscreen exit is a user safety gesture (ESC). Allowing trusted input to reach web content before the exit is fully committed weakens the input integrity boundary of fullscreen and enables input capture during a privileged UI transition.</p>
<p>This is observable using only standard APIs (no synthetic events or DOM tricks) and differs from Firefox, which resumes trusted input only after fullscreen exit has completed.</p>
<p>From a security perspective, this is best understood as an input integrity violation during a privileged UI transition, rather than a UX or JS-level issue.</p>

<p>Hi</p>
<p>Thanks for the follow-up — that’s a fair question.</p>
<p>I agree that once fullscreen content is no longer visible, input will eventually need to be routed back to the page. The concern here is not that input is routed back, but when it is routed back relative to the fullscreen exit lifecycle.</p>
<p>The boundary I’m referring to is the privileged fullscreen exit transition itself. Fullscreen exit is initiated by a security-sensitive user action (ESC) and involves coordinated changes across visibility, focus, hit-testing, and gesture attribution.</p>
<p>In Chromium, there is a window where document.fullscreenElement is already null, but the fullscreen exit transition has not yet fully settled, and trusted mouse events are dispatched to page-level listeners.</p>
<p>This creates a temporal gap where trusted input is delivered while the browser is still transitioning out of a privileged UI mode. That gap should ideally not exist.</p>
<p>The concrete risk is not a direct exploit, but a weakening of input integrity and user intent attribution during a privileged UI transition. Small timing windows like this can lead to state ambiguity, especially for features that rely on precise gesture handling.</p>
<p>Firefox defers trusted input delivery until after fullscreen exit has completed, which suggests this behavior is avoidable and not required by the platform.</p>
<p>If this behavior is intended, it may be worth documenting explicitly. Otherwise, deferring trusted input dispatch until the exit transition is fully committed would close this gap.</p>
<p>Thanks again for taking a look — happy to clarify further if helpful.</p>
