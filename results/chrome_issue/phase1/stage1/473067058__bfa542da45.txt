<h1>Steps to reproduce the problem</h1>
<ol>
<li>Enable <strong>Split View / side-by-side tabs</strong> flag in Chrome (<code>chrome://flags/#side-by-side</code>).</li>
<li>Open a website that triggers an <strong>Install App prompt</strong> in the first tab (<code>Tab A</code>) <a href="https://rebelsec.id/app/" data-b-widget="url" data-b-original-href="https://rebelsec.id/app/" data-b-redirected-href="https://www.google.com/url?q=https://rebelsec.id/app/&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw33cQodntiG5LR69jaWmmGZ">https://rebelsec.id/app/</a>.</li>
<li>While the prompt is visible, switch to a second tab (<code>Tab B</code>) in the Split View layout.</li>
<li>Observe that the <strong>address bar updates</strong> to reflect <code>Tab B</code>’s URL, but the <strong>Install App prompt from Tab A remains visible</strong>.</li>
<li>Interact with the prompt. The modal origin differs from the currently displayed URL in the omnibox.</li>
<li>Confirm that this behavior is <strong>different from standard permission requests</strong>, where notifications are correctly dismissed when switching tabs.</li>
</ol>
<h1>Problem Description</h1>
<p>In Split View mode, the <strong>Install App prompt modal</strong> remains <strong>active on screen</strong> even after switching to another tab. While the <strong>omnibox updates</strong> to show the URL of the newly active tab, the modal still belongs to the original tab.</p>
<p>This creates a <strong>visual mismatch between the displayed URL and the modal origin</strong>, potentially misleading users to approve app installations believing the action is associated with the active tab.</p>
<p>Notably, this is <strong>different from standard permission requests</strong> (e.g., location/notification), which are correctly dismissed when switching tabs. This indicates inconsistent handling of different modal types.</p>
<p>This behavior aligns with discussions in <a href="https://issues.chromium.org/issues/422176169" data-b-widget="issue-reference" data-b-issue-id="422176169">422176169</a> regarding modal dialogs needing to be associated with their originating tab, and <a href="https://issues.chromium.org/issues/440523110" data-b-widget="issue-reference" data-b-issue-id="440523110">440523110</a> discussing user confusion from UI inconsistencies in Split View.</p>

<p>Yes, the distinction here from the permission prompt case is that the permission prompt is anchored to the page info icon in the omnibox, while the PWA install dialog is tab modal and anchored to the tab itself.</p>
<p>This is also further mitigated by the fact that the user has to (1) trigger the PWA install dialog while that tab is active, and then (2) manually change tabs to the other tab. This combines to make it hard to see how a reasonable and prudent could be tricked by this (see <a href="https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/faq.md#What-makes-a-UI-spoof-interesting-to-report" data-b-widget="url" data-b-original-href="https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/faq.md#What-makes-a-UI-spoof-interesting-to-report" data-b-redirected-href="https://www.google.com/url?q=https://chromium.googlesource.com/chromium/src/%2B/HEAD/docs/security/faq.md%23What-makes-a-UI-spoof-interesting-to-report&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1vXggzer5JDTPd-59wn49h">https://chromium.googlesource.com/chromium/src/+/HEAD/docs/security/faq.md#What-makes-a-UI-spoof-interesting-to-report</a>).</p>
