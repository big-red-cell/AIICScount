<h1>Steps to reproduce the problem</h1>
<ol>
<li>Enable <strong>Split View</strong> via <code>chrome://flags/#side-by-side</code>.</li>
<li>Open <strong>Tab A</strong> with a page containing a link that triggers a modal or interactive flow (e.g., a form page).</li>
<li>Right-click the link and select <strong>“Open Link”</strong>; the modal opens, but the <strong>omnibox still shows Tab A’s URL</strong> while the modal is technically in Tab B.</li>
<li>Interact with the modal; observe that the <strong>visible URL does not match the origin of the interactive content</strong>.</li>
</ol>
<h1>Problem Description</h1>
<p>In Split View, Chrome can display a modal or interactive content from one tab while the <strong>omnibox shows the URL of another tab</strong>, creating a <strong>mismatch between the visible origin and the actual content source</strong>.</p>
<p>This mismatch can <strong>mislead users to trust a different origin</strong>, potentially allowing <strong>UI spoofing</strong>. Standard permission prompts are correctly dismissed or scoped when switching tabs, indicating <strong>inconsistent handling of certain modals in Split View</strong>.</p>
<p>The issue represents a <strong>security concern</strong> because browser UI indicators no longer reliably reflect the true origin of active content.</p>
<p>This behavior aligns with discussions in <a href="https://issues.chromium.org/issues/422176169" data-b-widget="issue-reference" data-b-issue-id="422176169">422176169</a> regarding modal dialogs needing to be associated with their originating tab, and <a href="https://issues.chromium.org/issues/440523110" data-b-widget="issue-reference" data-b-issue-id="440523110">440523110</a> discussing user confusion from UI inconsistencies in Split View.</p>
