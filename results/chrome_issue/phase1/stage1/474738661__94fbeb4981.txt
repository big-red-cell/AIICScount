<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<h1>Permissions Policy Enforcement Issue: local-network-access overrides explicit loopback-network &#39;none&#39;</h1>
<h2>Summary</h2>
<p>A permission policy bypass in Chrome&#39;s Local Network Access split permissions feature (enabled by default since December 2025) allows iframes to access localhost even when the embedding page explicitly denies <code>loopback-network</code> permission policy. The backwards compatibility implementation for the old <code>local-network-access</code> permission policy name overrides explicit denials of the new split permissions (<code>local-network</code> and <code>loopback-network</code>).</p>
<h2>Impact</h2>
<p><strong>Impact</strong> : Permission Policy Bypass enabling attacks for localhost access</p>
<p><strong>Current Impact</strong>: Pre-release (trunk/ASAN builds), Canary and Release</p>
<p>Versions tested:
Version 143.0.7499.193 (Official Build) (arm64)
Version 145.0.7625.0 (Official Build) canary (arm64)
Chromium 145.0.7626.0 (Developer Build) (arm64) ASAN</p>
<p><strong>What is bypassed:</strong></p>
<ul>
<li>✅ <strong>Permission Policy</strong> - Parent site&#39;s Permissions Policy restrictions are not enforced as expected</li>
<li>✅ <strong>Tested from public HTTPS origin</strong> - Real-world attack scenario confirmed</li>
</ul>
<p><strong>User interaction required:</strong></p>
<ul>
<li>⚠️ User must click &quot;Allow&quot; on permission prompt</li>
<li>The vulnerability is that the prompt <strong>should not appear at all</strong> with <code>loopback-network &#39;none&#39;</code></li>
</ul>
<p><strong>Example scenario:</strong></p>
<ol>
<li>A third-party iframe is embedded with <code>allow=&quot;local-network-access; loopback-network &#39;none&#39;&quot;</code></li>
<li>Parent site intends to block localhost access via permission policy</li>
<li><strong>BUG</strong>: Iframe overrides policy using old <code>local-network-access</code> syntax</li>
<li>Chrome shows permission prompt (should have been silently blocked)</li>
<li>User clicks &quot;Allow&quot; on the Local Network Access permission prompt</li>
<li>Iframe accesses localhost services (dev servers, databases, internal APIs)</li>
</ol>
<p><strong>Security Impact:</strong></p>
<ul>
<li>Parent sites cannot enforce permission policies on iframes</li>
<li>Permission Policy security boundary is broken</li>
<li>Allows network requests to localhost despite explicit policy denial</li>
<li>Attack vector for localhost access</li>
</ul>

<h2>Root Cause Analysis</h2>
<p>In <code>services/network/public/cpp/permissions_policy/permissions_policy.cc</code> lines 467-478:</p>
<pre><code><span class="stx-keyword">if</span> (base::FeatureList::IsEnabled(
        features::kLocalNetworkAccessChecksSplitPermissions)) {
  <span class="stx-keyword">if</span> (feature ==
      <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::kLocalNetworkAccess) {
    allow_lists_and_reporting_endpoints.allowlists_.emplace(
        <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLocalNetwork</span>,
        <span class="stx-qualifier">Allowlist</span>::FromDeclaration(<span>parsed_declaration</span>));
    allow_lists_and_reporting_endpoints.allowlists_.emplace(
        <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLoopbackNetwork</span>,
        <span class="stx-qualifier">Allowlist</span>::FromDeclaration(<span>parsed_declaration</span>));
  }
}
</code></pre>
<p><strong>Observed behavior</strong>:</p>
<ul>
<li><code>emplace()</code> only inserts if the key doesn&#39;t already exist</li>
<li>When parsing <code>allow=&quot;local-network-access; loopback-network &#39;none&#39;&quot;</code>:
<ol>
<li>Parser sees <code>local-network-access</code> first</li>
<li>Calls <code>emplace()</code> for both <code>kLocalNetwork</code> and <code>kLoopbackNetwork</code> with the <code>local-network-access</code> allowlist</li>
<li>Parser then sees <code>loopback-network &#39;none&#39;</code></li>
<li>Tries to <code>emplace()</code> but <strong>fails silently</strong> because key already exists</li>
<li>The explicit denial is <strong>completely ignored</strong></li>
</ol>
</li>
</ul>
<p><strong>This also violates the documented behavior</strong> in the code comments (lines 459-466) which state that declaration order should matter, but the first <code>local-network-access</code> always wins regardless of order.</p>
<h2>Attack Scenario</h2>
<p><strong>Example: Bank embedding third-party analytics widget</strong></p>
<pre><code><span class="stx-comment">&lt;!-- Bank site (example.com) embeds analytics widget --&gt;</span>
&lt;<span class="stx-keyword">iframe</span> src=<span class="stx-string">&quot;https://analytics-widget.com&quot;</span>
        allow=<span class="stx-string">&quot;loopback-network &#39;none&#39;&quot;</span>&gt;
&lt;/<span class="stx-keyword">iframe</span>&gt;
</code></pre>
<p><strong>Developer&#39;s Intent</strong>: Block the analytics widget from accessing user&#39;s localhost</p>
<p><strong>What SHOULD happen</strong>:</p>
<ul>
<li>Browser enforces <code>loopback-network &#39;none&#39;</code></li>
<li>Widget cannot even prompt user (silently blocked)</li>
<li>User&#39;s localhost is protected</li>
</ul>
<p><strong>What ACTUALLY happens (the bug)</strong>:</p>
<ol>
<li>Chrome&#39;s permission policy parser fails to enforce the <code>&#39;none&#39;</code> denial</li>
<li><code>allowsFeature(&#39;loopback-network&#39;)</code> returns <code>true</code> (should be <code>false</code>)</li>
<li>Widget can prompt user for localhost access (should be impossible)</li>
<li>User sees popup and clicks &quot;Allow&quot;</li>
<li>Widget accesses localhost services (dev servers, databases, internal APIs)</li>
</ol>
<p><strong>Result</strong>: Parent site&#39;s Permissions Policy denial does not take effect in this configuration.</p>
<h2>Suggested Fix</h2>
<p>Replace <code>emplace()</code> with <code>insert_or_assign()</code> or check if the new permissions are already explicitly declared before applying backwards compatibility:</p>
<pre><code><span class="stx-comment">// Check if new permissions were explicitly declared</span>
<span class="stx-keyword">bool</span> <span>has_explicit_local</span> =
    allow_lists_and_reporting_endpoints.allowlists_.contains(
        <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLocalNetwork</span>);
<span class="stx-keyword">bool</span> <span>has_explicit_loopback</span> =
    allow_lists_and_reporting_endpoints.allowlists_.contains(
        <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLoopbackNetwork</span>);

<span class="stx-keyword">if</span> (!has_explicit_local) {
  allow_lists_and_reporting_endpoints.allowlists_.emplace(
      <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLocalNetwork</span>,
      <span class="stx-qualifier">Allowlist</span>::FromDeclaration(<span>parsed_declaration</span>));
}
<span class="stx-keyword">if</span> (!has_explicit_loopback) {
  allow_lists_and_reporting_endpoints.allowlists_.emplace(
      <span class="stx-qualifier">network</span>::<span class="stx-qualifier">mojom</span>::<span class="stx-qualifier">PermissionsPolicyFeature</span>::<span class="stx-const">kLoopbackNetwork</span>,
      <span class="stx-qualifier">Allowlist</span>::FromDeclaration(<span>parsed_declaration</span>));
}
</code></pre>

<h4>Impact analysis</h4>
<p>A sandboxed iframe that is explicitly denied loopback-network via Permissions Policy can still trigger a Local Network Access permission prompt and gain access to localhost after user approval.</p>
<p>This breaks the guarantee that embedders can reliably restrict sensitive network capabilities using Permissions Policy and sandboxing, and allows embedded content to access local network resources contrary to the declared policy.</p>
