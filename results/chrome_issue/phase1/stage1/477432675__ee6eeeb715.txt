<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Technical Details:
I have discovered a UI/Address Bar spoofing vulnerability in Google Chrome version 144.0.7358.97. The vulnerability allows a malicious website to display its own content while showing a trusted domain (e.g., hackerone.com) in the address bar.
Steps to Reproduce:</p>
<ol>
<li>Open Chrome and navigate to the attacker&#39;s site: <a href="https://0x403fox.github.io/spoofing.html" data-b-widget="url" data-b-original-href="https://0x403fox.github.io/spoofing.html" data-b-redirected-href="https://www.google.com/url?q=https://0x403fox.github.io/spoofing.html&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1du4PkwWmSrRyfpQEvvxRZ">https://0x403fox.github.io/spoofing.html</a>.</li>
<li>Click the &quot;Klik Untuk POC&quot; button.</li>
<li>A new tab opens, initially showing about:blank.</li>
<li>The content from the attacker&#39;s site is rendered, but the address bar incorrectly displays <a href="https://www.hackerone.com" data-b-widget="url" data-b-original-href="https://www.hackerone.com" data-b-redirected-href="https://www.google.com/url?q=https://www.hackerone.com&amp;sa=D&amp;source=buganizer&amp;usg=AOvVaw1qIeChTO--xFWLlR3AAQRl">https://www.hackerone.com</a>.</li>
</ol>
<h4>Impact analysis</h4>
<p>An attacker can exploit this vulnerability to perform highly sophisticated phishing attacks. By displaying a legitimate URL (like a bank or social media login page) while controlling the rendered content, the attacker can deceive users into providing sensitive credentials or personal information.
Even security-conscious users who verify the URL and HTTPS padlock icon would be misled because the browser&#39;s UI fails to reflect the true origin of the content.</p>

Author: dc...@chromium.org
<p>I&#39;ve gone through both videos, and while the PoC is able to use document.write in the newly-opened window, the origin displays about:blank–this is working as intended. A newly-opened window is almost always same-origin (ignoring sandboxed restrictions) to its opener. When the PoC uses location.replace to navigate somewhere else, the content that was written with document.write() no longer appears–there is no spoofing.</p>
<p>You can try to vary the PoC by opening a window to example.com/foo (which would display example.com as the origin), but if the opener uses document.write(), the origin display resets to about:blank.</p>
