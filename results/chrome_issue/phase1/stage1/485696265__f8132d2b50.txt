<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p><code>WasmTypeInfo::element_type()</code> and <code>WasmTypeInfo::type()</code> (src/wasm/wasm-objects-inl.h, lines 559-569) read the <code>canonical_element_type</code> and <code>canonical_type</code> uint32 fields from the in-sandbox <code>WasmTypeInfo</code> HeapObject <strong>without any SBXCHECK validation</strong>.</p>
<p>This is the same class of bug as <strong><a href="https://issues.chromium.org/issues/469759459" data-b-widget="issue-reference" data-b-issue-id="469759459">issue 469759459</a></strong> (fixed in commit <code>678e837e8c7</code>), where <code>WasmGlobalObject::type()</code> was renamed to <code>unsafe_type()</code> and an <code>SBXCHECK(type.is_valid())</code> was added. That fix covered <code>WasmGlobalObject</code> and <code>WasmTableObject</code>, but was <strong>not applied</strong> to <code>WasmTypeInfo</code>.</p>
<p>As noted in the fix comment for 469759459:</p>
<blockquote>
<p>&quot;Various consumers of ValueKind (e.g. ValueKind::name()) use the raw enum value as index into a global array. As such, if the index is corrupted (which must be assumed, as it comes from within the sandbox), this can lead to out-of-bounds reads outside the sandbox. [...] This SBXCHECK accomplishes that.&quot;</p>
</blockquote>

<h3>WasmTypeInfo is in-sandbox</h3>
<p><code>WasmTypeInfo extends HeapObject</code> (src/wasm/wasm-objects.tq:295-300) — it lives within the sandbox and its <code>canonical_type</code> / <code>canonical_element_type</code> uint32 fields can be corrupted by a sandbox attacker. Additionally, <code>WasmTypeInfo</code> is NOT registered in <code>SandboxTesting::GetFieldOffsetMap()</code> (src/sandbox/testing.cc), meaning it has <strong>zero sandbox fuzzer coverage</strong>.</p>
<h3>Impact 1: OOB Heap Write via element_type() (PoC 1)</h3>
<p>A corrupted <code>canonical_element_type</code> flows through <code>element_type()</code> → <code>value_kind_size()</code> → <code>kValueKindSize[]</code> (a C array without bounds checking). In <code>array_copy_wrapper</code> (src/wasm/wasm-external-refs.cc:789), the corrupted size controls <code>MemCopy</code>:</p>
<pre><code><span class="stx-keyword">int</span> <span>element_size_bytes</span> = element_type.value_kind_size();  <span class="stx-comment">// corrupted</span>
<span class="stx-class">size_t</span> <span>copy_size</span> = length * <span>element_size_bytes</span>;
MemCopy(<span class="stx-class">dst</span>, <span class="stx-class">src</span>, <span>copy_size</span>);  <span class="stx-comment">// OOB copy</span>
</code></pre>
<p>Changing element type from i32 (size=4) to i64 (size=8) causes <code>array.copy</code> to write <strong>2x</strong> the intended bytes into adjacent heap objects.</p>
<p>Confirmed output (V8 14.7.0, arm64, release):</p>
<pre><code>OOB: dst[32] = 0xdead0020
OOB: dst[33] = 0xdead0021
...
OOB: dst[63] = 0xdead003f
</code></pre>
<p>32 elements written beyond the intended copy range.</p>
<h3>Impact 2: OOB Read from C++ heap via type() (PoC 2)</h3>
<p>A corrupted <code>canonical_type</code> flows through <code>type()</code> → <code>type_index()</code> → <code>IsCanonicalSubtype_Locked()</code> (src/wasm/canonical-types.cc:337), which accesses <code>canonical_supertypes_[corrupted_index]</code> — a <code>std::vector</code> on the C++ heap. Caught by Chrome&#39;s libc++ hardening (not by V8-level SBXCHECK):</p>
<pre><code>libc++ Hardening assertion __n &lt; size() failed: vector[] index out of bounds
...
IsHeapSubtype → JSToWasmObject → WebAssemblyGlobalSetValue
</code></pre>

<h3>Suggested Fix</h3>
<p>Add <code>SBXCHECK(type.is_valid())</code> to both accessors, mirroring commit 678e837e8c7:</p>
<pre><code><span class="stx-qualifier">wasm</span>::<span class="stx-class">CanonicalValueType</span> <span class="stx-qualifier">WasmTypeInfo</span>::<span>element_type</span>() <span class="stx-keyword">const</span> {
  <span class="stx-keyword">auto</span> <span>type</span> = <span class="stx-qualifier">wasm</span>::<span class="stx-qualifier">CanonicalValueType</span>::FromRawBitField(canonical_element_type());
  SBXCHECK(<span>type</span>.is_valid());
  <span class="stx-keyword">return</span> <span>type</span>;
}

<span class="stx-qualifier">wasm</span>::<span class="stx-class">CanonicalValueType</span> <span class="stx-qualifier">WasmTypeInfo</span>::<span>type</span>() <span class="stx-keyword">const</span> {
  <span class="stx-keyword">auto</span> <span>type</span> = <span class="stx-qualifier">wasm</span>::<span class="stx-qualifier">CanonicalValueType</span>::FromRawBitField(canonical_type());
  SBXCHECK(<span>type</span>.is_valid());
  <span class="stx-keyword">return</span> <span>type</span>;
}
</code></pre>
<p>Additionally:</p>
<ul>
<li>Register <code>WasmTypeInfo</code> in <code>SandboxTesting::GetFieldOffsetMap()</code> for sandbox fuzzer coverage</li>
<li>Add <code>SBXCHECK_LT(sub_index.index, canonical_supertypes_.size())</code> in <code>IsCanonicalSubtype_Locked()</code> for defense-in-depth</li>
</ul>
<h4>Impact analysis</h4>
<p>An attacker with in-sandbox write capability (e.g., via a separate V8 renderer bug) can corrupt <code>WasmTypeInfo</code>&#39;s <code>canonical_element_type</code> or <code>canonical_type</code> fields to trigger:</p>
<ol>
<li>
<p><strong>OOB heap write</strong> (Path 1): Corrupting <code>canonical_element_type</code> from i32 to i64 doubles the <code>MemCopy</code> size in <code>array_copy_wrapper</code>, writing controlled data beyond the destination array into adjacent heap objects. The <code>kValueKindSize[]</code> lookup uses a C array (not std::vector), so this is NOT caught by libc++ hardening. This can be chained with heap grooming to overwrite critical object fields.</p>
</li>
<li>
<p><strong>OOB read from C++ heap</strong> (Path 2): Corrupting <code>canonical_type</code> to an out-of-range type index causes <code>IsCanonicalSubtype_Locked</code> to access <code>canonical_supertypes_[corrupted_index]</code> on the C++ heap. This is caught by libc++ hardening in Chrome release builds, but there is no V8-level SBXCHECK.</p>
</li>
</ol>
<p>This is the exact same bug class as the already-fixed <a href="https://issues.chromium.org/issues/469759459" data-b-widget="issue-reference" data-b-issue-id="469759459">issue 469759459</a>, where <code>WasmGlobalObject::type()</code> lacked SBXCHECK. The fix for that issue was backported to V8 14.5 (Chrome 145 Stable), but <code>WasmTypeInfo</code> was not addressed — it was simply missed. <code>WasmTypeInfo</code> also has zero sandbox fuzzer coverage (not registered in <code>GetFieldOffsetMap()</code>), explaining why this was not caught by automated testing.</p>
