<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<h1>VRP PoC #2: Prototype Pollution on GinJavaBridge Objects</h1>
<h2>Summary</h2>
<p>JavaScript bridge objects created via <code>addJavascriptInterface()</code> have a <strong>writable <code>__proto__</code></strong> property. An attacker can inject arbitrary properties and functions onto the bridge object&#39;s prototype chain.</p>
<p>The bridge object is:</p>
<ul>
<li><strong>NOT frozen</strong> (<code>Object.isFrozen() === false</code>)</li>
<li><strong>NOT sealed</strong> (<code>Object.isSealed() === false</code>)</li>
<li><strong>Extensible</strong> (<code>Object.isExtensible() === true</code>)</li>
</ul>
<p>This allows an attacker to:</p>
<table>
<thead>
<tr>
<th>Attack</th>
<th>Result</th>
</tr>
</thead>
<tbody>
<tr>
<td>Inject <code>isAdmin()</code> → returns <code>true</code></td>
<td>Privilege escalation</td>
</tr>
<tr>
<td>Inject <code>validateSession()</code> → returns <code>true</code></td>
<td>Auth bypass</td>
</tr>
<tr>
<td>Shadow <code>getAuthToken()</code> with interceptor</td>
<td>Token theft (MITM)</td>
</tr>
<tr>
<td>Inject <code>secretConfig</code> data property</td>
<td>Fake configuration injection</td>
</tr>
<tr>

<td>Poison bridge in ALL frames</td>
</tr>

<h2>Severity</h2>
<p><strong>MEDIUM-HIGH</strong></p>
<ul>
<li>Affects all Android WebView versions (Chrome 133 through Chromium 147)</li>
<li>Requires attacker-controlled JS execution in the same WebView (via XSS, ad iframe, or malicious page)</li>

<hr>
<h2>Root Cause</h2>
<p>In <code>content/browser/android/java/gin_java_bridge_object.cc</code>, the bridge wraps Java objects as V8 objects using a <code>NamedPropertyHandlerConfiguration</code> interceptor. However:</p>
<ol>
<li><strong><code>__proto__</code> is handled by V8 before the interceptor</strong> — V8&#39;s own prototype chain mechanism processes <code>__proto__</code> assignments before GinJavaBridge&#39;s interceptor sees them</li>
<li><strong><code>Object.freeze()</code> is never called</strong> on the wrapper object after creation</li>
<li><strong><code>v8::ObjectTemplate::SetImmutableProto()</code></strong> is not used on the object template</li>
<li>The wrapper object inherits from <code>Object.prototype</code> with full mutability</li>
</ol>
<pre><code>V8 Object Creation Flow:
  1. GinJavaBridge creates wrapper via ObjectTemplate
  2. ObjectTemplate has NamedPropertyHandler (intercepts get/set)
  3. BUT __proto__ is V8-internal, NOT intercepted
  4. Object.freeze() / SetImmutableProto() are NEVER called
  5. Result: __proto__ is fully writable
</code></pre>

<h2>Suggested Fix</h2>
<h3>Option A: Freeze the bridge object (minimal change)</h3>
<pre><code><span class="stx-comment">// In gin_java_bridge_object.cc, after creating the wrapper:</span>
<span class="stx-qualifier">v8</span>::<span class="stx-class">Local</span>&lt;<span class="stx-qualifier">v8</span>::<span class="stx-class">Object</span>&gt; wrapper = ...;

</code></pre>
<h3>Option B: Use immutable prototype (preferred)</h3>
<pre><code><span class="stx-comment">// In gin_java_bridge_object.cc, on the ObjectTemplate:</span>
<span class="stx-qualifier">v8</span>::<span class="stx-class">Local</span>&lt;<span class="stx-qualifier">v8</span>::<span class="stx-class">ObjectTemplate</span>&gt; <span>tmpl</span> = <span class="stx-qualifier">v8</span>::<span class="stx-qualifier">ObjectTemplate</span>::New(<span>isolate</span>);
tmpl-&gt;SetImmutableProto();  <span class="stx-comment">// Prevents __proto__ modification</span>

<pre><code><span class="stx-comment">// Create wrapper with null prototype (no __proto__ chain to pollute)</span>

<h4>Impact analysis</h4>
<p>An attacker-controlled web page loaded in any Android WebView can pollute
the prototype chain of Java bridge objects created via addJavascriptInterface().</p>
<p>Bridge objects are never frozen (Object.isFrozen()===false) and <strong>proto</strong> is
fully writable. This allows an attacker to:</p>
<ol>
<li>Privilege escalation: Inject bridge.<strong>proto</strong>.isAdmin = ()=&gt;true — any app<br>
code calling bridge.isAdmin() now returns true without hitting Java</li>
<li>Authentication bypass: Shadow verifyPin() or validateSession() with
functions that always return true</li>
<li>Silent token theft: Replace getAuthToken() with an interceptor that
exfiltrates the real token to attacker&#39;s server while returning it
normally — user notices nothing</li>
<li>Cross-frame propagation: Pollution from an ad iframe propagates to the
bridge object in all frames including the app&#39;s main frame</li>
</ol>
<p>Injected methods are indistinguishable from real Java methods in for..in
enumeration. No user interaction required beyond loading the page.</p>
<p>Affects all Android WebView versions. Tested on Chromium 147.0.7717.0
(tip-of-tree) and Chrome 133.0.6943.137 (stable).</p>
<p>Root cause: gin_java_bridge_object.cc never calls SetImmutableProto() or
Object.freeze() on bridge wrapper objects.</p>

<p>I&#39;ve updated my PoC to reflect this accurately.</p>
<p><strong>However, I found three new findings that are more significant than the original report:</strong></p>
<hr>
<h3>Finding 1: Object.prototype pollution via bridge prototype chain</h3>
<p>The bridge object&#39;s prototype chain is:</p>
<pre><code>bankApp → GinJavaBridge proto (p1) → Object.prototype (p2) → null
</code></pre>
<p><code>bankApp.__proto__.__proto__ === Object.prototype</code> returns <strong>true</strong>.</p>
<p>This means an attacker can reach and pollute <code>Object.prototype</code> through the bridge chain:</p>
<pre><code>bankApp.__proto__.__proto__.isAdmin = <span class="stx-keyword">function</span>() { <span class="stx-keyword">return</span> <span class="stx-keyword">true</span>; };

<span class="stx-comment">// Now EVERY plain object in the entire JS context is poisoned:</span>
<span class="stx-keyword">var</span> <span>config</span> = {};
config.isAdmin();  <span class="stx-comment">// returns true</span>
({}).isAdmin();    <span class="stx-comment">// returns true</span>
</code></pre>
<p>This is fundamentally different from own-property modification. Own-property modification (<code>bankApp.foo = 1</code>) only affects that single reference. <code>Object.prototype</code> pollution affects <strong>every object in the JS execution context</strong> — including objects the attacker has no direct reference to.</p>
<p><code>Object.prototype</code> pollution is a well-recognized vulnerability class with multiple CVEs (e.g., CVE-2019-10744 lodash, CVE-2019-11358 jQuery, CVE-2021-25946 &quot;set-in&quot;, CVE-2020-28498 elliptic). The bridge chain provides a direct path to it.</p>
<p><strong>Verified output:</strong></p>
<pre><code>[CRITICAL] bankApp.__proto__.__proto__ IS Object.prototype!
({})._GLOBAL_POISON_ = GLOBAL_LEAK
[CRITICAL] Object.prototype polluted via bridge chain!
[CRITICAL] Every JS object in this context is poisoned!
</code></pre>
<hr>
<h3>Finding 2: All bridge objects share the same prototype</h3>
<p>When an app registers multiple bridges (which is common — e.g., a banking SDK + analytics SDK + ad SDK), they all share the <strong>same</strong> GinJavaBridge prototype:</p>
<pre><code>Object.getPrototypeOf(bankApp) === Object.getPrototypeOf(paymentApp)  <span class="stx-comment">// true</span>
</code></pre>
<p>Polluting one bridge poisons ALL bridges:</p>
<pre><code>bankApp.__proto__._POISON_ = <span class="stx-string">&quot;FROM_BANK&quot;</span>;
paymentApp._POISON_;  <span class="stx-comment">// &quot;FROM_BANK&quot; — leaked across bridges!</span>
</code></pre>
<p>Real-world scenario: A malicious ad SDK&#39;s JavaScript pollutes its own bridge prototype → the banking bridge prototype is automatically poisoned because they share the same proto object. The ad code never needs to reference <code>bankApp</code> directly.</p>
<p><strong>Verified output:</strong></p>
<pre><code>bankApp proto === paymentApp proto: true
[VULN] Polluting bankApp proto POISONS paymentApp!
[VULN] Different bridge objects SHARE the same prototype!
</code></pre>
<hr>
<h3>Finding 3: Full prototype replacement via <code>Object.setPrototypeOf()</code></h3>
<p><code>Object.setPrototypeOf(bankApp, maliciousObject)</code> succeeds, allowing complete replacement of the bridge&#39;s prototype chain with an attacker-controlled object:</p>

<h3>Why these findings matter beyond &quot;attacker already has JS execution&quot;:</h3>
<ol>
<li>
<p><strong>Object.prototype pollution is a distinct vulnerability class.</strong> The argument &quot;if an attacker can run JS, it&#39;s already too late&quot; applies to DOM manipulation and own-property modification. But <code>Object.prototype</code> pollution escalates impact from &quot;I can modify one object&quot; to &quot;I can modify the behavior of ALL objects in the context, including ones I have no reference to.&quot; This is why <code>Object.prototype</code> pollution gets CVEs even in same-context scenarios.</p>
</li>
<li>
<p><strong>Cross-bridge pollution breaks SDK isolation assumptions.</strong> App developers register separate bridges for separate purposes, expecting isolation. A low-privilege bridge (analytics/ads) should not be able to affect a high-privilege bridge (banking/auth). The shared prototype violates this expectation.</p>
</li>
<li>
<p><strong>The fix is minimal and low-risk.</strong> Calling <code>SetImmutableProto()</code> on the ObjectTemplate would prevent prototype modification without breaking any legitimate use case (since no legitimate app modifies <code>__proto__</code> of a bridge object — they modify own properties, which would still work). This also prevents the <code>Object.prototype</code> pollution chain.</p>
</li>
</ol>
<p><strong>Suggested fix</strong> (unchanged, but now with stronger justification):</p>

tmpl-&gt;SetImmutableProto();  <span class="stx-comment">// Prevents __proto__ modification</span>
<span class="stx-comment">// Own property modification still works for backwards compatibility</span>
</code></pre>
