<h3>The problem</h3>
<h4>Please describe the technical details of the vulnerability</h4>
<p>Transient Activation Leak on Fullscreen Exit (ESC) enabling Clipboard Write &amp; Download Without User Gesture</p>
<p><em><strong>Technical Details:</strong></em></p>
<p>When a website enters fullscreen via a valid user gesture and the user presses ESC to exit fullscreen, Chrome incorrectly retains transient user activation for one additional task.
As a result, APIs that normally require a user gesture can be executed without user consent.</p>
<p><em><strong>Steps:</strong></em></p>
<ol>
<li>
<p>User clicks a button → triggers document.documentElement.requestFullscreen().</p>
</li>
<li>
<p>Page enters fullscreen.</p>
</li>
<li>
<p>User presses ESC to exit fullscreen.</p>
</li>
<li>
<p>A fullscreenchange event fires after exiting fullscreen.</p>
</li>
<li>
<p>Within this event handler, privileged APIs are called:</p>
<pre><code>  - navigator.clipboard.writeText()
   - Programmatic download via a.click()
</code></pre>
</li>
</ol>
<p><em><strong>Observed Behavior:</strong></em></p>
<pre><code>       -[BUG] clipboard.writeText() SUCCESS — activation LEAKED ❌
       -[BUG] Programmatic download triggered — activation LEAKED ❌
</code></pre>
<p>Both actions succeed without a new user gesture, indicating the transient activation was not cleared.</p>
<p><em><strong>Expected Behavior:</strong></em></p>
<p>-After exiting fullscreen via ESC:</p>
<p>-Transient user activation should be cleared immediately.</p>
<p>-clipboard.writeText() should fail with NotAllowedError.</p>
<p>-Automatic downloads via a.click() should not succeed.</p>
<p><strong>Root Cause:</strong>*</p>
<ol>
<li>
<p>Chrome retains the transient user activation beyond the expected lifecycle during fullscreen exit triggered by ESC.</p>
</li>
<li>
<p>This breaks the activation model defined in Chromium specifications:</p>
</li>
<li>
<p>User Activation Lifecycle</p>
</li>
</ol>
<h4>Impact analysis</h4>
<p><em><strong>Impact:</strong></em></p>
<p>Malicious pages could perform actions without explicit user interaction:</p>
<ol>
<li>
<p>Write arbitrary text to the clipboard.</p>
</li>
<li>
<p>Trigger file downloads silently.</p>
</li>
<li>
<p>Redirect or open new pages programmatically.</p>
</li>
</ol>
<p><em><strong>This allows bypassing user-gesture restrictions, which could be exploited in social-engineered attacks.</strong></em></p>

<p>Just an additional clarification:</p>
<p>ESC is not a positive-intent user gesture and should not confer any
activation or extend activation lifetime. It is a “cancel/exit” action for
fullscreen, and per the user activation model it should clear transient
activation immediately.</p>
<p>Because ESC is being interpreted as a gesture boundary where activation
is preserved, the observed behavior is not just a standard gesture
bypass but a lifecycle violation where a non-intent UI action
unexpectedly maintains activation for privileged operations.</p>
<p>This may justify reviewing the severity under the user activation
lifecycle correctness category, as this breaks assumptions for any API
that relies on &quot;gesture must be intentional&quot;.</p>

<p>When the page enters fullscreen and the user exits using <strong>ESC</strong>, certain APIs that require a <strong>user gesture</strong> can still be triggered <strong>programmatically</strong>, even though no valid user activation should remain.</p>
<p>The issue is <strong>not limited to the Clipboard API</strong>. Other sensitive APIs were also tested.</p>
<ul>
<li>
<p><strong>Phase 1</strong>:
After entering fullscreen and exiting with ESC <strong>without any click</strong>, clipboard access is correctly blocked, but a <strong>programmatic download is still triggered</strong>, indicating a partial activation leak.</p>
</li>
<li>
<p><strong>Phase 2</strong>:
After entering fullscreen, performing <strong>one click in fullscreen</strong>, and exiting with ESC, multiple APIs succeed unexpectedly:</p>
<ul>

<li>Programmatic download succeeds</li>
<li><code>navigator.hid.requestDevice()</code> succeeds</li>
</ul>
</li>
</ul>
<p>These actions should be blocked after fullscreen exit if no active user gesture exists.</p>
<p>This behavior occurs on a <strong>secure context</strong> (<code>https://</code>) and can be reproduced when the page is served via a web server (e.g., <code>python -m http.server</code>).</p>
