# Issue 368562236__a67257b4f4

**Bucket:** POTENTIAL

## Summary
The issue claims that Chrome allows cross-origin JavaScript execution via
drag-and-drop: HTML payloads dropped from a different origin into a
`contenteditable` element are not sanitized, so active content (e.g.
`onerror` handlers) executes and an XSS alert appears. The thread was closed
as WAI by a Chromium maintainer (DataTransfer `setData`/`getData` are
intentionally unsanitized; contenteditable insertion strips active content).

## Environment
- OS/runtime: Windows 10 (10.0.26200 x64), PowerShell 7, Node v24.13.1
- Browser: `C:\Program Files\Google\Chrome\Application\chrome.exe` — Chrome/151.0.7922.174 (Stable), V8 15.1.206.23
- Automation path: CDP over WebSocket (Node `WebSocket` client) against an isolated instance launched with `--remote-debugging-port=9222` and a fresh `--user-data-dir` under the repro workspace; HTTP file servers on `127.0.0.1:8000` / `127.0.0.1:8001`
- Required environment (per issue): Desktop Chrome Canary 131.0.6728.0 (reporter) / Canary 130.0.6723.4 (Chromium dev repro), macOS Monterey; two localhost origins (e.g. `python3 -m http.server` on 8000 and 8001)
- Attachments used: none (issue text contains no attachments; no issue page fetch performed)

## Environment gap
The observable was tested on the only available browser build, Chrome
151.0.7922.174 Stable on Windows, while the issue's own reproduction evidence
is tied to Chrome Canary 130/131 desktop (reporter: 131.0.6728.0; Chromium
developer: 130.0.6723.4, macOS). That is a version/channel mismatch for the
reported trigger, so per the reproduction criteria the bucket is POTENTIAL:
a version-matched Canary 130/131 run may show the reported effect. On the
available build the claimed browser-level observable (alert after a default
contenteditable drop) does not occur — the drop path strips all tested
active content.

## Attack chain
For the reported environment (Canary 130/131 desktop, two localhost origins):

1. Serve `dragme.html` on origin A (`http://127.0.0.1:8000`, e.g. `python3 -m http.server 8000`) and `dropme.html` on origin B (`http://127.0.0.1:8001`); `dropme.html` contains a `contenteditable` element. — browser + file server
2. Open both pages in the browser; `dragme.html` registers a `dragstart` handler that calls `dataTransfer.setData('text/html', '<img src="x" onerror="alert(...)">')`. — page JavaScript
3. Perform a real drag from the draggable element in origin A and drop it into the `contenteditable` element in origin B (mouse drag via CDP `Input.dispatchMouseEvent` + `Input.setInterceptDrags`, or a physical drag). — CDP / human
4. Expected observable (per issue): the dropped HTML is inserted unsanitized, the image fails to load, `onerror` fires, and an alert appears in the origin-B page — cross-origin JS execution.

## Notes
Executed attempts (2 consumed) on Chrome 151.0.7922.174, both reaching the
drop trigger point with readback disproving the claimed effect:

- **Attempt 1 — real cross-origin drag payload:** dragstart handler in origin A
  (`http://127.0.0.1:8000`) set `text/html` to
  `<img src="x" onerror="alert('XSS-FIRED origin=' + location.origin)">`.
  - verify: source page dragstart DataTransfer items read back as
    `[{"mimeType":"text/html","data":"<img src=\"x\" onerror=\"alert('XSS-FIRED origin=' + location.origin)\">"},{"mimeType":"text/plain","data":"hello from origin A"}]`
  - verify: drop dispatched into `#dropzone` of origin B (`http://127.0.0.1:8001`);
    contenteditable innerHTML read back after drop as
    `"\n  drop here&nbsp;<img src=\"x\">"` — the `<img>` element was inserted but the
    `onerror` attribute was stripped.
  - verify: no `Page.javascriptDialogOpening` event within 8 s (no alert).
- **Attempt 2 — payload battery through the same drop path:** six active-content
  payloads were dropped into the contenteditable (`img onerror`, `svg onload`,
  `iframe srcdoc` with `<script>`, `a href="javascript:..."`, `details ontoggle`,
  `math/mtext img onerror`).
  - verify: post-drop innerHTML readbacks, e.g.
    `"reset&nbsp;<img src=\"x\">"` (onerror removed),
    `"reset&nbsp;<svg></svg>"` (onload removed),
    `"reset&nbsp;<iframe></iframe>"` (srcdoc removed),
    `"reset<a> link</a>"` (javascript: href removed),
    `"reset s"` (ontoggle/details removed).
  - verify: `dialog=null` for every payload — no JavaScript executed.

These readbacks show the default contenteditable drop path in the available
build sanitizes active content, matching the maintainer's closing comment in
the issue thread ("If you paste into a contentEditable, you'll see that we do
strip active content", and DataTransfer `setData`/`getData` are deliberately
unsanitized — i.e. WAI). The unverified remainder is whether Canary 130/131
behaved differently; that version was not available and no downgrade was
attempted, hence POTENTIAL rather than REPRODUCED or NOT_REPRODUCIBLE
(2 consumed attempts, not 3). Severity, exploitability, and fix
appropriateness were not assessed.
