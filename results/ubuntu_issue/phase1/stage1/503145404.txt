### The problem


#### Please describe the technical details of the vulnerability

## Summary

A sandboxed iframe without `allow-popups` can open new unsandboxed browsing contexts when a user middle-clicks, Ctrl+clicks, or Shift+clicks a link within the iframe. The fix for CVE-2026-5903 (CL 7572487) only blocks navigation when `TriggeringEventInfo == kFromUntrustedEvent`. Trusted user input events bypass this check and reach the browser's `OpenURL` path, which has no sandbox popup enforcement.

## Root Cause

The CVE-2026-5903 fix in `FrameLoader::StartNavigation` (`third_party/blink/renderer/core/loader/frame_loader.cc`, lines 882-891) added a check that blocks new browsing context creation from sandboxed iframes, but scoped it too narrowly to untrusted events only:

```cpp
if (request.GetNavigationPolicy() != kNavigationPolicyCurrentTab &&
    request.GetTriggeringEventInfo() ==
        mojom::blink::TriggeringEventInfo::kFromUntrustedEvent &&
    frame_->GetSecurityContext()->IsSandboxed(
        network::mojom::blink::WebSandboxFlags::kPopups)) {
  return;
}
```

When a user performs a middle-click (button=1) or Ctrl+click on a link inside a sandboxed iframe, the resulting `MouseEvent` is trusted (`isTrusted: true`). The anchor element's `NavigateToHyperlink` method (`html_anchor_element.cc:482-484`) sets `kFromTrustedEvent`, which does not match the fix's condition.

The navigation then proceeds through a code path with no sandbox popup enforcement:

1. `FrameLoader::StartNavigation` — fix check passes (trusted event)
2. `LocalFrameClientImpl::BeginNavigation` — no sandbox check
3. `RenderFrameImpl::BeginNavigation` — sees non-`kCurrentTab` policy, calls `OpenURL()`
4. `RenderFrameHostImpl::OpenURL` (browser process, line 9823) — **no sandbox check**
5. `Navigator::RequestOpenURL` (line 1063) — **no sandbox check**
6. Browser opens new tab via `WebContentsImpl::OpenURL` → `delegate_->OpenURLFromTab`

This `OpenURL` path is distinct from the `CreateNewWindow` path used by `window.open()`, which has sandbox popup enforcement at both renderer (`create_window.cc:347-358`) and browser (`render_frame_host_impl.cc:10094`) levels.

## HTML Specification

The spec is unambiguous that sandbox popup blocking applies regardless of user gesture.

The "choose a navigable" algorithm (HTML spec §7.3.1.7, `document-sequences.html#sandboxWindowOpen`) lists conditions in a *first applicable* switch. The sandbox check:

> "If `sandboxingFlagSet` has the **sandboxed auxiliary navigation browsing context flag** set — The user agent may report to a developer console that a popup has been blocked."

This condition has **no precondition about transient activation**. It fires unconditionally when the flag is set. Contrast with `allow-top-navigation-by-user-activation`, where the spec explicitly created a separate flag conditional on user activation. No equivalent conditional variant exists for auxiliary navigation — the only way to permit it is to include `allow-popups` in the sandbox attribute at parse time.

The flag definition (§7.1.5, `browsers.html#sandboxed-auxiliary-navigation-browsing-context-flag`):

> "This flag prevents content from creating new auxiliary browsing contexts, e.g. using the `target` attribute or the `window.open()` method."

## Steps to Reproduce

1. Save the attached `server.py` and run `python3 server.py` — this starts a local HTTP server on port 8096
2. Open `http://localhost:8096` in Chrome 147.0.7727.101
3. The page contains a red-bordered iframe with `sandbox="allow-scripts"` (no `allow-popups`). Inside the iframe there are three links labeled "Link A", "Link B", "Link C"
4. **Middle-click** (press the mouse wheel button) on any of the three links inside the red-bordered iframe
5. **Result**: A new background tab opens, navigating to `http://localhost:8096/target`. The new tab displays a "Sandbox Bypass Evidence" table showing it has full capabilities (can call `window.open()`, can read cookies, runs on the same domain). The status panel on the original page turns red and shows "BYPASS DETECTED"
6. **Expected**: The navigation should be blocked because the iframe lacks `allow-popups`. No new tab should open

**Alternative triggers** (same result):
- **Ctrl+click** on any link inside the red-bordered iframe → opens a new background tab
- **Shift+click** on any link inside the red-bordered iframe → opens a new foreground window

**Control tests** (verify the sandbox is otherwise enforced):
- Click the "window.open() → blocked" button inside the red iframe → blocked (console shows sandbox error)
- Click the "JS Ctrl+click → blocked" button → blocked (CVE-2026-5903 fix catches synthetic untrusted events)
- Click the "JS middle-click → blocked" button → blocked (same fix)
- Left-click a link with `target="_blank"` → blocked
- Middle-click a link in the green-bordered iframe (`sandbox="allow-scripts allow-popups"`) → allowed (proves the link itself works; the only difference is `allow-popups`)

## Cross-Browser Comparison

Firefox 149.0 also exhibits the same behavior — a middle-click on a link in a `sandbox="allow-scripts"` iframe (without `allow-popups`) opens a new unsandboxed tab. This confirms the behavior is a cross-browser spec deviation, not an intentional Chrome design choice. Each browser should independently fix their implementation to match the spec.

## Affected Versions

- Chrome 147.0.7727.101 (confirmed)
- All versions after the CVE-2026-5903 fix (CL 7572487, merged at refs/heads/main@{#1587969})

## Suggested Fix

Remove the `kFromUntrustedEvent` condition so that ALL non-current-tab navigations from sandboxed-without-allow-popups frames are blocked:

```cpp
// frame_loader.cc:882-891
if (request.GetNavigationPolicy() != kNavigationPolicyCurrentTab &&
    frame_->GetSecurityContext()->IsSandboxed(
        network::mojom::blink::WebSandboxFlags::kPopups)) {
  return;
}
```

Additionally, add a browser-side defense-in-depth check in `RenderFrameHostImpl::OpenURL` to reject non-`CURRENT_TAB` dispositions from sandboxed frames missing `allow-popups`, similar to the existing check at `RenderFrameHostImpl::CreateNewWindow` (line 10094).



#### Impact analysis

## Impact

Web applications use the `sandbox` attribute to contain untrusted content — user-generated HTML in webmail clients, forums, embedded widgets, CMSes. Omitting `allow-popups` is an explicit decision to prevent sandboxed content from opening new browsing contexts.

This bypass allows the sandboxed content to open new tabs when a user performs middle-click — a routine browsing action ("open in new tab"). The practical impact:

1. **Popup bypass from contained content**: Sandboxed content that should not be able to open popups can present links that escape the sandbox via middle-click. This defeats the containment guarantee that embedding applications rely on.

2. **No sandbox flag propagation**: The new tab created through the `OpenURL` path does not inherit sandbox flags. In contrast, when `CreateNewWindow` is used (for `window.open()` with `allow-popups`), sandbox flags are propagated at `create_window.cc:360-364`. The `OpenURL` bypass skips this propagation entirely.

3. **Tab-under potential**: Middle-click opens a background tab. The user may not immediately notice a new tab has been opened by sandboxed content, which could serve as a vector for phishing pages that mimic the embedding site.
