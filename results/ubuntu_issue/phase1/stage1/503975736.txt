<h1>Problem Description</h1>
<p>A logic flaw exists in the interaction between the browser’s camera permission model and the HTML media capture mechanism, allowing a website to re-trigger access to the device camera interface even after the user has explicitly denied camera permission.</p>
<p>Specifically, after a user denies camera access through the standard permission dialog, the same origin can still programmatically invoke an HTML file input with the capture attribute. This causes the operating system to immediately open the camera interface without re-prompting for permission.</p>
<p>This behavior violates user expectations, creates a misleading permission state, and weakens contextual integrity around access to sensitive hardware. While this does not enable silent or automatic access to the camera stream, it effectively undermines the user’s explicit denial within the same interaction flow, enabling deceptive UI patterns and potential privacy abuse.</p>
<p>Actualy:</p>
<ol>
<li>The user denies camera permission.</li>
<li>The website is still able to trigger the system camera interface via HTML media capture.</li>
<li>The user may be misled into capturing and submitting an image, believing the action is unrelated to the previously denied permission or part of a required system process.</li>
<li>From the user’s perspective, the denial decision appears ineffective.</li>
</ol>
<p>Expected:
After a user explicitly denies camera access:</p>
<ol>
<li>Any subsequent attempt by the same origin to trigger camera-related functionality (including HTML media capture) should:</li>
</ol>
<ul>
<li>Be blocked, or</li>
<li>Require explicit user confirmation, or</li>
<li>Display a clear warning indicating that camera access is being requested again despite the prior denial.</li>
</ul>
<ol start="2">
<li>At a minimum, the denial decision should maintain contextual continuity within the same browsing session.</li>
</ol>
<p>Impact:
Although this issue does not allow silent or background camera access, it introduces meaningful privacy and security risks:</p>
<ul>
<li>Enables deceptive UI and social engineering scenarios.</li>
<li>Undermines user trust in permission prompts.</li>
<li>Breaks the expectation that selecting “Deny” effectively prevents camera usage.</li>
<li>Can be exploited for phishing, fake verification flows, or involuntary image collection.</li>
<li>Particularly risky in embedded or in-app browser environments where UI indicators are limited.</li>
</ul>

<p>Thank you for the report.</p>
<p>This behavior is Working as Intended (WAI) and does not constitute a security vulnerability.</p>
<p>The standard camera permission prompt controls access to the getUserMedia API, which grants a website programmatic, ongoing access to the device&#39;s live camera stream. In contrast, the HTML <span>&lt;input type=&quot;file&quot; capture&gt;</span> element does not grant the website access to the camera hardware or a live stream. Instead, it delegates the action to the operating system&#39;s native file picker or camera application.</p>
<p>When invoked, the website remains entirely entirely blind to the camera interface. It only receives the final image file if, and only if, the user manually takes a photo and explicitly confirms the decision to hand that file back to the browser. Because the user maintains full, interactive control over whether a photo is taken and uploaded, no security boundary is bypassed. Denying live camera access does not, and should not, prevent a user from manually uploading a photo using a standard HTML file input.</p>
