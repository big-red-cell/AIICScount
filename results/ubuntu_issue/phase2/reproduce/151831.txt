Bug #151831: password stealing via bashrc

URL: https://bugs.launchpad.net/ubuntu/+source/bash/+bug/151831

Metadata: security_related=true; information_type=Public Security; targets=bash (Ubuntu) (Won't Fix, Wishlist)

Description:
carrying on from this thread: http://ubuntuforums.org/showthread.php?t=572089

and a re-opening of this bug: https://bugs.launchpad.net/ubuntu/+bug/127116

basically, as .bashrc is editable by non-root, if you can get code onto a sudoers account it can modify .bashrc to alias 'sudo' (or gksudo, etc) to a script designed to mimic the behavior of sudo. This allows you to yoink the user's password next time they run a command using sudo, from whence you could get root privileges.

P.S.: I'm using the gutsy-beta, so this hasn't been fixed recently

Message 2 | Author: jdstrand | Subject: Re: password stealing via bashrc
Thank you for your report and helping make Ubuntu even better!

Having an rc file for shell initialization is not a bug, but a feature of the shell.  Unless you entirely remove rc file shell initialization, you cannot 'fix' this issue.  Eg, if you make ~/.bashrc read-only, the attacker only has to remove the read-only version and replace it with a new one (using the immutable flag is also not a viable option, as making the kernel enforce the immutable bit may not be appropriate for all users).

However, if you removed or made .bashrc, .bash_profile, .profile, .kshrc, or all the other shell initialization files read-only, many users would be upset at the loss of functionality, and is therefore also not a viable option.

Users should always use an absolute path to sudo or any commands run as a privileged user.  Eg:
   /usr/bin/sudo ...

instead of:
   sudo ...

This will thwart the attack.  Remember too that aliases also can't override an absolute path.  Eg using something like:
    alias /usr/bin/sudo="echo gotcha"

Results in:
-bash: alias: `/usr/bin/sudo': invalid alias name

Security minded users may also want to use file integrity checkers to alert to changes in these rc files.

Message 6 | Author: cjwatson | Subject: Re: password stealing via bashrc
.bashrc can only be edited if the account is otherwise compromised. If the account is compromised, then there is an arbitrary number of ways to attack it from within (for example, you could trivially leave a little daemon running as that user to capture passwords and instruct cron to restart it after reboots, or if they're a desktop user you could arrange for GNOME to start up your keylogger any time they log in). Fundamentally, users have the right to start programs with their own privileges, and rightly expect that with a modern system they will be able to configure the system to do that for them automatically (at various levels of expertise, whether in .bashrc or with "Add to Panel..." or whatever); the security boundary is around the account, not within it. Removing the .bashrc facility, worrying about how to execute sudo, and so on is closing the stable door after the horse has bolted.

Furthermore, there comes a point where removing convenience to gain tiny amounts of security is counterproductive. When the system is made sufficiently inconvenient for day-to-day use, users will simply find out (and document for each other) how to use root privileges to disable the inconveniences, and then you're right back to square one only worse because now deployed systems are less consistent and harder to support. We learned this lesson in the Warty cycle when sudo required a password for every escalation to root; as it turned out, the vast majority of our early adopters simply got into the habit of running 'sudo -s' and leaving root shells open because having to authenticate every time was so annoying. (For the same sort of reason, single sign-on is justifiably popular.)

With respect, I honestly think this bug should be closed again as Won't Fix for the reasons above. The Ubuntu security team is working on a number of other more effective measures to increase the security of the system, and I think it is appropriate to be able to reject those that are not likely to be effective.

Message 8 | Author: stebalien | Subject: Re: password stealing via bashrc
Privilege escalation via a key-logger is not a good example. It can be prevented by not letting a user write to a drive with execute permissions.

Preventing this exploit is relatively simple. Have a "super" PATH variable that trumps everything including functions, aliases, and the regular PATH variable. This variable could only be set by /etc/bash.bashrc, /etc/profile, or root. It's contents would look like PATH.

Example:
PATH=/bin:/sbin:/usr/bin:/usr/sbin:/usr/local/bin:/usr/local/sbin
SPATH=/usr/secure-bin:/sbin:/usr/sbin:/usr/local/sbin

There would be soft-links to security related binaries in the /usr/secure-bin folder.
